## a1: F2 — persistent chip when the retry budget is spent

**The finding.** When Ollama Cloud 503s exhausted the 4-attempt retry budget, the per-retry banner faded and the chat went silent. The user could not tell whether the agent was thinking, retrying, or fully stalled.

**Root cause.** The backend emitted an `ollama_retry` status event per retry (→ a transient, auto-fading banner) but emitted *nothing* when the budget was spent — it just raised, and the raise was caught upstream as a generic error.

**Fix.**
- `backends.py` — `stream()` yields a terminal `ollama_exhausted` backend-status event when the retry helper returns a retryable 5xx (budget spent), before the existing raise. Additive — the terminal error event still follows.
- `app.js` + `styles.css` — `handleBackendStatus` gains an `ollama_exhausted` branch → a **persistent** chip (no auto-fade). It names the model + attempt count, says the step is stalled, and suggests the other deepseek tier (pro/flash hit separate cloud quotas). Two affordances: "Switch model" (scrolls to + highlights the model selector — no auto-switch, since a mid-mission swap has caveats the user should own) and dismiss.

4 tests in [tests/test_backends.py](../tests/test_backends.py)::`TestOllamaExhaustedStatus`.

## a2: F6 — retry on open-phase timeout

**The finding.** The v0.6.3 field run was killed when the grill's cold call to `deepseek-v4-pro:cloud` hit the 240s read-timeout ceiling. The backend retried HTTP 5xx but **not** timeouts — a `ReadTimeout` was a hard, un-retried failure.

**Fix.**
- `backends.py` — `_open_chat_stream_with_retry` now catches `httpx.TimeoutException` during the **open phase** and retries it on the same exponential backoff as a 5xx. A timeout thrown back in *after* the response was yielded (the caller's own mid-stream consumption) is re-raised, not retried — guarded by an `opened_and_yielded` flag so a half-read stream is never silently restarted.
- Per-retry `ollama_timeout` status events; on budget exhaustion the helper re-raises, and `stream()` flushes the buffered retry events + emits a terminal `ollama_exhausted` (timeout flavor — `status_code` 0, `reason` "timeout") before the error event.
- **Read-timeout default 240 → 300s; overall 300 → 360s.** Env-var overridable (`RESONANT_OLLAMA_HTTP_READ_TIMEOUT_SEC`). 300s read + up-to-3 retries gives a slow-but-alive cloud real headroom. (The 300s value was the user's pick over 600s — generous without burning 10 minutes on a dead connection.)
- `app.js` — the `ollama_timeout` retry banner is phrased "Backend slow to respond" (no status code — it's a slow call, not an error response); the exhausted chip phrases the timeout flavor as "not responding (read timeout)".

11 tests in [tests/test_backends.py](../tests/test_backends.py) — timeout-retry emits the notify, all-timeouts exhaust + raise, mid-stream timeout is NOT retried, `stream()` emits the timeout-flavored exhausted event, retry events precede it, read-timeout default is 300.

## What this delivers

The v0.6.2 and v0.6.3 field runs both died at the cloud boundary —
once to a 503 storm, once to a read-timeout stall — with the GUI
giving the user no actionable signal. After v0.6.4:

1. A spent 5xx retry budget → a persistent chip, not a faded banner.
2. An open-phase timeout is *retried* (it was a hard failure before),
   on a 300s ceiling with headroom.
3. A spent timeout budget → the same persistent chip, phrased for the
   timeout case.

The next cloud-committed field run can survive a slow cloud instead
of dying at the first timeout.
