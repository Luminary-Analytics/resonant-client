## a1: Build the stub harness

Pre-v0.5.17, every test that wanted to exercise `Session.run()` had to either mock the entire backend inline (cumbersome) or use the real one (network-bound). Neither covered the deeper run() loop branches.

`tests/streaming_stub.py` ships:

- **`StreamingBackend` class** with the exact attribute surface Session expects (name, model, base_url, api_key, tool_mode, handles_tools, stream(), classify()).
- **Two construction modes:** `events=[...]` (single sequence replayed on every stream() call) and `scripts=[[...], [...]]` (per-call sequences for multi-iteration tool-dispatch tests).
- **`raise_on_stream=Exception(...)`** for testing the error fallback.
- **`classify_response` / `classify_should_raise`** for testing should_plan.
- **`stream_calls` list** capturing every stream() invocation's args (user_msg, history_len, tool_count, max_tokens, instructions_preview) for assertion.

Plus event-shape constructors so tests read declaratively:

```python
backend = StreamingBackend(events=[
    text_delta("Hello"),
    text_delta(" world"),
    tool_call("file_read", {"path": "x"}, call_id="c1"),
    done(model="custom-model"),
])
```

Plus assertion helpers (`kinds_of`, `events_of_kind`, `first_of_kind`).

[tests/test_session_run_with_harness.py](../tests/test_session_run_with_harness.py) ships **21 tests across 6 classes** covering the basic flow:

- `TestRunHappyTextPath` (9) — session.start metadata, text deltas forwarded, text.done concatenated, history append, status with done metadata, session.end with step count, step.start/end emission, max_steps cap → ERROR.
- `TestRunBackendErrorEvent` (2) — `error` event yields ERROR + SESSION_END and skips subsequent iterations.
- `TestRunBackendStatusPassThrough` (2) — `backend.status` events forwarded verbatim (the v0.5.6a1 contract); doesn't terminate the loop.
- `TestRunStreamException` (2) — backend.stream() raise → "Stream error: ..." + SESSION_END.
- `TestRunCancellationInsideStream` (1) — cancel_event flipped mid-stream yields cancelled events.
- `TestStreamingBackendItself` (5) — sanity checks on the harness.

## a2: Tool-dispatch denial branches

Using the harness to cover the cleanly-isolatable branches inside `for item in tool_calls:` — the denial paths and the await_user tool — without actually executing real tools.

[tests/test_session_tool_dispatch.py](../tests/test_session_tool_dispatch.py) ships **11 tests across 6 classes**:

- `TestMalformedToolArgs` (1) — invalid JSON arguments fall back to `{}` via the lines 780-783 + 896-899 defensive parsers. Original `arguments_str` preserved.
- `TestHookDenial` (2) — PRE_TOOL_USE hook returns `allowed=False` → TOOL_RESULT with denied=True (NOT is_error — hook decisions are informational), records call+result in conversation_history, continues to next tool.
- `TestExecutionPolicyDenial` (1) — `execution_policy.evaluate()` returns DENY → TOOL_RESULT with denied=True AND is_error=True, reason from `get_reason()` bubbles into output.
- `TestPermissionDenial` (3) — autonomy_tier="suggest" + non-read-only tool fires the permission check. Without callback, falls back to `auto_approve` flag → denied. With callback returning True → approved + tool executes. With callback returning False → denied.
- `TestAwaitUserTool` (3) — the v0.3.5 await_user tool. No callback returns the sentinel string. Callback exceptions caught and surfaced as "(error obtaining user input: ...)" without classifying as is_error.
- `TestCancelDuringToolLoop` (1) — cancel_event flipped between tool iterations: lines 888-891 see it at top of next loop body and emit cancelled events. Only the FIRST tool produced a result; the second was cut off.

## a3: Text-branch coverage

[tests/test_session_text_branches.py](../tests/test_session_text_branches.py) ships **13 tests across 4 classes** covering the branches that fire from the assistant's text shape:

- `TestTodosUpdated` (3) — markdown checkbox text triggers `parse_markdown_todos` and `TODOS_UPDATED` event with done/total counts. `[x]`/`[X]` both count as done.
- `TestChoicesFlow` (4) — `<choices>` block triggers CHOICES event + on_choice callback dispatch. The selected option becomes the next iteration's `user_msg`. Without callback, `options[0]` is selected (verified by checking backend.stream_calls[1]["user_msg"]).
- `TestHandlesToolsShortcut` (3) — `backend.handles_tools=True` (CLI backends like claude-code) makes tool_call events display-only. TOOL_CALL yielded but NO TOOL_RESULT. Synthetic "[CLI executed tools: ...]" assistant history entry. Breaks the agentic loop after iter 1.
- `TestPlanModeReturn` (3) — `plan_mode=True` causes Session to yield PLAN_GENERATED + STEP_END after first iteration and return without SESSION_END (caller handles approval flow).

## Carry-over to v0.5.18+

The streaming-stub harness is now a project asset — any future test that wants to drive Session.run() can use it. Remaining session.py gaps (106 lines):

- **Actual tool execution** (lines 1025-1115) — needs a stubbed `execute_tool` OR safe real tools (file_read on a tmp file). The harness gets us to the dispatch boundary; from there, real-tool tests are a different shape.
- **Doom-loop integration** (1275-1285) — covered indirectly by `test_doom_loop.py` for the underlying counters; the run-loop integration still needs harness-driven repeated tool calls.
- **`_execute_task` sub-agent forwarding** (1403-1494) — needs nested Session/StreamingBackend to mock the child run.

**Next harness payoff target: `harness/orchestrator.py` background-cycle methods.** The same StreamingBackend can drive `_run_cycle`'s planner/generator/evaluator role sessions. Currently 45% coverage; the harness should push it to 75-85%. v0.5.18 candidate.
