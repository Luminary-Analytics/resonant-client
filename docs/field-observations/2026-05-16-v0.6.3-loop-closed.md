# Field-observation log — v0.6.3 closed-loop test (attempted)

> Goal: the loop's first real closed-circuit test — dispatch two
> missions in one project against the Mac Studio, verify the second
> references skills the first produced. **Outcome: infra-blocked.**
> Ollama Cloud latency made the autonomous mission unrunnable. The
> v0.6.3 loop code could not be validated end-to-end this session.

---

## Run setup

- **Version:** v0.6.3 (loop-closed: F1 + loader-wiring + iter-chip)
- **Project:** `D:\Repos\_field-run-v063` — a seeded throwaway: a tiny
  argparse CLI (`app.py`) + `AGENTS.md`, git-initialized
- **Model:** `deepseek-v4-pro:cloud` (the v0.6.2 default-switch — pro
  for autonomous missions)
- **Mission 1 prompt:** "Add a `--version` flag to the CLI in app.py …
  print exactly `fieldrun 0.1.0` … minimal spec with 2-3 acceptance
  criteria appropriate."
- **Driver:** MCP Chrome preview tools

## What happened

1. Mission dispatched cleanly — composer accepted the project path +
   autonomous toggle; the mission session opened with the grill prompt
   sent as the first message.
2. **The grill's cold first call to `deepseek-v4-pro:cloud` timed
   out.** The chat showed `✗ timed out` + a "Stopped" run card after
   the HTTP read timeout (~120s) elapsed.
3. Clicked the **Continue** follow-up chip to retry the grill.
4. The retry ran — `thinking 135s` … `thinking 172s` … still in
   flight, no first grill question produced. A 10-25 question rigorous
   grill at multi-minute-per-question is not a viable unattended run.
5. Abandoned the run. The mission never left the `drafting` phase, so
   none of the v0.6.3 loop code (F1's iter-loop entry, the loader
   wiring, the iter-card chip, the extractor) was exercised.

## Finding — F-INFRA: the cloud model path is not viable for unattended field runs (HIGH)

This is the **third** consecutive field-run attempt blocked by Ollama
Cloud:

| Attempt | Model | Blocker |
|---|---|---|
| v0.6.2 mission 1 | flash | grill self-executed (F1 — since fixed) |
| v0.6.2 mission 2 | flash | 503 rate-limit storm, iter stalled |
| v0.6.3 mission 1 | pro | grill cold call timed out; retry crawled 172s+ |

Pro and flash are both `:cloud` models — proxied through
`ollama.com`, not the Mac Studio's local GPU. When Ollama Cloud is
congested, every call either 503s (flash, v0.6.2) or crawls past the
read timeout (pro, v0.6.3). The Mac Studio's only genuinely-local
model is `qwen3-vl:8b` — a vision model, too weak for an agentic
coding loop.

**Implication:** the closed-circuit field validation cannot be run
unattended-via-MCP while the cloud is congested. The v0.6.3 loop is
covered by unit + component tests (16 loader-wiring, 8 grill Rule 0,
+ live MCP verification of the chip), but the end-to-end "real model,
two missions" validation is still outstanding.

**Decision (2026-05-16, user):** *not* pulling a local coding model.
The best DeepSeek v4 (`pro`) only exists behind Ollama Cloud — a
weaker local model would validate the loop against a model that is
not the production flagship, which defeats the purpose. The project
stays committed to the `:cloud` model path. Therefore the client
must tolerate cloud variance, rather than the deployment routing
around it.

**Recommendations (revised after that decision):**
1. **Harden the client against a slow cloud** — the real lever, since
   the cloud model is here to stay. Concretely F6 below: a longer
   grill-phase read timeout + auto-retry, so a slow-but-alive cloud
   degrades gracefully instead of failing the run. This is the
   difference between a field run completing or not.
2. Treat the closed-circuit field validation as a
   "when-cloud-cooperates" task — cloud congestion is intermittent;
   kick the run off at a low-traffic window.
3. **Grill-phase timeout UX** (F6, new — see below) — both the
   resilience fix and the UX fix.

## Finding — F6: grill-phase timeout has thin UX (MEDIUM)

When the grill's model call timed out, the GUI showed a bare
`✗ timed out` error-block + a "Stopped" card, and the mission sat in
`drafting`. Recovery required the user to notice and click "Continue".

This is the same *family* as F2 (rate-limit stall UX) but a distinct
failure mode — an HTTP read timeout, not a 503-retry-budget
exhaustion, so F2's new `ollama_exhausted` chip does not cover it.

**Fix candidates:**
- A grill-specific read timeout that is longer than the chat default
  (a rigorous-grill cold call on pro is legitimately a long call).
- An auto-retry on grill-phase timeout (1-2×) before surfacing the
  error, mirroring the backend's 5xx retry.
- A clearer stalled-grill affordance than a generic error-block —
  e.g. "the model timed out drafting the spec — retry / switch
  model / simplify the prompt".

## What this does NOT invalidate

The v0.6.3 code shipped and is correct as far as the test surface
reaches:
- F1 (grill Rule 0) — 8 prompt-invariant tests; the grill *prompt* is
  correct, it just never got far enough to exercise it
- Loader wiring — 16 tests in `test_skill_loader_wiring.py`, including
  `dispatch_item` appending skills + emitting `skill_context_loaded`
- Iter-card chip — live-verified in MCP Chrome (simulated event →
  chip renders → pill opens the detail modal)

The gap is purely the *integration-under-a-real-model* tier.

## Carry-over

- **F-INFRA** → resolved by decision: stay on the `:cloud` model;

  "when-cloud-cooperates" task.
- **F6** → grill-phase timeout resilience + UX. **P0** — it is the

- The closed-circuit two-mission test remains the open validation
