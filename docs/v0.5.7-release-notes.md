## a1: honor `default_model` on every project switch

The pre-v0.5.7 `build_backend_spec` resolved the model with:

```python
selected_model = model or (models[0] if models else "")
```

When no explicit `model` was supplied (the project-switch path) the session always landed on whatever Ollama returned first in `/api/tags` — typically `deepseek-v4-flash` by alphabetical tag order. That happened even with `general.default_model` pinned to `deepseek-v4-pro:cloud`. The `apply_safe_default_backend` chain only writes that setting on first launch (when the value is empty), so the SETTING was correct — it just wasn't being read at session-construction time.

**Fix:** new `_resolve_default_model(models)` helper that prefers the configured value (case-insensitive) when it's present in the detected models list. Falls through to `models[0]` when the configured value is missing or unavailable, matching the legacy silent-fallback contract so this change doesn't introduce a new failure mode for users with stale settings pinning deprecated tags.

**10 new tests** in `tests/test_default_model_resolution.py` covering empty / configured / case-insensitive / missing-from-list / settings-failure paths.

## a2: disambiguate in-flight vs completed iter counter

The chat-header autonomous badge counts iterations from the live event stream (jumps to N at `autonomous_iteration_started`); the sidebar inspector counts entries in roadmap.md's iteration_log (only appended when an iter ships, so trails by 1 during an in-flight iter). Both correct under their own definitions but the visual disagreement was confusing during the linux-bridge run when iter 5 was running mid-Cargo-build.

**Fix:**
- `_autonomousState` now tracks `iterInFlight: bool`. Set true on `iteration_started`, cleared on `iteration_complete`, `iteration_failed`, and `reflection`.
- Header badge renders `iter N (running)` when `iterInFlight`, collapsing back to `iter N` once the iter ships. Same number, explicit state.
- Inspector label changed from `iter N` to `iter N completed`, with a hover tooltip explaining that the chat-header may show one ahead during an in-flight iter.

Frontend-only — no Python tests added.

## a3: reject `file_write`/`file_edit` paths starting with `-`

During the linux-bridge mission a file literally named `-p` appeared at the project root mid-iteration, almost certainly from a tokenization slip where `mkdir -p src` got split into three args (mkdir, -p, src) and `-p` landed in the path field of a write tool. The agent self-cleaned later, but only after the stray file had already polluted the working tree. Leading-dash filenames are also a known foot-gun for shell parsers — a later `rm <pattern>` may misinterpret the file as a flag.

**Fix:**
- New `_validate_write_path(path, allow_leading_dash)` helper in `engine/tools.py`. Rejects basename OR any intermediate path segment that starts with `-`. Skips Windows drive specs (C:) and `.` / `..` specials so legitimate paths still work.
- Wired into `_exec_file_write` and `_exec_file_edit`. Returns `ToolResult(is_error=True, ...)` with a clear message: "Refusing to write... almost always a tokenization slip". File is NOT written and intermediate directories are NOT created.
- Opt-in escape hatch via `allow_leading_dash: true` in tool args for the rare legitimate case (e.g. an `-rc1.tag` build artifact). Documented in both tool schemas so the model knows the dial exists.

**17 new tests** in `tests/test_leading_dash_path_guard.py` covering direct validator unit tests + integration tests through file_write and file_edit. Includes the exact field-observed `-p` case.

## a4: collapse dispatch card to a chip after click

Before this, clicking "Build autonomously" on the autonomous-mission dispatch card just disabled the buttons and relabeled the primary action "Daemon dispatched". The full card (preset row, blurb, fullauto note, etc.) stayed visible in the chat for the remainder of the run — visual clutter that competed with the live iteration cards for screen real estate.

**Fix:** new `_collapseDispatchCardToChip(card, budget)` helper replaces the card with a one-line chip recording:
- dispatch timestamp (HH:MM:SS) so the user can scroll back and see when the daemon was kicked off
- chosen budget for at-a-glance recall ("4h", "Full auto", etc.)
- Stop button that proxies to the existing `_handleAutonomousStopClick` flow (same confirm dialog + WS command + UI update as the chat-header badge's Stop affordance)

Frontend-only.

## a5: codify grill exemplar + REFLECT failure-annotation

Two positive findings from the linux-bridge run that we want to lock in against prompt-edit drift.

**Finding #12 — grill question quality.** All 27 questions in the linux-bridge run rated 5/5, following a consistent 5-beat pattern: acknowledge → bridge → options → recommend → invite override. Codified into a new EXEMPLAR section in the rigorous-mode addendum (`grill_me.py`). Includes a concrete worked example (CLI argparse question) so the model has something to pattern-match against, plus notes on active scope-narrowing (synthesis-confirmation), avoiding hedged recommendations, and skipping filler.

**Finding #9 — REFLECT failure annotation.** When a `[chrome]` or `[bash]` criterion fails, REFLECT was already annotating the criterion line with the actual diagnosis (e.g. "actual recipes live at `src-tauri/recipes/`" instead of just leaving the checkbox red). Excellent behavior — but undocumented. Added an ANNOTATE FAILURES section to `specialists.py` with bad/good examples and a `*(FAIL: ...)*` italic-marker pattern. Extends the rule to bash criteria where the deterministic pre-pass left vague evidence.

**12 new tests** total: 5 in `TestRigorousQuestionExemplar`, 7 in `TestReflectFailureAnnotation`. Both pin specific phrasing the docs use, so a refactor that drops the section catches in CI.
