# v0.5.6 — field findings become guard rails

**Date:** 2026-05-03
**Predecessor:** [`docs/v0.5.5-release-notes.md`](./v0.5.5-release-notes.md)
**Theme:** the post-v0.5.5 linux-bridge field run produced 12 actionable findings; v0.5.6 ships the four highest-severity ones as a1–a4.

---

## TL;DR

A real-world end-to-end run of an autonomous mission against an ambitious greenfield prompt (open-source Linux launcher for Windows apps — Tauri + Svelte greenfield, ~3,900 lines shipped over one mission) surfaced four issues that a synthetic test could never have. v0.5.6 fixes them as four small, focused alphas:

- **a1: Ollama 503 retries are now visible.** A new `backend.status` event surfaces transient cloud failures + retry attempts as a yellow header banner, so a 60-second silence isn't mistaken for a hang.
- **a2: spec-validity gate.** Truncated `## Final spec` blocks now render an actionable "Ask the model to complete the spec" card instead of crashing with a `ValueError` when the dispatch button is clicked.
- **a3: atomic terminal-state transition.** When the autonomous daemon hits `stuck` / `blocked` / `satisfied` / `failed`, roadmap.md status + session.mission_state.phase + GUI badge now all converge before the next user action — no more orphan-detection false positives.
- **a4: in-page text input for project switching.** Browser-mode users no longer need to drop into devtools to switch projects when the native folder picker is unavailable.

Full pytest **1652 pass / 2 skip**. **+24 net new tests** vs v0.5.5 (a1: 7, a2: 5 [tested via Python equivalents], a3: 24).

## a1: surface Ollama 503/retry as `backend.status` events

The linux-bridge run repeatedly stalled silently when Ollama Cloud returned `503 Service Unavailable` for our chosen model. The transparent retry already worked at the HTTP layer (`_open_chat_stream_with_retry` in `backends.py`), but it was completely invisible to the user — no log line, no event, no banner. A 60-second silence looked identical to a hang, prompting the user to cancel/restart and lose progress.

**Backend chain (5 layers, plumbed end-to-end):**
- `backends.py` — `_open_chat_stream_with_retry` now takes a `notify_retry` callback fired before each backoff with `{"kind":"ollama_retry","status_code","attempt","max","model","backoff_seconds","body_preview"}`. New `EVENT_BACKEND_STATUS = "backend.status"` constant.
- `events.py` — new `EngineEvent.BACKEND_STATUS = "backend.status"` enum value.
- `engine/session.py` — recognizes the new internal event type and re-emits as `make_event(EngineEvent.BACKEND_STATUS, **data)`.
- `OllamaBackend.stream()` buffers retry notifications between requests so they're yielded as proper events on the next chunk boundary, not lost mid-flight.

**Frontend:**
- New WS case `backend.status` → `_renderOllamaRetryBanner(event)` shows a yellow header banner: "⏳ Ollama returned 503; retry 2/4 in 8s for model deepseek-v4-flash". Auto-fades after `(backoff + 1.5)*1000`ms so the user sees it but it doesn't accumulate.
- New `.backend-status-banner` / `.backend-status-retry` / `.backend-status-banner-fading` styles in `styles.css`.

**7 new tests** in `TestOpenChatStreamWithRetryNotify` and `TestBackendStatusEventConstant` (mocked via `httpx.Client` patch).

## a2: spec-validity gate on dispatch card

The model truncated its `## Final spec` block mid-sentence in iter 9 of the linux-bridge grill. The user clicked "Build this roadmap" → backend `extract_spec()` parsed cleanly but `build_roadmap_from_spec` raised `ValueError: spec has no acceptance criteria`. The error surfaced as an opaque toast with no recovery path; the user had to manually prompt the model to "continue the spec" and re-paste.

**Frontend gate:**
- `_validateAutonomousSpec(specMd)` mirrors the backend `extract_spec()` semantics in JS: checks for `## Final spec` heading, `**Acceptance criteria:**` section, and ≥1 typed criterion matching `^- [ ] `[bash|chrome|vision|manual]``. Returns `{ok, reason, sectionsFound, criteriaCount}`.
- `handleMissionSpecReady` now calls the validator BEFORE building the dispatch card. On failure, renders a yellow `_buildSpecIncompleteCard(sessionId, validity)` with a "Ask the model to complete the spec" button that injects a continue-prompt into the chat input.
- Backend `extract_spec()` and `build_roadmap_from_spec` are unchanged — the gate is purely a UX layer that catches the truncation case before it can reach the error path.

**5 new tests** in `TestExtractSpecTruncationDetection` covering the truncation cases that the JS validator now refuses (and the backend would reject) — the JS-side validation logic mirrors the Python semantics so both must agree.

## a3: atomic terminal-state transition on stuck verdict

The most subtle finding from the field run. When the daemon hit a `stuck` verdict in iter 12, three pieces of state needed to converge:

1. roadmap.md `**Status:**` field on disk
2. session.mission_state.phase in the JSON session record
3. GUI badge

Before a3, only (3) updated — the WS event flipped the badge but roadmap.md kept `**Status:** running` and the session record stayed `autonomous_running`. On the next app launch, the orphan-detection scanner saw a "running" mission with no live daemon → falsely offered to resume a stuck mission. The sidebar mission browser also showed "running" badges on long-dead daemons.

**Two-sided fix.** Daemon writes (1), WS handler writes (2), in lock-step:

- `AutonomousMissionDaemon._emit_stop` now updates the on-disk roadmap status (`complete` / `paused`) BEFORE emitting the WS event, via a new idempotent `_update_roadmap_status_safely` helper. Same treatment for the run-loop crash path (sets status to `failed`).
- The terminal event payload now carries a `new_phase` field (`autonomous_complete` / `autonomous_paused` / `autonomous_failed`) so the WS handler doesn't need to re-implement the daemon's stop-reason → phase mapping.
- New module-level helper `_make_autonomous_event_forwarder(state, ws, loop)` in `gui/app.py` replaces the inline `_emit_autonomous` / `_emit_resume` closures in the WS handler. Forwards every daemon event to the WS, then on terminal events updates `session.mission_state.phase` via `cur.advance_mission_phase(new_phase)` + `cur.save()` and emits `sessions_updated` so the sidebar / orphan list / inspector all reconcile.

**Defensive contract:**
- intent_id mismatch → no-op (don't corrupt other sessions' state)
- missing new_phase → no-op (don't write empty string)
- session save failure → logged, swallowed (daemon thread keeps ticking, GUI badge still updates)
- WS send failure → logged, phase update still happens
- status update is idempotent (already-at-target writes are skipped)

**24 new tests** total: 9 in `TestAtomicTerminalStateTransition` covering complete/paused/blocked/misconfigured/user_stop/failed paths + idempotency + save-failure tolerance. 15 in the new `tests/test_autonomous_event_forwarder.py` covering pass-through behavior, terminal-event interception, intent-id mismatch, missing payload fields, save/send failures.

## a4: in-page text input for project switching

In browser mode (no pywebview window attached), clicking the project switcher hung indefinitely — the tkinter fallback opened a Tk window hidden behind the browser that looked like a hang, with no escape hatch. The field-run user had to drop into devtools and run `app.send({command:'set_project',path:'D:\\Repos\\resonant-linux-bridge'})` by hand.

**Three fixes shipped together:**

1. **Modal text-input fallback (`_promptForProjectPath`)** — a small centered modal with a path text input pre-filled to the current cwd, with the trailing path segment pre-selected so the common "tweak the folder name" edit is one keystroke. Enter to submit, Esc / backdrop / Cancel to dismiss. Reuses the snapshot-list-modal overlay styles for consistency.

2. **`folder_picker_unavailable` now opens the modal in-place** instead of bouncing the user back to `showNewSessionSetup()` (which abandoned the active session). Routes mission-composer picks back to the composer (preserves the existing `_pendingFolderPickConsumer` dispatch).

3. **Backend fast-path for browser mode.** When `_webview_window` is None, the backend now skips the tkinter dialog (the source of the apparent hang) and immediately emits `folder_picker_unavailable` so the modal opens at click-time instead of after a confused wait. Tkinter remains as a defensive belt-and-suspenders fallback.

**Discovery affordances:**
- Welcome screen's recent-projects list now has a "Type a folder path…" item alongside "Choose a different folder", so users who know the picker won't work in their setup don't have to wait for it to fail first.
- Header project pill: Shift-click or right-click goes straight to the modal, bypassing the picker round-trip.

Frontend-only feature (no JS test harness in this codebase); the backend change is one branch above an existing emit. Full suite still green.
