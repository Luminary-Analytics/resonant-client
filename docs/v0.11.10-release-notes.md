# Resonant Client v0.11.10

An internal restructuring release. No behaviour changes, no new features — the
groundwork that makes subsequent changes safer to make and easier to verify.

## Why a release with no visible changes

Two of the project's largest files had grown to the point where they were the
main obstacle to changing anything else: a single 9,300-line module containing a
2,400-line function and a 5,700-line class. Work of this kind is worth shipping
on its own, before it accumulates alongside behaviour changes and becomes
impossible to attribute if something regresses.

## What moved

- Harness prompt construction — how instructions and payloads are assembled for
  the generator and evaluator roles — now lives in its own module rather than on
  the interface server's state object. That was 95 methods and roughly four
  fifths of the class it was attached to.
- A further 24 WebSocket commands moved into the command registry introduced in
  v0.11.7, along with the payload builders they use.

The application's state object is down from 5,700 lines to 1,296, and its main
module from 9,287 to 4,241.

## Correctness work found along the way

- The git helpers determined which repository to inspect by reading a global
  application object, so the answer depended on process-wide state rather than
  the caller. They now take the project explicitly.
- Each extracted area gained tests that pin its boundary, including one that
  fails if the harness module starts reaching into the application for anything
  beyond its documented dependencies. Restructuring that is not fenced tends to
  undo itself.

## Validation

- Full Python suite: 2,909 passed, 2 platform-skipped. Ruff clean.
- Every extracted command verified round-tripping against a running server, and
  the interface confirmed loading with a live connection — the checks that
  matter for a change whose whole claim is that nothing behaves differently.
