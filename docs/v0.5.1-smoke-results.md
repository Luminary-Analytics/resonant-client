## Why pro is faster than flash on this workload

Counterintuitive but consistent with the design intent. Looking at the audit logs:

- **Flash** spends most of iter 1 inside the implementer specialist, exploring + writing in parallel. The plan was thin (one subgoal "build it"), so the implementer figures out structure as it goes.
- **Pro with PLAN_DEEP** spends a chunk up front in the planner reading existing files, then emits a more decomposed plan with 2–3 specific subgoals. Each subgoal is small enough that the implementer ships it in seconds.

Total iter time: pro's deeper plan + cheaper implementations < flash's single big implementation. For workloads where the spec maps cleanly to a few well-defined subgoals, pro wins.

This generalizes: **when the spec is well-formed, more planning up front is cheaper than more implementing later.** Pro's nature finally has a venue to express itself.

## Code quality comparison (qualitative, n=1 each)

Both produced clean, working CLIs. Subtle stylistic differences:

| | Flash (33 lines) | Pro (30 lines) |
|---|---|---|
| Encoding handling | `encoding="utf-8", errors="replace"` (defensive) | `encoding='utf-8'` (clean) |
| Output format | `f"{lines:>6}{words:>6}{chars:>6} {filepath}"` | `f"{lines:8d} {words:8d} {chars:8d} {filepath}"` |
| Error handling | argparse handles missing arg | manual `len(sys.argv) != 2` check + `os.path.isfile` check |
| Imports | `argparse` only | `sys` + `os` |
| Style | Modern Python (`def main() -> None:`) | Slightly older style (no type hints, two-space tabs in places) |

Flash leaned on stdlib idioms (argparse). Pro wrote more procedural code with manual validation. Both pass all 4 criteria. Both would pass code review.

For most users this is a wash; flash's argparse-first style is a touch more maintainable.

## What this unlocks for v0.5.1+

1. **Real product story for pro on autonomous.** RESONANT.md updated.
2. **The walker retry is a quiet improvement for ALL tiers.** Even flash benefits — a misformatted planner output (rare but happens) auto-recovers instead of going stuck.
3. **Cross-platform criterion authoring.** Spec authors can use `wc`, `find`, `grep`, `<`, etc. without thinking about Windows.
4. **The smoke harness is reusable.** `scripts/smoke_autonomous_counter.py` works for both tiers and any future tier we add (e.g. `kimi-k2.6:cloud`, `glm-5.1:cloud`, etc.).

## Open questions for v0.5.2+

1. **Other models** — does PLANNER_BY_TIER need entries for `kimi-k2.6`, `glm-5.1`, `minimax-m2.7`? They're all on the Mac Studio. Worth a smoke run.
2. **Pro on bigger specs** — wordcount is 4 criteria. The bootstrap-roguelite (8 criteria, multi-file, includes [chrome] + [vision]) is the real GA-banner test. Should pro run faster than flash there too?
3. **Walker retry effectiveness** — never fired during these smokes (both planners worked first try). Need a smoke against a flakier model OR a deliberately-malformed prompt to validate the retry path live.
4. **Cross-mission learnings** — when a planner repeatedly fails, should we adjust the prompt automatically? "Adaptive prompt tuning" is v0.6.0+ territory but the PLAN_DEEP success suggests it's a real pattern.
