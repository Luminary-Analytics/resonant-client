# v0.5.16 — remove `resonant serve` (orphaned legacy)

**Date:** 2026-05-06
**Predecessor:** [`docs/v0.5.15-release-notes.md`](./v0.5.15-release-notes.md)
**Theme:** strategic cleanup carried over from v0.5.12a2's triage. `engine/server.py` and the TUI's `serve` subcommand were the orphaned server side of a client/server pair — the paired client (`resonant connect`) was removed in v0.4.4, but the server was left in place anyway. v0.5.16 removes the server for symmetry. No bundled client today knew how to connect to it; no users of the asymmetric leftover were affected.

---

## TL;DR

Three deletions + four small tui.py edits, no behavior changes for any other code path:

- `resonant_client/engine/server.py` — deleted (191 lines, the `EngineServer` class).
- `tests/test_engine_server.py` — deleted (the v0.5.12a2 triage tests).
- `resonant_client/tui.py` — removed the `serve` subparser, the dispatch block in `main()`, the help-text mentions of `resonant serve` / `resonant connect`, and the now-stale `serve_parser`/`subparsers` setup.

Net: 11 fewer tests (the deleted file's coverage), -250 LOC across the deletions and tui.py edits, no functional regressions.

Full pytest **2091 pass / 2 skip**.

---

## Why now

The v0.5.12a2 alpha documented the asymmetry but deferred the removal as a strategic decision. The triage doc (in the module docstring, now also deleted with the file) called out:

> the paired client side — `resonant connect <ws_url>` — was removed in v0.4.4 when v0.4.0 cut the multi-backend infrastructure. This server is still importable + runnable from `resonant serve`, but there is no longer a bundled client that knows how to connect to it. External tools implementing the JSON-over-WebSocket protocol could still drive it, but no such tool ships with the project today.

The post-refocus product is GUI-first via `resonant-gui` (a different, actively-maintained WebSocket server in `gui/server.py`). The `engine/server.py` server served a different audience that no longer exists.

External integrations needing a programmatic interface should use `resonant_client.gui.server` via `resonant-gui` — it's the live, tested, GUI-driven path.

## What was removed

### Files

- `resonant_client/engine/server.py` — the `EngineServer` class (init, `handle_client` async router, `_run_session` worker thread, `start` entry point).
- `tests/test_engine_server.py` — the 11 minimal construction-level tests added in v0.5.12a2 to catch import-level regressions on the legacy code. Now redundant.

### tui.py edits

- **Argparse epilog** — removed the `serve` and `connect` example lines (both pointed at code that no longer existed or had no client).
- **Subcommand setup** — removed the `subparsers = parser.add_subparsers(dest="mode")`, the `serve_parser = subparsers.add_parser(...)` block, and the `--host` / `--port` arguments specific to serve mode.
- **Dispatch block in `main()`** — removed the `if args.mode == "serve":` block that constructed `EngineServer` and ran `asyncio.run(server.start())`.
- **In-app help text** — replaced the lines that mentioned `resonant serve` and `resonant connect` with a single `resonant-gui` entry pointing at the actual current architecture.

A v0.5.16 comment block was added explaining the removal in context of the v0.4.4 client-side cut.

### Carried-over comment

The v0.4.4 explanatory comment about `resonant connect`'s removal was kept (now joined by a v0.5.16 sibling). Anyone digging through `git blame` will find both contextual notes in the same place.
