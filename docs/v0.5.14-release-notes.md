## a1: harness/service.py coverage

The harness service hosts the shared static helpers that client shells delegate to: status normalization, text/list/mapping coercion, output-contract templates, role-specific instruction blocks, project summary, resume prompt. Pre-v0.5.14 the module was at 15% — the lowest harness module.

The static methods are pure functions and trivially testable. The gap was simply absence of test investment. The harness is opt-in (default off post v0.4.0 refocus per cluster 5), so the lifecycle methods only fire for users who turn it on, but the normalizers and contract-builders are critical when they DO run.

A regression in `normalize_contract_status` would silently misroute sprint state for opted-in users (proposed→approved→implemented transitions all flow through this method). `_normalize_string_mapping` is what turns `acceptance_evidence={"check1": True}` into the `{"check1": "PASS"}` format the harness consumers expect.

[tests/test_harness_service.py](../tests/test_harness_service.py) ships 50 tests across 7 classes:

- `TestNormalizeContractStatus` (16) — empty/None handling, canonical status pass-through, alias coverage, uppercase normalization, planner-role generator-ready phrase fallback, planner-role planning-complete fallback, "complete"/"completed"/"done" generic completion mapping per session_role, unrecognized status passes through.
- `TestTruncateText` (6) — short text unchanged, exact length unchanged, long text truncated with single ellipsis (length matches max_chars), strips surrounding whitespace, None treated as empty, max_chars=0 edge case.
- `TestNormalizeStringList` (10) — None/empty/string/whitespace-only/list/tuple/set inputs all produce expected canonical list. Coercion of non-strings verified.
- `TestNormalizeStringMapping` (8) — non-dict returns empty, basic mapping, whitespace stripping, empty keys/values dropped, bool True→"PASS"/False→dropped, non-string values coerced.
- `TestBuildOutputContract` (4) — chat mode returns empty, planner/generator/evaluator each emit a JSON template with the expected `action` + role-specific fields. JSON parses cleanly.
- `TestBuildInstructions` (4) — chat mode returns empty, planner + evaluator include the JSON output contract, generator role drops the contract block (correctly noted in source as noise for an edits-mostly session).
- `TestGetSummary` (2) — returns dict shape for a fresh project, normalizes a "ready_to_implement" contract status to "approved" in the summary output (integration of normalize + workspace read).

Coverage delta on `resonant_client/harness/service.py`: **15% → 69%** (remaining 31% is `build_resume_prompt` — long method, deferred).

## a2: harness/orchestrator.py static helpers

The orchestrator's static classification helpers drive **WHICH role runs next** in the planner→generator→evaluator cycle:
- `_choose_next_role` is the central state machine.
- `_is_generator_ready_contract` gates auto-approval.
- `_repairable_generator_failure` decides whether a blocked verdict gets a generator retry vs falling back to planner.
- `_is_retryable_failure` decides whether a single failure triggers a one-shot retry.

A regression in any of these would silently misroute the cycle — the kind of slow-burn defect that's invisible until users notice "my sprint keeps planning instead of generating" or "auto-approve isn't firing on a clean spec."

The dataclass `to_dict` methods (`HarnessCycleStep` / `HarnessCycleRun`) also weren't tested — `to_dict` truncates `result` to 500 chars while `to_full_dict` preserves the full text; that contract is critical for log size in the persisted run history.

[tests/test_harness_orchestrator_static.py](../tests/test_harness_orchestrator_static.py) ships 50 tests across 9 classes covering all eight static helpers + the two dataclass methods. Notable picks:

- `TestChooseNextRole` (11) — every branch of the state machine exercised: passed → None, no sprint → planner, proposed → planner, approved/needs_revision → generator, implemented → evaluator, blocked verdict + repairable → generator, blocked + non-repairable → planner, failed + blocked + repairable → generator (one-shot retry), failed without blocked → planner, unknown status → planner.
- `TestIsGeneratorReadyContract` (7) — all 5 read-only objective tokens that short-circuit to True; target_files + (line_hints OR validation_commands OR edit_strategy) → True; target_files alone insufficient.
- `TestRepairableGeneratorFailure` (7) — SyntaxError / Traceback / ModuleNotFoundError / IndentationError / TypeError tokens recognized in findings/summary/required_revisions/validation_artifacts. Case-insensitive.

The active background-cycle methods (`_run_cycle`, `_attempt_role_retry`, `_attempt_teacher_recovery`, plus the public lifecycle methods that start threads) remain at 0% — they need a stub backend harness + threading discipline that doesn't pay off in a hygiene minor. Deferred until the harness gets heavier real-world use.

Coverage delta on `resonant_client/harness/orchestrator.py`: **28% → 45%** (+17 pts).

## Carry-over to v0.5.15+

The biggest remaining harness gap is the active background-cycle methods in orchestrator.py (`_run_cycle` and friends, ~55% of the module). Covering those needs:
- A stub backend that lets the planner/generator/evaluator role sessions yield controlled event sequences.
- Threading discipline so the background ThreadPoolExecutor doesn't leak between tests.

Same shape of deferral applies to the deeper `engine/session.py` `run()` branches (~27% still uncovered): tool dispatch, doom-loop guards, compression-fires, choice handling, sub-agent forwarding all need a `backend.stream()` stub harness.

If a future hygiene minor wants to invest in that harness, the payoff is high — both modules would jump 20+ percentage points.

Other under-covered modules from the v0.5.11 audit remain candidates:
- `engine/clipboard.py` (30%) and `engine/accessibility.py` (20%) — both OS-specific, harder to test cleanly.
- `engine/mcp.py` (41%) — MCP integration.
- `harness/service.py:build_resume_prompt` — the deferred 31% from a1.

Strategic question still open from v0.5.12: should `engine/server.py` + `resonant serve` be removed for symmetry with the v0.4.4 `resonant connect` removal?

P0-P3 carry-over from v0.5.6 unchanged. P0 (field-validate via mdcheck) still gated on user's live run.
