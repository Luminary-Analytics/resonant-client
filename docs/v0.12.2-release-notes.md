# Resonant Client v0.12.2

Fixes an unresponsive interface when a configured model server is switched off.

## Clicking sessions does something again

If a provider Resonant was configured to use — Ollama, or an EXO host — was
switched off or unreachable, the app could stop responding: clicking a session
or starting a new one did nothing at all. Two separate problems combined.

**The connection was being dropped by its own error report.** A project switch
against an unreachable provider produced a legitimate error, the handler tried
to tell you about it, and that message hit a WebSocket the browser had already
closed. The resulting protocol error escaped the handler and ended the
connection. The frontend reconnected and hit the same thing again, so the
sidebar populated from the first burst and nothing else ever loaded. Failing to
*report* a failure is no longer fatal.

**Provider detection was slow and repeated.** Each unreachable host costs a
connect timeout, and those ran one after another — measured at 6.4 seconds with
both an Ollama and an EXO host down. That ran on every connect and every
project switch, with no feedback in the meantime.

Detection now probes providers concurrently and reuses a recent result rather
than re-checking hosts that cannot have changed in the last few seconds.
Explicitly re-checking backends, or changing a provider URL in Settings, still
forces a fresh probe.

Measured on a machine with both hosts down:

| | Before | After |
|---|---|---|
| First project switch | 6.5 s | 2.9 s |
| Later project switch | 6.5 s | 0.2 s |
| Switching session | unresponsive | instant |

## Also

- When Ollama is unreachable, the error now names the URL that was actually
  tried instead of quoting the default — which is misleading in exactly the
  case where a wrong URL is the problem. (Shipped in v0.11.16; worth repeating
  because it is what made this diagnosable.)

## Validation

- Full Python suite: 3,007 passed, 2 platform-skipped. Ruff clean.
- The dropped-connection cascade has a regression test covering a send to a
  closed socket, the error reply that follows it, and the case where an
  unrelated send failure must still surface rather than being swallowed.
- Verified in a running browser against the reported setup: project switches
  and session switches both complete, and the connection stays open across a
  provider failure that previously ended it.
