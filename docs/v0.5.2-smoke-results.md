## What v0.5.2 actually shipped (4 alphas)

Same 4-alpha + iteration-on-data pattern as v0.5.1.

### a1: Default tier flip + sharpened rigorous-grill prompt
- `network_defaults.get_default_model()` and the first-launch setting both flip to `deepseek-v4-pro:cloud`
- `RESONANT.md` repositioned: pro is recommended default; flash is the fallback for very-simple specs
- Rigorous-grill addendum (8 rules now, was 5):
  - **R1+** at least 3 questions probe edge cases / failure modes
  - **R2+** demand BEHAVIOR-testing criteria over existence-testing (with concrete bad/good examples)
  - **R3+** the 4-criterion floor splits into 4 distinct aspects (happy path / edge case / constraint / regression)
  - **R4 NEW** — for any output-producing feature, ask for a concrete input → expected-output example
  - **R5 NEW** — distinguish greenfield vs refactor in the first 3 questions
  - **R8 NEW** — question style cap: 1-2 sentences

### a2: parse_tool_calls handles `<tool_call name="X">` attribute form
Pro emits a different XML format than flash. The parser now supports four formats with a unified pattern + attribute capture group. Defense in depth (a3 below makes pro bypass the parser entirely).

### a3: Pro uses NATIVE Ollama tool calling
THE KEY FIX. Two missing pieces in `_detect_tool_support`:
1. `deepseek-v4-pro` was missing from `_KNOWN_TOOL_SUPPORT`
2. `/api/show` checked `template` for `{{.Tools}}` but ignored `capabilities` array (cloud models have empty templates)

Pro's `/api/show` reports `capabilities: ["completion", "tools", "thinking"]` — Ollama itself supports it natively. With both fixes pro now goes through the native Ollama tool-call API, which is rock-solid. No more XML format roulette.

### a4: Drop Form A `==` from `parse_bash_assertion`
Real-world commands routinely contain `==` (Python `assert`, bash `[[ ]]`, jq filters, etc.). Form A `_EQUALS_ASSERTION_RE` matched the FIRST `==` in `raw`, splitting the command at the wrong point. Form B (trailing `output == X` after the backticks) covers all real use cases unambiguously.

`<` and `>` stay in Form A but require `\d+` per v0.5.1a4.
