# Resonant Client — v0.6.8 Review & Harness Competitive Analysis

*2026-07-01 · Produced by a 23-agent review/research pass: 2 diff reviewers (findings adversarially verified), 1 capability mapper over the harness core, 7 web-research agents (Claude Code, OpenCode/Crush, Codex CLI/Gemini CLI, Aider/Cline/Roo, Goose + local-model serving, GLM/DeepSeek model-specific, cross-cutting techniques), 1 synthesis pass.*

## 1. What changed: v0.6.6 → v0.6.8 (+ follow-up)

Four commits since v0.6.5 GA, ~2,500 lines, almost entirely the web GUI:

- **v0.6.6** — Claude-style sidebar (project card, prominent "New session" button, Pinned quick-filter, typeahead project filter), simplified new-session flow, missions→sessions rename finished in user-facing copy.
- **v0.6.7** — composer footer decluttered: folder/project chip in; git-branch pill and "Plan this" fork icon out; dead `_renderMissionsGroup` chain removed.
- **v0.6.8 + refinement** — OpenCode-style titlebar (hamburger menus, command-palette pill, runtime-status popover with Servers/MCP/LSP/Plugins tabs backed by new `lsp_list`/`plugin_list` WS commands), updater controls (`check_updates` → WinSparkle, updater init at server start), frameless-window resize/move bridge APIs + DOM resize handles, folder-picker rework (start dir, tkinter focus mitigation, cancel-vs-unavailable), lazy session persistence (in-memory backend auto-created at connect; on-disk `SessionRecord` written only on first message), and two hardening fixes in `sessions.py` (Resonant source checkout excluded from default-cwd selection; `utf-8-sig` tolerance for recents.json).

Overall verdict from both reviewers: **decent quality for a diff this size**. Version strings agree at 0.6.8 (release gate holds), new HTML-rendering paths consistently escape interpolated values (no new XSS), removed DOM elements are null-guarded, and the lazy-session flow held up under tracing (cold start, project switch, first message). The confirmed defects are concentrated at integration seams.

_is_unsafe_cwd now flags the Resonant source repo, and because the recents loop applies the same check, users who last worked IN the resonant-client repo lose their project on every cold launch.

### F9. [low] `resonant_client/gui/app.py:5831`

The connect-time default-backend auto-create is an unsynchronized check-then-act: two concurrent WebSocket connections can both pass `if not state.backend` and run ensure_default_runtime_session/create_backend concurrently in executor threads, interleaving writes to the shared state.backend / state.backend_spec / state.session triple.

**Failure scenario:** Cold start with the GUI open in two browser tabs (or the desktop window plus a browser tab): both sockets connect before either finishes detect_backends + create_backend, both see state.backend None, and both call create_backend on threadpool threads. create_backend assigns self.backend = spec.create_backend(...) then self.backend_spec = spec then self.session = ... non-atomically, so interleaving can leave state.backend from call A paired with state.backend_spec/state.session from call B — e.g. a session whose spec/thinking-mode belongs to a different backend instance — plus costs.reset_session() firing twice. The same pattern exists in the 'init', 'redetect_backends', and 'set_project' handlers.

### F10. [low] `resonant_client/gui/app.py:8275`

_lsp_list_payload parses configured LSP commands with POSIX-mode shlex.split, which eats backslashes in Windows paths, so shutil.which never finds the binary and configured servers with absolute Windows paths always render as status 'missing'.

**Failure scenario:** On Windows (the primary platform), a user adds settings lsp_servers = {"pyright": {"command": "C:\\tools\\pyright\\pyright-langserver.exe --stdio"}}. shlex.split (POSIX rules) yields command_head 'C:toolspyrightpyright-langserver.exe'; shutil.which fails; the new LSP tab in the titlebar status popover reports the server as 'missing' even though the executable exists and the command is valid. shlex.split(command, posix=False) or ntpath-aware splitting is needed.

### F11. [low] `resonant_client/gui/static/app.js:602`

_bindWindowResizeHandles (and _bindWindowDragFallback at line ~665) retry forever at 1 Hz in plain-browser mode, registering a fresh {once:true} 'pywebviewready' listener on every cycle that never fires — an unbounded listener/timer leak.

**Failure scenario:** Run the GUI without pywebview (python -m resonant_client.gui.server opened in Chrome — the documented browser mode). hasResizeApi() is永 false, so each 1s timeout resets _waitingForResizeApi, re-enters the function, and adds another window 'pywebviewready' once-listener plus another setTimeout. Two functions do this concurrently: ~7,200 leaked listeners per hour in a long-lived tab, plus permanent timer churn. The listeners can never fire (no pywebview), so nothing ever stops the loop.

## 3. Where the harness stands (capability map)

Resonant Client (v0.6.8) is a mature, Ollama-only agentic coding harness with an unusually deep autonomous-mission stack. Its strongest assets today: (1) a hardened OllamaBackend with retry/backoff, open-phase timeout retry, a per-endpoint circuit breaker, and an AIMD adaptive concurrency governor; (2) a 4-format malformed-tool-call parser with JSON repair for text-mode models; (3) the plan-graph → specialist → walker orchestration with auto-verify/repair spawning and planner JSON-retry; (4) the autonomous-mission daemon with deterministic acceptance checks ([bash]/[vision] run by the runtime, verdict cross-checked against the roadmap so the model cannot fake convergence), 7 priority-ordered stop rules, park-on-human-decision, heartbeats and dispatch timeouts; (5) the provenance-gated skill self-improvement loop (extract → curate → inject), fully wired and tested. The weakest load-bearing pieces relative to state-of-the-art harnesses: edit application (file_edit is exact-match, first-occurrence, no fuzzy matching, no uniqueness guard, no structured repair loop), context management (compaction only fires at the start of a user turn — never mid-turn during a 50-step specialist run; the glm-5.2 compaction budget of ~96K tokens exceeds the default num_ctx=32768 so Ollama silently truncates long before compaction fires; no prompt/KV-cache-aware prompt assembly), codebase intelligence (keyword-only RAG, no embeddings/tree-sitter/repo-map, injected only on iteration 1), sandboxing (bash command content is unsandboxed — only cwd is validated; escapes are caught only by a handful of heuristic floor rules), and MCP (stdio-only, single-line blocking JSON-RPC, tools only). There is no git-based workspace checkpoint/rewind, no parallel sub-mission dispatch (known P3), no tool-arg schema validation (malformed args silently become {}), and no sampling-parameter control (temperature never set). Anything proposing "add skills", "add autonomous missions", "add acceptance checks", "add doom-loop guards", "add cost tracking", "add a smoke-test harness", or "add session fork/replay" would duplicate existing, working code.

### Per-area maturity and gaps

**[solid] Agent loop & cycle guards** — files: D:\Repos\resonant-client\resonant_client\engine\session.py, D:\Repos\resonant-client\resonant_client\events.py

Session.run() in engine/session.py: iterative stream→parse→execute loop, default max_steps=25 (specialists override: implement=50, reflect=20, plan_deep=16). Three independent stuck-detection layers, each two-stage (nudge then hard-stop): (a) trailing-identical doom loop (nudge at 2 repeats, stop at 4); (b) windowed signature cycle guard (3 occurrences in a 12-call window; per-model override: deepseek-v4-pro gets 4; nudge tells the model to call await_user, hard-stop only if nudge ignored); (c) read-only churn cap (14 consecutive read-only calls with zero writes, pro gets 20; bash/batch/task are neutral). await_user tool pauses the loop for a synchronous human answer. Choices (<choices> blocks), markdown-todo parsing (TODOS_UPDATED events), auto-lint/auto-test post-edit feedback injection with per-file fingerprint dedup, cooperative cancellation via threading.Event throughout, typed EngineEvent protocol consumed by TUI/GUI.

*Gaps:* Loop is strictly sequential per step — tool calls within a step execute serially (parallelism only via the explicit batch tool). System instructions are rebuilt every iteration and RAG/memory context is appended only on iteration 1, so the system prompt differs between iteration 1 and later iterations (defeats Ollama's implicit KV prefix cache every turn). No per-turn token accounting or budget display in the loop itself.

**[partial] Context management (compaction, context-window handling)** — files: D:\Repos\resonant-client\resonant_client\engine\compression.py, D:\Repos\resonant-client\resonant_client\engine\truncation.py

engine/compression.py: chars/4 token estimator, per-model compress thresholds (_MODEL_CONTEXT_BUDGETS: flash 24K, pro 96K, glm-5.2 96K, unknown 100K) with family-fallback matching; keeps last 6 user turns verbatim, summarizes older history via a ≤1024-token model call, replaces with a single '[Previous conversation summary]' assistant message. COMPRESSION event surfaces before/after token counts. Sub-agent Task results truncated to 8K chars; tool outputs centrally truncated (engine/truncation.py: head for file_read 2000 lines/50KB, tail for bash, per-line 500-char cap for grep, honest 'showing X of Y' footers).

*Gaps:* CRITICAL MISMATCH: compaction fires only when estimated history exceeds the model budget (96K tokens for glm-5.2), but the actual request num_ctx defaults to 32768 (env-fixed, never adapted per model) — so on the flagship, Ollama silently truncates/slides context long before the compressor ever runs; the comment in compression.py claiming this is 'safe under the 32K num_ctx' is arithmetically wrong. Compaction is checked ONCE at the start of run() (per user message), never mid-turn — a 50-step implement specialist within one turn can blow the window with zero compaction. Summarization is single-shot lossy prose (no structured file/decision ledger, no tool-result pruning as a cheaper first pass, no pinned-context mechanism).

**[solid] Tool set & tool-calling reliability** — files: D:\Repos\resonant-client\resonant_client\engine\tools.py, D:\Repos\resonant-client\resonant_client\backends.py, D:\Repos\resonant-client\resonant_client\protocol.py

~52 tools in AGENT_TOOLS (engine/tools.py, OpenAI function format): file ops (file_read/write/edit, glob, grep), bash (timeout-guarded, cancel-aware, tail-truncated), 12 browser_* (Playwright), 8+ computer_* + accessibility_tree/click + screen_ocr/record/diff + window/monitor/clipboard/process tools, 5 first-class git tools, 6 persistent REPL tools (python/node), task (sub-agents), batch (parallel, max 25, ThreadPoolExecutor 10 workers, recursion-guarded), await_user. Adaptive tool-calling in backends.py: native detection via known-model lists → /api/show capabilities/template → live probe (cached per model); text-mode fallback injects compact tool docs into system prompt and parses <tool_call> blocks. protocol.py parse_tool_calls handles 4 observed formats (bare tag, unclosed tag, name-attribute form found on deepseek-pro, GLM arg_key/arg_value XML) with _try_parse_tool_json repairing raw backslashes, literal newlines, and doing brace-matched manual extraction as a last resort; plus raw-JSON and bare 'bash(cmd)' detectors as final safety nets. Buffering strategy avoids streaming half a tool call as text. Allowlist enforcement at dispatch (real boundary, not just prompt filtering).

*Gaps:* No JSON-schema validation of tool arguments — session.py silently coerces unparseable args to {} (line ~897), so the tool errors with a confusing message instead of the model getting a targeted 'your args were malformed' repair prompt. call_id is a hash of name+args, so two identical calls in one response collide. grep shells out to Windows findstr (different regex dialect than the documented 'regex pattern'). glob caps at 50 matches with no pagination. No per-tool retry policy; recovery is entirely 'model sees the error string'.

## 4. Synthesis: executive summary

Resonant is furthest behind the pack in three load-bearing areas. (1) Context-window management: there is an outright arithmetic bug — the glm-5.2 compaction budget (~96K tokens in compression.py) exceeds the default num_ctx=32768, so Ollama silently head-drops history on the flagship long before the compressor ever fires; compaction also never runs mid-turn during 50-step specialist runs, there is no cheap tool-output-eviction tier before lossy summarization, and prompt assembly is actively KV-cache-hostile (the system prompt mutates between iteration 1 and 2, invalidating the Mac Studio's prefix cache every single turn — the self-hosted equivalent of paying full prompt price on every request). (2) Edit application: file_edit is exact-match, first-occurrence, no uniqueness guard, no fuzzy rescue, no repair hint — while every peer (OpenCode's 9-strategy replacer, Aider's flexible patcher with a measured 9X error reduction, Roo's Levenshtein apply_diff) ships forgiving edit application precisely because open models re-indent and emit literal \n constantly; each rejected edit costs a slow local re-prefill or a rate-limited cloud retry. (3) Model-wire correctness for the two flagships: DeepSeek's documented contract requires replaying reasoning_content across tool-call turns and session.py never does, sampling parameters are never pinned (Ollama's temp 0.8/top_p 0.9 defaults are off-distribution for both models and show up directly as malformed tool calls), tool args that fail to parse silently become {}, and the known Ollama-cloud encoding bugs (GLM stringifying nested object args, DeepSeek DSML tokens leaking into text) have no harness-side defense. A secondary gap is the absence of any workspace checkpoint/rewind — failed mission attempts fix-forward on top of their own damage, which is where open models spiral. Where Resonant is genuinely AHEAD and should protect its lead: the autonomous-mission stack (deterministic [bash]/[vision] acceptance checks whose verdicts are cross-checked against the roadmap so the model cannot fake convergence, 7 priority-ordered stop rules, park-on-human-decision, crash recovery) exceeds anything Claude Code, OpenCode, or Goose ship; the provenance-gated skill self-improvement loop is convergent with (and ahead of) Gemini CLI's experimental auto-memory; the 4-format malformed-tool-call parser with JSON repair and the AIMD concurrency governor + circuit breaker for ollama.com 403s are differentiated infrastructure no competitor has because no competitor is Ollama-native. Goose's removal of automatic lead/worker switching also validates Resonant's explicit plan-graph phase boundaries — do not build mid-session auto model swapping. Recommendations 1–6 below are quick wins: all small-effort, high-impact, and aimed squarely at local-model failure modes (silent truncation, edit-failure round-trips, prefill latency, wire-format flakes).

## 5. Recommendations (ranked by impact-per-effort)

### R1. QUICK WIN: Fix the num_ctx/compaction mismatch — per-model context sizing, truncate:false, mid-turn compaction checks

*Effort: small · Impact: high · Inspired by: Goose/Ollama local-model research (silent truncation in server/prompt.go, truncate:false escape hatch), Aider's per-request num_ctx auto-sizing, OpenCode's per-model limit.context metadata*

**What to build:** In backends.py: query /api/show per model at init, record effective context_length, and send options.num_ctx sized to the model (not the process-global RESONANT_OLLAMA_NUM_CTX=32768); pass truncate:false on /api/chat so overflow becomes a catchable error instead of Ollama's silent head-drop. In compression.py: derive _MODEL_CONTEXT_BUDGETS from the num_ctx actually in force (~80% of it) instead of the hardcoded 96K for glm-5.2 that exceeds 32768 — the comment claiming this is safe is arithmetically wrong. In session.py: check the compaction threshold inside the iteration loop, not just at turn start, so a 50-step implement specialist can't blow the window mid-turn.

**Why it matters for local models:** Silent mid-context loss is the single worst failure mode of Ollama serving: the model keeps the system prompt and last message but loses the middle of the mission — tool results, plan state, earlier file contents — with zero API signal, then re-reads files and contradicts its own decisions. Today this is guaranteed to happen on the flagship before compaction ever fires.

**Already have:** compression.py with per-model budgets, family-fallback matching, and COMPRESSION events; fixed num_ctx from env; the inventory itself flags this as a CRITICAL MISMATCH — the machinery exists, the arithmetic and trigger timing are wrong.

### R2. QUICK WIN: Fuzzy multi-strategy edit application with uniqueness guard and self-repair hints

*Effort: small · Impact: high · Inspired by: OpenCode's 9-strategy replacer pipeline (edit.ts), Aider's flexible patcher (9X error reduction measured), Roo Code's Levenshtein apply_diff, Claude Code's uniqueness-required exact Edit*

**What to build:** Rewrite _exec_file_edit in engine/tools.py as a strategy cascade: exact match → line-trimmed → whitespace-normalized → indentation-flexible (strip common base indent) → escape-normalized (models emit literal \n, \t) → block-anchor with Levenshtein middle-line similarity (~0.65 threshold). Add: uniqueness check when replace_all=false (error asking for more surrounding context if old_text matches multiple times — today the first occurrence is silently edited, potentially at the wrong location), a replace_all parameter, a disproportionate-match guard (refuse if the fuzzy match spans 3+ lines or 2x more than old_text), and on total failure return the closest-match snippet with its line number so the model can self-repair in one turn instead of guessing.

**Why it matters for local models:** GLM-5.2 and DeepSeek routinely fail exact-match edits via whitespace drift, re-indentation, and escaped newlines. Every rejected edit costs a full round-trip — slow prefill on the Mac Studio or a governor-metered cloud call — and repeated failures derail weak models entirely. Pure string algorithms, zero extra tokens, converts failed turns into successes deterministically. The inventory calls this the highest-leverage single improvement available.

**Already have:** Exact-string first-occurrence replace with a bare 'old_text not found' error; leading-dash path guard; post-edit auto-lint/auto-test feedback loops (which stay and get triggered more often once edits actually land).

### R3. QUICK WIN: KV-cache prefix discipline — byte-stable system prompt, append-only history

*Effort: small · Impact: high · Inspired by: Claude Code's 'prompt caching is everything' append-only request shaping, Manus ('KV hit rate is the most important production metric'), llama.cpp cache_prompt prefix-exact mechanics documented in the Goose/local research*

**What to build:** In engine/session.py: stop rebuilding system instructions every iteration and stop making iteration 1's prompt differ from iteration 2+ (RAG/memory/skills context is currently appended only on iteration 1, which mutates the prefix and invalidates Ollama's KV cache every turn). Freeze the system prompt + tool-schema JSON byte-stable at session start — stable tool ordering, sorted JSON keys, no timestamps — and move RAG/memory/skill context into the first user message or appended system-reminder messages. Make history strictly append-only except at explicit compaction events (each compaction = one deliberate, batched cache bust). In backends.py, serialize tool results deterministically and avoid interleaving unrelated requests on the same local model (per-slot caches thrash under OLLAMA_NUM_PARALLEL).

**Why it matters for local models:** There is no vendor cache bill — the 'prompt cache' IS the Mac Studio GPU doing or skipping a full re-prefill of a 50–100K-token transcript every agent step. Prefix reuse is the difference between ~1s and tens of seconds per step, and the current iteration-1-vs-2 prompt mutation forfeits it on every single turn of every session.

**Already have:** Fixed-options invariant (num_ctx/num_batch set once to avoid model reloads), keep_alive 120m, warm_up() — the backend half of the discipline exists; the prompt-assembly half actively defeats it.

### R4. QUICK WIN: DeepSeek reasoning_content replay + vendor sampling pins + per-role think effort

*Effort: small · Impact: high · Inspired by: DeepSeek V4 thinking-mode API contract (reasoning must be replayed across tool-call turns), GLM-5.2/DeepSeek model cards (temp 1.0), DeepSeek's own Claude Code integration (effort=max for agents)*

**What to build:** In session.py/backends.py: store message.thinking on every assistant turn and replay it verbatim in the messages array for all subsequent turns inside tool loops — DeepSeek's docs state interleaved reasoning MUST be passed back during tool calling, and Resonant currently drops it (harmless for GLM, whose template manages think retention). Pin per-model sampling in the options dict: glm-5.2 → temp 1.0/top_p 0.95; deepseek-v4 → temp 1.0/top_p 1.0 (or omit sampling entirely when thinking is on, matching DeepSeek's contract) — today temperature is never set and Ollama's 0.8/0.9 defaults are off-distribution for both. Route think effort per role: 'high' for interactive GLM sessions (latency), 'max' for DeepSeek autonomous missions (what DeepSeek itself auto-applies for agent harnesses). Clamp num_predict ≤65536 for deepseek-v4-pro:cloud (ollama#16890) to avoid 400s.

**Why it matters for local models:** Dropping reasoning_content silently lobotomizes the mission flagship's multi-step planning — the model loses its own chain of intent at every tool hop and re-derives plans, showing up as flip-flopping and redundant calls. Off-distribution sampling manifests directly as malformed tool-call XML/DSML and edit-format failures that Resonant pays for in retries. This is the most concrete pure-correctness gap found across all seven reports.

**Already have:** options.think plumbing with per-model wire-value mapping (_wire_think_value, verified live); per-model cycle-guard thresholds; no sampling control anywhere, no thinking replay.

### R5. QUICK WIN: Tool-argument validation ladder — schema check, JSON-string coercion, DSML leak salvage

*Effort: small · Impact: high · Inspired by: Cline's typed per-parameter errors with format reminders and progressive escalation, Goose toolshim (as a repair tier only), confirmed Ollama-cloud bugs #15645 (GLM stringifies nested objects) and #16375 (DeepSeek DSML tokens leak into text)*

**What to build:** In session.py's dispatch path (~line 897, where unparseable args silently coerce to {}): (1) validate parsed args against the tool's JSON schema and return a targeted "your arguments were malformed: <specific error> — expected format: <example>" repair message instead of dispatching {} and confusing the model with a downstream tool error; (2) when a parameter typed object/array arrives as a string, attempt json.loads before validation — this transparently rescues GLM's XML arg_key/arg_value template stringifying nested JSON on :cloud; (3) scan assistant text content for leaked '<|DSML|' tool-call markup (the format is regular; the string="true" attribute even declares types) and reconstruct it into a proper tool call or strip-and-retry, with a telemetry counter so smoke runs detect when Ollama upgrades fix/regress it; (4) fix the call_id hash collision by including an ordinal. Additionally flatten tool schemas in tools.py toward string/number/enum params (avoiding nested objects) — which also lands inside DeepSeek's strict-mode schema subset.

**Why it matters for local models:** These are the exact wire-level failure modes of both flagships on Ollama cloud today. A leaked DSML turn looks like a text-only response, the loop assumes the model chose not to act, and a multi-hour autonomous mission silently stalls; a stringified object arg hard-fails the tool and burns mission retry budget.

**Already have:** Best-in-class malformed-call PARSING (4 formats + JSON repair + brace-matched extraction in protocol.py) — but nothing validates what comes out of the parser, and no DSML/leak handling exists.

### R6. QUICK WIN: Ollama structured outputs (format param) for every non-conversational model call

*Effort: small · Impact: high · Inspired by: Ollama grammar-constrained structured outputs, Claude Code SDK structured-output workers, Goose recipes' schema-enforced response.json_schema, Anthropic's subagent structured-result contract*

**What to build:** Pass a JSON Schema in the /api/chat format field for every call that currently parses free text or retries on bad JSON: walker.py's planner subgoal expansion (replaces the 1-retry-with-generic-hint mechanism), acceptance_check.py/reflect.py verdicts, intent_service.py classification, backend.classify (SIMPLE/COMPLEX), grill_me.py final-spec extraction, and skill_mission_extraction.py outputs. Standardize a specialist return schema ({status, summary, files_touched, evidence, gaps}) so the walker consumes machine-checkable results.

**Why it matters for local models:** Grammar-constrained decoding makes malformed output structurally impossible rather than merely discouraged — converting 'usually valid JSON' into 'always valid JSON' at zero latency for exactly the model class that flubs it. Deletes entire retry loops across ~6 call sites and hardens the acceptance verdicts the whole mission stack depends on.

**Already have:** Planner JSON-retry (capped at 1, single generic hint) in walker.py; prose-parsed verdicts cross-checked by the deterministic roadmap layer (which stays as the backstop).

### R7. Tool-output eviction tier before summarization + oversized outputs paged to disk

*Effort: medium · Impact: high · Inspired by: Claude Code microcompaction (clear old tool outputs first) and tool-results-to-disk with 2KB previews, Anthropic context-editing beta (84% token reduction from eviction alone), OpenCode's prune-vs-summarize split, Goose's tool-call cutoff*

**What to build:** In engine/compression.py, add a pre-summarization layer: past a soft threshold, replace the bodies of tool results older than the last K calls with a one-line stub plus a re-fetch handle ('[output cleared — re-run file_read path X or read <scratch file>]'), keeping assistant/user turns intact. At ingest (engine/truncation.py), write tool outputs above ~50KB to a session scratch file with a ~2KB preview + path so the model re-reads only the slices it needs. Trigger eviction in large batches at high-water marks — each history rewrite is a deliberate KV-cache bust, so be infrequent-but-decisive. Pin todo/plan/mission-spec blocks so they survive every compaction verbatim.

**Why it matters for local models:** 70%+ of agent-session tokens are file dumps and command output that age fast. Eviction is FREE — no model call, no quality risk — whereas summarization costs a full-context generation by an open model that writes worse summaries than a frontier model. Every avoided summarization preserves mission fidelity and avoids a full re-prefill on the Mac Studio.

**Already have:** Single-shot lossy prose summarization (turn-start only) and solid head/tail ingest truncation with honest footers; no middle tier between them.

### R8. Shadow-git workspace checkpointing with rollback-on-failed-attempt

*Effort: medium · Impact: high · Inspired by: Gemini CLI's shadow repo at ~/.gemini/history/<hash> with /restore, Cline's per-tool-use checkpoints with three restore modes, Claude Code /rewind, OpenCode git-snapshot /undo*

**What to build:** New engine/checkpoints.py building on git_tools.py: a hidden GIT_DIR under ~/.resonant/projects/<hash>/shadow with --work-tree pointed at the project (never touching the user's real git index); commit-all before each file-mutating tool call in interactive sessions and before each dispatch in autonomous missions (hook into autonomous_factory.dispatch_item next to the existing inflight checkpoint). Expose three restores in the GUI (files-only, conversation-only, both — sessions.py already has the dual-history structure to support conversation rewind). Critical mission wiring: in autonomous_loop.py, when an acceptance check fails and a retry is scheduled, roll the worktree back to the pre-attempt snapshot so DeepSeek retries from pristine state with the failure report appended — instead of fixing forward atop its own mess.

**Why it matters for local models:** Open models mangle files more often than frontier ones and are notably bad at repairing their own damage — fix-forward spirals are where mission retry budgets die today. Snapshot-and-rollback gives every retry a clean start, keeps the user's git history pristine for morning review, and is genuinely cheap to build (git --git-dir/--work-tree add -A && commit, keyed by project hash).

**Already have:** Excellent SESSION persistence (dual histories, fork, replay, plan-graph snapshots, roadmap inflight checkpoints) — but nothing snapshots the user's FILES; the inventory explicitly lists 'no workspace checkpointing' as a gap.

### R9. QUICK WIN: offset/limit pagination on file_read and grep, with actionable truncation footers

*Effort: small · Impact: medium · Inspired by: Claude Code's Read offset/limit + cat -n line grounding, cross-cutting 'actionable truncation' consensus (footers that name the exact follow-up call)*

**Already have:** Central head/tail truncation with honest 'showing X of Y' footers and a 2000-line/50KB file_read cap — but no offset, so truncated content is permanently unreachable.

### R10. QUICK WIN: todo/plan recitation at the tail of context every turn

**What to build:** session.py already parses markdown todos (TODOS_UPDATED events) — extend it to re-render the current todo state + active goal as the final context block each turn, appended at the tail (append-only = KV-friendly; never rewrite it mid-history). ## Appendix A. Research digests

### claude-code

Claude Code is deliberately a simple, single-threaded agent loop (gather context -> act -> verify) wrapped in heavy harness engineering: deterministic tool contracts (exact-string Edit that fails loudly, Read-before-Edit enforcement, ripgrep-backed Grep/Glob instead of RAG), layered context management (auto-compaction plus 'microcompaction' that clears old tool outputs first and persists oversized results to disk), context isolation via subagents with a fixed depth limit and an experimental agent-teams layer (shared file-locked task list + mailbox), progressive-disclosure Skills (SKILL.md open standard), deterministic lifecycle hooks that override model judgment, a CLAUDE.md/auto-memory hierarchy ordered for prompt-cache stability, plan/permission modes enforced by the harness rather than the prompt, OS-level bash sandboxing (Seatbelt/bubblewrap + domain-allowlist proxy), per-prompt file checkpointing with /rewind, background tasks, MCP with deferred tool-schema loading (ToolSearch), and obsessive append-only request shaping so the prompt cache (or, for Resonant, Ollama's local KV/prefix cache) almost never invalidates. The recurring design principle most relevant to Resonant: move reliability out of the model and into the harness — exact contracts, harness-enforced state machines, deterministic hooks, and cache-stable context layout — which is precisely what compensates for open models' weaker instruction-following and flakier tool calling.

**Notable features:**

- **Agent loop with auto-compaction and microcompaction** *(medium)* — The core loop is a single-threaded gather-context / take-action / verify cycle: the model emits tool calls, the harness executes them, results feed back in, repeat until the model stops. Context management is layered. (1) Microcompaction: as the window approaches the limit, Claude Code first clears older tool outputs (the cheapest content to lose) before touching conversation text. (2) Oversized tool results are never fully inlined: outputs beyond a threshold are written to disk (e.g. '~/.claude/projects/<proj>/<session>/tool-results/toolu_xxx.txt') and the model receives a ~2KB preview plus the file path, so it can re-Read only the parts it needs — verified first-hand in this session. (3) Full auto-compaction: when clearing outputs isn't enough, a one-off summarization request is sent that shares the conversation's cached prefix (so it reads cache, not reprocesses), and the history is replaced with a structured summary. What survives is codified: project-root CLAUDE.md is re-read from disk and re-injected; invoked skills are re-attached at up to 5,000 tokens each under a combined 25,000-token budget, most-recent first; nested CLAUDE.md files reload lazily. Thrash protection: if context refills immediately after each summary, it stops auto-compacting after a few attempts and errors instead of looping. Compaction boundaries are logged in the JSONL transcript with preTokens metadata. Users can steer with '/compact focus on X' or a 'Compact Instructions' section in CLAUDE.md. *Relevance:* Resonant's autonomous missions (autonomous_loop.py) run for hours on models with 128-200k effective context, and open models degrade harder than frontier models when context is stuffed. The priority ordering is the key insight: clearing/paging old tool outputs is free (no LLM call, no quality risk) and should come before any summarization — ideal for Ollama where a summarize call costs real wall-clock time on the Mac Studio. Persisting big outputs to files with a preview also plays to weaker models: GLM-5.2 can re-grep the saved file instead of holding 60KB in context. The 'what survives compaction' contract (re-inject CLAUDE.md, re-attach recent skills under a token budget) is directly transplantable into session.py and would fix the classic failure where a mission forgets its standing instructions mid-run.
- **Tool-set design: exact-string Edit, Read-before-Edit enforcement, ripgrep Grep/Glob, no RAG** *(small)* — Tools are layered by abstraction (minusx teardown): low-level Bash/Read/Write, mid-level Edit/Grep/Glob, high-level Agent/WebFetch. Edit is exact-string replacement, not diff-based: old_string must match file bytes exactly (including indentation) and be unique in the file, or the edit fails with a descriptive error; replace_all handles multi-occurrence. The harness enforces a state machine: you cannot Edit or overwrite a file you haven't Read in the current conversation — the call errors regardless of what the model 'thinks'. Read returns cat -n format (line numbers + tab), which grounds the model's line references, and its output prefix must be stripped when quoting into Edit. Grep is a ripgrep wrapper with structured params (glob/type filters, output_mode content|files_with_matches|count, -A/-B/-C context, head_limit defaulting to 250 lines, multiline); Glob returns paths sorted by modification time. Bash tool descriptions actively discourage using find/grep/cat/sed in favor of the dedicated tools. Anthropic explicitly rejected RAG/embeddings for code search — 'LLM search >>> RAG' — letting the model iteratively search like a developer. Edit is the most-used tool, followed by Read and TodoWrite. The model also self-manages a todo list rather than following external orchestration. *Relevance:* This is the highest-leverage, lowest-cost adoption target for tools.py. Exact-string Edit is dramatically more reliable with weaker models than unified diffs: diffs require correct line numbers and hunk math (GLM/DeepSeek frequently botch both), while exact-match either succeeds or fails loudly with a retryable error — no silent corruption. Harness-enforced Read-before-Edit converts an instruction-following problem into a mechanical guarantee, exactly the compensation open models need. Structured Grep with head_limit protects small contexts from 10k-line dumps. The 'no RAG for code search' finding is worth internalizing: Resonant's rag.py may be better reserved for docs/skills retrieval, with iterative ripgrep as the primary code-navigation path.
- **Subagents (Agent/Task tool) with context isolation** *(medium)* — Subagents are markdown files with YAML frontmatter (name + description required; optional tools/disallowedTools allow/deny lists, model with per-invocation override chain, permissionMode, maxTurns, skills to preload full content at startup, mcpServers scoped per-agent, hooks, memory: user|project|local for a persistent agent-memory directory, background: true, isolation: worktree for an isolated git worktree, effort). The parent model writes a delegation prompt; the subagent starts with a FRESH context containing only its own system prompt (not the full Claude Code prompt), the task message, CLAUDE.md hierarchy + git status (except the built-in Explore and Plan agents, which skip both to stay cheap), and any preloaded skills. Only the final text summary returns to the parent, plus a token/duration trailer. Built-ins: Explore (Haiku, read-only, with a quick/medium/very-thorough thoroughness parameter), Plan (read-only, inherits model), general-purpose (all tools). Subagents can nest to a fixed depth of 5; a completed subagent returns an agent ID and can be RESUMED with full prior history via SendMessage; transcripts persist as separate JSONL files unaffected by parent compaction. Subagents auto-compact with the same logic as the main loop. A 'fork' variant inherits the entire parent conversation (and therefore reuses the parent's prompt cache) for side tasks that need full context. *Relevance:* Context isolation is worth more when context is scarce: on local models, letting a research phase burn 40k tokens of file reads in the main window kills the rest of the mission. An Explore-equivalent — read-only tools, no CLAUDE.md, optionally a smaller/faster Ollama model (Haiku-analog) — is cheap to add to specialists.py and maps cleanly onto Resonant's walker/plan-graph phases. The resume-by-ID mechanic (persisted subagent transcripts) is a better retry primitive for Resonant's acceptance-check/retry-budget loop than respawning from scratch: a failed attempt resumes with its own accumulated context instead of repeating discovery. Note the deliberate restraint: fixed depth limit, summaries-only returns, no free-form multi-agent chatter — fragile open models need those guardrails even more.
- **Workflow-style orchestration: agent teams + SDK structured-output workers** *(medium)* — Two orchestration layers sit above subagents. (1) Agent teams (experimental, CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1): the main session becomes a lead that spawns full independent Claude Code sessions as teammates. Coordination is filesystem-based: team config at ~/.claude/teams/{session-derived-name}/config.json (members array with name/agent-id/agent-type), shared task list at ~/.claude/tasks/{team-name}/ with pending/in-progress/completed states, task dependencies that auto-unblock, and FILE LOCKING on task claims to prevent races. Teammates message each other via a SendMessage mailbox; idle teammates notify the lead; messages from other agents are explicitly labeled as agent-origin so a teammate can't fake user consent. Plan-approval workflow: a teammate can be held in read-only plan mode until the lead approves its plan; rejection sends feedback and keeps it planning. Quality gates via hooks: TeammateIdle/TaskCreated/TaskCompleted hooks can exit 2 to block completion and send feedback. Teammates don't inherit lead conversation history — only spawn prompt + project context. (2) Workflow scripts via the Agent SDK: headless claude -p runs with --agents JSON, structured-output tool schemas the worker MUST call exactly once (the pattern running this very research task), and hooks/permission flags — letting an external script compose typed agent stages. *Relevance:* Resonant already has orchestration (orchestrator.py, runner.py, plan_graph.py, walker.py) — the transferable mechanics are the coordination primitives, not the concept: a file-locked shared task store with explicit dependency edges, a mailbox where sender identity is typed (agent vs user) so approvals can't be spoofed, deterministic TaskCompleted gates (run acceptance_check.py as an exit-2 hook rather than trusting the model to self-report success), and lead-approves-plan-before-write for risky mission steps. The SDK structured-output pattern is directly applicable to DeepSeek v4 pro missions: define a JSON-schema 'final answer' tool per stage, validate, and re-prompt on schema failure — far more robust with open models than parsing free text. Anthropic's own caution (teams are experimental, high token cost, no nesting) argues for keeping Resonant's plan-graph as the spine and adding these primitives underneath.
- **Skills (SKILL.md) with progressive disclosure and dynamic context injection** *(small)* — A skill is a directory with SKILL.md (YAML frontmatter + markdown body) plus optional supporting files/scripts; the directory name becomes the /command. Progressive disclosure is the core mechanic: at session start only name + description (+ when_to_use) enter context, capped at 1,536 chars per skill within a listing budget of 1% of the context window (least-used skills' descriptions dropped first when it overflows); the full body loads only on invocation and then persists in context. Invocation control: disable-model-invocation: true keeps even the description out of context until the user types /name (for side-effectful workflows like deploy); user-invocable: false makes it model-only background knowledge. allowed-tools pre-approves tools while the skill is active; model/effort can override per-skill; paths: globs auto-load a skill only when matching files are touched. Dynamic context injection: !`command` lines (and ```! blocks) execute BEFORE the model sees the content, and output replaces the placeholder — so a skill ships with live git diff/PR data pre-inlined. context: fork + agent: Explore runs the skill body as a subagent's task prompt in isolation. $ARGUMENTS/$0..$N/named-arg substitution; ${CLAUDE_SKILL_DIR} for bundled scripts. On compaction, each invoked skill is re-attached (first 5k tokens, 25k combined budget). Skills follow the agentskills.io open standard; live file-watching reloads edits mid-session; the skill-creator plugin runs A/B evals (with-skill vs without) with trigger-rate tuning. *Relevance:* Resonant already has skills.py plus a self-improvement loop that ingests field observations as skills — adopting the SKILL.md format gives free interop with the agentskills.io ecosystem and Claude Code skill libraries. The budgeted description index is critical for local models: as Resonant's self-generated skill library grows, an unbounded skill listing will eat GLM-5.2's context and degrade its (already weaker) skill-selection accuracy; the 1%-budget + drop-least-used + 1,536-char-cap scheme is a concrete fix. disable-model-invocation matters more with open models, which over-trigger tools. Pre-execution !`cmd` injection is a gem for flaky tool-callers: the harness fetches the diff/status deterministically instead of hoping the model calls the right tool first. The eval loop (trigger-rate + output A/B) slots directly into the self-improvement loop as an acceptance check for auto-generated skills.
- **Hooks: deterministic lifecycle interception (PreToolUse etc.)** *(medium)* — Hooks are user-defined handlers at lifecycle events, configured in settings.json (user/project/local/plugin/skill/agent-frontmatter scopes). Events span per-session (SessionStart/SessionEnd), per-turn (UserPromptSubmit, Stop), and per-tool-call (PreToolUse, PostToolUse, PermissionRequest, PermissionDenied), plus async ones (FileChanged, SubagentStart/Stop, PreCompact/PostCompact, TaskCreated/TaskCompleted, TeammateIdle...). Matchers filter by tool name (exact, pipe-list, or regex), and an 'if' field narrows further with permission-rule syntax that is injection-aware: Bash(rm *) also matches rm inside $(...), after &&, or behind env-var prefixes. Five handler types: shell command (JSON on stdin), HTTP POST, MCP tool call, single-turn prompt to a model, and an agent hook that can use read-only tools to investigate before deciding. Contract: exit 0 = parse stdout JSON; exit 2 = BLOCK the action and feed stderr to the model as an error; other = non-blocking warning. JSON outputs give fine control: PreToolUse can return permissionDecision allow/deny/ask/defer, updatedInput to REWRITE tool arguments before execution, and additionalContext injected into the model's context; Stop hooks can block stopping (forcing continued work until tests pass); SessionStart can inject context and env vars. Defaults: 600s timeout, decisions logged. *Relevance:* Hooks are the single best answer to weak instruction-following: CLAUDE.md says 'never force-push' and GLM-5.2 forgets it 30 turns in, but a PreToolUse hook makes it physically impossible — the docs themselves say 'to block an action regardless of what Claude decides, use a PreToolUse hook, not CLAUDE.md'. The exit-2-feeds-stderr-to-model loop doubles as automatic self-correction: block, explain, and the model retries differently — cheap recovery for flaky tool calls. updatedInput enables silent repair (normalize paths, add --no-watchman, inject flags) without burning a model round-trip. A Stop hook that runs Resonant's smoke-test harness and refuses to let a mission end while tests fail is a deterministic upgrade to acceptance_check.py. Implementation is a dispatch layer in session.py around tool execution plus a settings schema — no model changes.
- **CLAUDE.md memory hierarchy + auto memory (MEMORY.md)** *(small)* — Two systems, both loaded every session. (1) CLAUDE.md hierarchy, in load order: managed/enterprise policy file -> ~/.claude/CLAUDE.md (user) -> project CLAUDE.md files discovered by walking UP the directory tree from cwd (root-most first, so closer files are read last) -> CLAUDE.local.md appended after each level's CLAUDE.md. All concatenated, never overriding. Subdirectory CLAUDE.md files load LAZILY, only when the model reads files in that subdirectory. @path imports expand at launch (max depth 4, code-fence-aware); AGENTS.md interop via '@AGENTS.md' import. .claude/rules/*.md splits instructions into topic files, with paths: frontmatter globs that load a rule only when matching files are touched. HTML comments are stripped before injection to save tokens. claudeMdExcludes globs skip irrelevant monorepo files. Guidance: <200 lines per file, delivered as a user message not system prompt. (2) Auto memory: the model maintains ~/.claude/projects/<project>/memory/ with a MEMORY.md index (first 200 lines or 25KB loaded at startup, whichever first) plus topic files (debugging.md etc.) read on demand via normal file tools; the model curates the index itself and writes learnings mid-session. Project-root CLAUDE.md is re-injected after compaction; subagents can have their own memory directories scoped user/project/local. *Relevance:* The load-order discipline doubles as cache discipline: stable instruction layers early, volatile content late, which matters for Ollama prefix-cache reuse (see prompt-caching entry). Lazy loading (subdirectory files, path-scoped rules) is a direct token saver on small local contexts. Auto memory is the pattern most aligned with Resonant's self-improvement loop: a size-capped index + on-demand topic files gives cross-session learning WITHOUT embeddings — arguably a simpler, more debuggable substrate than rag.py for 'what did we learn about this repo'. The 200-line/25KB hard cap is important with open models, which follow long instruction files even more poorly than Claude; Anthropic's own docs concede adherence drops with length and that memory is context, not enforcement (enforcement belongs in hooks).
- **Plan mode and the permission-mode spectrum (incl. auto mode's classifier)** *(medium)* — Six harness-enforced modes: default (prompt on writes/commands), acceptEdits (auto-approve file edits + a whitelist of filesystem commands like mkdir/mv/cp/sed within the working dir), plan (read-only), auto (classifier-supervised autonomy), dontAsk (auto-deny anything not pre-approved — for CI), bypassPermissions (everything, refused under root/sudo). Plan mode is a mode, not a prompt: write tools are gated off by the harness, research is delegated to the read-only Plan subagent, and the model must present a plan via an ExitPlanMode-style approval step; each approve option ('start in auto mode' / 'accept edits' / 'review each edit') switches the session's permission mode, and the user can open the plan in $EDITOR (Ctrl+G) before approving. Crucially, plan-mode instructions are APPENDED as conversation messages so the cached prefix survives. Auto mode: a separate server-side classifier model reviews each non-trivial action before it runs, with a fixed decision order (explicit allow/deny rules -> auto-approve reads and working-dir edits except protected paths -> classifier). The classifier sees user messages, tool CALLS, and CLAUDE.md but NOT tool results (stripping hostile content to resist prompt injection); it honors conversational boundaries ('don't push until I review'); after 3 consecutive or 20 total blocks it falls back to prompting; entering auto mode drops broad allow rules like Bash(*). All modes except bypass protect a fixed path list (.git, .claude, .vscode, shell rc files, lockfile configs...) from auto-approved writes. *Relevance:* Plan-as-enforced-mode fixes a real open-model failure: telling GLM-5.2 'don't edit yet, just plan' in the prompt gets violated; removing Edit/Write from the offered toolset makes violation impossible, and the explicit approve-plan-then-switch-mode step slots exactly into Resonant's grill_me.py spec-refinement flow (interrogate -> plan -> approve -> execute). The permission spectrum maps to Resonant's two personas: interactive GLM-5.2 sessions want default/acceptEdits; DeepSeek autonomous missions want dontAsk (pre-approved allowlist, auto-deny the rest — deterministic, no user) rather than bypass. Auto mode's architecture is replicable locally: a small fast Ollama model as an action classifier that never sees tool results (injection resistance) and falls back to blocking after repeated denials — a strong safety layer when the acting model itself is unreliable. Protected-path lists are a trivial, high-value first step.
- **OS-level Bash sandboxing (Seatbelt / bubblewrap + network proxy)** *(large)* — Instead of approving every command string, the OS enforces a boundary on the running process and all children. macOS uses the built-in Seatbelt framework; Linux/WSL2 use bubblewrap plus socat, with an optional seccomp filter to block Unix domain sockets; native Windows unsupported. Filesystem defaults: write access only to the working directory and a session temp dir ($TMPDIR is redirected); read access to everything except denied paths; settings add allowWrite/denyRead/denyWrite paths and a sandbox.credentials block that denies credential files and unsets secret env vars for sandboxed commands. Network: NO domains pre-allowed; all traffic routes through a proxy outside the sandbox; first use of a new domain prompts once, then it's allowed for the session, with allowedDomains/deniedDomains config (hostname-based, no TLS inspection — domain fronting is an acknowledged limitation). The payoff is 'auto-allow mode': sandboxed commands run with NO permission prompt because the boundary itself is the control; deny rules and rm-targeting-/-or-home still prompt. Escape hatch: when a command fails due to sandbox restrictions, the model may retry with a dangerouslyDisableSandbox parameter, which reroutes through the normal permission prompt; allowUnsandboxedCommands:false disables the hatch. Sandbox denies writes to Claude Code's own settings files so a command can't rewrite its policy. *Relevance:* Resonant's primary host is a Mac Studio — Seatbelt (sandbox-exec profiles) is available with zero install, making this unusually practical. For autonomous DeepSeek missions the trade is compelling: today the choice is prompt-per-command (kills autonomy) or trust-everything (scary with a flaky open model); OS enforcement gives run-anything-freely inside a boundary that holds even when the model runs something unexpected, since it constrains the process rather than judging the command string. The model-assisted escape hatch (fail -> analyze -> retry outside with approval) is a good pattern for handling the long tail of incompatible tools. Caveat: this is the most engineering-heavy item — Seatbelt profile generation plus a domain-allowlist proxy — so start with filesystem-only confinement and add the network proxy later.
- **Checkpointing and /rewind (session-level undo, separate from git)** *(small)* — Before every file edit, the harness snapshots the affected file's current contents; every user prompt creates a checkpoint boundary. Checkpoints persist across resumes and are garbage-collected with sessions after 30 days (cleanupPeriodDays). /rewind (or double-Esc) opens a menu listing each user prompt in the session with five actions: restore code AND conversation to that point; restore conversation only (keep current files); restore code only (keep conversation); 'summarize from here' (replace the selected message and everything after with an AI summary — discard a side quest); 'summarize up to here' (compress early history, keep recent work intact). After a conversation restore, the original prompt is placed back in the input for editing/re-sending. Original messages stay in the JSONL transcript even after summarize. Documented limitations: files changed by bash commands (rm/mv/cp) are NOT tracked — only the harness's own edit tools; external/concurrent edits aren't captured; explicitly positioned as 'local undo' complementing git, not replacing it. Rewind is also cache-friendly: truncating to an earlier turn lands on an already-cached prefix, unlike compaction which builds a new one. *Relevance:* The cheapest large reliability win on this list. Open models mangle files more often than frontier ones, and Resonant's mission retry budget currently has no clean 'undo attempt N' primitive — snapshot-before-edit plus restore-code-to-checkpoint gives every retry a pristine starting state without polluting git history with WIP commits (git_tools.py stays for durable history). Implementation is genuinely small: content-addressed copies keyed by (session, prompt-index, path) written by the Edit/Write tool path in tools.py, plus transcript truncation for conversation rewind. The targeted 'summarize from here' is a smarter mid-mission context reclaim than whole-session compaction — drop the failed debugging detour, keep the mission spec intact. Honor the same caveat: bash-mediated changes are untracked, so say so in the UI.
- **Background tasks (Bash run_in_background, Ctrl+B, background subagents)** *(medium)* — The Bash tool takes a run_in_background parameter: the command runs detached, persists across turns, and re-invokes the agent when it exits — no polling, no blocking. Foreground sleep is blocked in background-capable contexts; a Monitor-style tool waits on conditions instead. Interactively, Ctrl+B backgrounds an already-running task; users can also just ask. Output is retrievable incrementally while running (BashOutput-style reads with optional regex filtering), so the model checks a dev server's logs mid-task. Subagents can run in the background too (background: true frontmatter or Claude's choice): they execute concurrently with the main conversation, and since v2.1.186 their permission prompts surface in the main session naming the requesting subagent (Esc denies that one call without killing the agent); previously they auto-denied. Background task results arrive as messages when complete. CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1 turns it all off; timeouts are per-call (default 120s, max 600s for foreground). *Relevance:* Two distinct wins. (1) Dev-server workflows: Resonant's GUI smoke-test pass needs 'start server, keep it running, read its logs, drive the browser via CDP' — impossible with blocking-only shell tools; run_in_background + incremental log reads is the enabling mechanic, and the notify-on-exit callback fits Resonant's async harness/service.py cleanly. (2) Throughput on ollama.com cloud: backgrounding lets the interactive GLM-5.2 session stay responsive while a long build runs — but note background SUBAGENTS multiply concurrent model calls, so they must route through backends.py's adaptive concurrency governor or they'll trip the 403 rate-limit circuit breaker. The permission-surfacing detail (background agent's prompt bubbles up named, deniable per-call) is the right UX to copy for mission oversight in the web GUI.
- **MCP support with deferred tool loading (ToolSearch)** *(medium)* — Full MCP client: stdio/HTTP/SSE/WS transports, config scopes (.mcp.json checked into the project, user settings, per-subagent frontmatter), OAuth for remote servers, resources (@server:resource mentions) and prompts (as slash commands). The standout mechanic is tool search: by default MCP tool SCHEMAS are not loaded into context — only tool names and server instructions appear at session start (~120 tokens for a whole server), and full JSON schemas are fetched on demand via a ToolSearch tool supporting exact selection ('select:Name1,Name2') or keyword ranking. Only tools actually used ever consume context. ENABLE_TOOL_SEARCH modes: default all-deferred; 'auto' = threshold mode loading schemas upfront only if they fit within 10% of the context window; 'false' = load everything (the pre-2026 behavior). Per-server alwaysLoad:true (or per-tool _meta 'anthropic/alwaysLoad') exempts hot tools from deferral. Server instructions act like skill descriptions, telling the model when to search. Output guard: MCP results over 10,000 tokens trigger a warning/truncation, raise with MAX_MCP_OUTPUT_TOKENS; servers can self-declare limits. Deferral is also cache-armor: a server connecting/disconnecting mid-session appends content instead of mutating the system-prompt prefix, so the KV cache survives. *Relevance:* Adopting MCP-as-client instantly grants Resonant hundreds of integrations (GitHub, Playwright, DBs) it will never build in-house — the highest-value ecosystem play available. But the deferral mechanic is the part that makes MCP VIABLE on open models: 20 servers' full schemas can exceed 50k tokens, which both drowns a 128k local context and measurably degrades GLM-5.2's tool-selection accuracy (more tools = more wrong calls). Anthropic's server-side implementation uses tool_reference blocks, but the pattern is replicable client-side in tools.py: advertise names+descriptions only, expose a resonant ToolSearch tool, and inject selected schemas as appended messages. The 10k-token output clamp is essential too — MCP servers happily return megabytes, and one un-clamped response ends a local-model session. Route deferred-schema injection as appends to preserve Ollama prefix cache.
- **Prompt-caching-first request shaping (append-only context discipline)** *(small)* — Anthropic calls this 'prompt caching is everything' and much of the harness is shaped by it. Requests are ordered into stability layers: system prompt (core instructions + tool definitions + output style, changes only on upgrade or tool-set change) -> project context (CLAUDE.md, auto memory, unscoped rules; changes on /clear//compact) -> conversation (changes every turn). Cache matching is exact-prefix: a change anywhere recomputes everything after it, so the harness is aggressively APPEND-ONLY — plan mode, skill invocations, permission-mode switches, file-change notices, and deferred MCP tool schemas all arrive as appended messages, never as mutations of earlier content; editing a previously-read file appends a <system-reminder> rather than rewriting the old read. The cache is keyed by model AND effort level (switching either = full re-read, with a confirmation dialog for effort). Documented invalidators: model switch, MCP server connect/disconnect when schemas are in the prefix, denying an entire tool (removes its definition from the system prompt), upgrades, compaction (by design). Cache-preserving: file edits, CLAUDE.md edits mid-session (deliberately NOT applied until restart), skill invocation, rewind (lands on a cached prefix). Compaction's summarizer call shares the conversation's prefix so it reads cache. Forks inherit the parent cache; fresh subagents build their own. Cache reads bill ~10% of input; TTL 5min/1h. *Relevance:* Resonant has no vendor caching bill, but the EXACT same physics governs Ollama's local prefix/KV cache on the Mac Studio: identical token prefix = KV reuse = skip prefill; any earlier-token change = re-prefill the whole tail. On a 100k-token mission context, re-prefill is tens of seconds per turn of pure latency — so append-only discipline is a first-order UX/throughput feature for Resonant, not billing hygiene. Concrete rules to port into session.py: fix system prompt + tool schemas at session start and never mutate them mid-session (defer schema changes to appended messages); keep volatile data (git status, timestamps) at the END of the prompt or in appended reminders; defer CLAUDE.md-equivalent edits to the next session; inject skills/plan instructions as messages; prefer rewind-to-prefix over rebuild. Also verify Ollama keep_alive and num_ctx settings hold the KV cache between turns, and be aware ollama.com cloud may not offer cross-request prefix reuse at all — one more reason the local host is the mission workhorse.

### opencode-crush

OpenCode (now under the anomalyco org, ~181k stars, v1.17.13 released 2026-07-01) is a TypeScript monorepo built around a strict client/server split: a headless HTTP server (~80 REST endpoints + SSE event stream, OpenAPI 3.1 spec at /doc that generates its SDK) that the TUI, desktop app, IDE extensions, and web console all consume as peers. Its provider layer rides on Vercel's AI SDK plus the models.dev catalog (75+ providers); local/Ollama models are configured as @ai-sdk/openai-compatible providers with explicit per-model context/output limits. Standout mechanics: a 9-strategy fuzzy replacer pipeline for the edit tool (exact → line-trimmed → block-anchor Levenshtein → whitespace-normalized → indentation-flexible → escape-normalized → trimmed-boundary → context-aware → multi-occurrence) that rescues malformed model edits; auto-spawned LSP servers (30+ built-ins keyed by file extension) whose diagnostics are appended to every edit result; a primary-agent/subagent system (build/plan + general/explore/scout) with per-agent model/temperature/permissions defined in markdown files; glob-based allow/ask/deny permissions; a JS plugin system with tool.execute.before/after and compaction hooks; AGENTS.md rules with CLAUDE.md fallback and an instructions glob array; compaction config (auto summarize when context fills, prune old tool outputs, reserved token buffer) plus a small_model for lightweight tasks; git-snapshot-based /undo//redo; opt-in session sharing to public URLs; and Claude-compatible SKILL.md agent skills with progressive disclosure. Crush (Charm's Go agent) converged on a similar shape: a shared-backend workspace model where clients with the same cwd join one workspace sharing sessions/LSP/MCP/permission-queue state over SSE (workspace dies when the last stream disconnects); manually-configured LSP servers feeding agent context; and multi-model support via the community Catwalk registry with mid-session model switching that preserves context and an "ollama" provider type that auto-discovers local models when the models list is left empty. Below, 12 features with mechanics, Resonant-specific relevance (GLM-5.2/DeepSeek v4 pro over Ollama: weaker instruction-following, flaky tool calls, local KV cache instead of vendor prompt-cache billing), and adoption difficulty.

**Notable features:**

- **OpenCode client/server architecture (headless server + SSE event bus + OpenAPI-generated SDK)** *(large)* — Every OpenCode launch starts a headless HTTP server on a random port; the TUI is just a client of it. `opencode serve` runs the server standalone. The server owns everything stateful — sessions, agent loop, provider calls, file ops, LSP/MCP/formatter lifecycles — and exposes ~80 REST endpoints grouped by domain (sessions: create/list/fork/delete; messages: send prompt, run shell; files: search/read/VCS status; config, providers/OAuth, commands, agents, tools+schemas). Real-time state fans out to all clients via server-sent events at /event and /global/event (first event is server.connected, then state-change broadcasts). The full API contract is published as an OpenAPI 3.1 spec at /doc, from which the official JS SDK is generated; auth is HTTP Basic via OPENCODE_SERVER_PASSWORD, with --cors flags for browser clients. TUI, desktop app, IDE extension, and web console are all peers on the same server, so a web UI can even remote-drive the TUI via dedicated endpoints. *Relevance:* Resonant already has both a TUI and a local web GUI plus a harness service layer (resonant_client/harness/service.py, orchestrator.py); the OpenCode lesson is to make ONE headless server the single owner of session state and have every frontend (TUI, GUI, autonomous_loop missions, smoke-test harness) consume the same REST+SSE surface. That gives you: attach the GUI to a running autonomous mission mid-flight, script missions via the API, and publish an OpenAPI spec so external tools can drive Resonant. It also cleanly decouples the Ollama backend (with its concurrency governor) behind one process instead of per-frontend duplication.
- **Multi-strategy fuzzy edit replacer pipeline (OpenCode's edit tool)** *(small)* — The edit tool takes filePath/oldString/newString/replaceAll and tries NINE matching strategies in order until one finds oldString (source: packages/opencode/src/tool/edit.ts): (1) SimpleReplacer — exact match; (2) LineTrimmedReplacer — compares lines ignoring leading/trailing whitespace; (3) BlockAnchorReplacer — anchors on the block's first and last lines, accepts if middle lines pass a Levenshtein similarity threshold (~0.65); (4) WhitespaceNormalizedReplacer — collapses whitespace runs to single spaces; (5) IndentationFlexibleReplacer — strips the common base indentation before comparing; (6) EscapeNormalizedReplacer — unescapes \n, \t, \\ that models emit as literals; (7) TrimmedBoundaryReplacer — trims the whole search string's boundaries; (8) ContextAwareReplacer — first/last-line anchors with >=50% middle-line similarity; (9) MultiOccurrenceReplacer — enumerates all exact matches for replaceAll. Guardrails: replaceAll=false requires a unique match (else error asking for more context); a 'disproportionate match' check refuses if the matched span exceeds oldString by 3+ lines or 2x length (4x for single-line trimmed), preventing fuzzy matchers from eating the wrong block. Errors are actionable ('Provide more surrounding context...'). On success it emits a diff patch, add/delete stats, and file events. *Relevance:* This is probably the single highest-ROI adoption. GLM-5.2 and DeepSeek v4 pro routinely fail exact-match edits: they normalize whitespace, re-indent, emit literal \n instead of newlines, or drop trailing spaces. With a naive exact-match edit tool each failure costs a full model round-trip on local hardware (slow) or a cloud call (rate-limited — your governor territory), and repeated failures derail weaker models entirely. A deterministic Python port of this pipeline in resonant_client/engine/tools.py converts a large fraction of failed edits into successes with zero extra tokens, while the disproportionate-match guard and unique-match requirement keep it from silently corrupting files. The whole thing is pure string algorithms — no dependencies beyond a Levenshtein function.
- **LSP integration with diagnostics-as-feedback (OpenCode auto-spawn; Crush manual config)** *(large)* — OpenCode ships 30+ built-in LSP server definitions keyed by file extension. When the agent touches a matching file it checks the server binary exists (e.g. rust-analyzer on PATH, pyright in the project), spawns it if not running, and keeps it warm. The payoff is wired into the edit loop: after every successful edit the tool calls lsp.touchFile(), pulls lsp.diagnostics(), and appends any errors for the modified file directly to the edit tool's result — the model sees 'edit applied, but line 42: type error X' in the same turn. There's also an experimental `lsp` tool exposing go-to-definition and find-references. Config: `"lsp": true` for all built-ins, per-server {command, extensions, env, initialization, disabled}. Crush does the same idea with manual config only (e.g. {"lsp": {"go": {"command": "gopls"}}}), described as giving the model context 'just like you' get from an IDE; LSP state is shared across all clients in a workspace. *Relevance:* Deterministic compiler-grade feedback is the cheapest way to compensate for a weaker model: GLM-5.2 doesn't need to be smart enough to spot its own type errors if pyright/gopls reports them in the tool result immediately. This shortens the mistake→discovery loop from 'later, when the smoke test fails' to 'same turn', which matters double on Ollama where every extra round-trip is slow and cloud calls burn rate-limit budget. Resonant currently leans on the smoke-test harness and acceptance_check.py for verification — LSP diagnostics slot in as a much earlier, cheaper tier. A pragmatic start: spawn pyright-langserver/typescript-language-server via pylsp-style JSON-RPC over stdio in engine/, and append diagnostics for the edited file to edit-tool results.
- **Primary agents + subagents with per-agent model/permissions/temperature (OpenCode agents system, ex-'modes')** *(medium)* — Two agent classes: PRIMARY agents you Tab-cycle between in the TUI (built-ins: 'build' with all tools, 'plan' restricted to read-only analysis), and SUBAGENTS that primaries auto-invoke via a task tool or the user @-mentions (built-ins: 'general' full-access executor, 'explore' read-only navigator, 'scout' read-only dependency/docs researcher). Subagent runs create child sessions navigable from the parent (keybinds for child-first/cycle/parent). Agents are defined as markdown files with frontmatter in .opencode/agents/ (project) or ~/.config/opencode/agents/ (global) — filename = agent id — or in opencode.json. Per-agent knobs: mode (primary/subagent/all), model override, prompt (supports {file:./path}), temperature, steps (max agentic iterations before forcing a text-only response), permission overrides, description (required — it's what the primary uses to pick subagents), hidden. Task permissions use glob patterns to control which subagents a primary may spawn. *Relevance:* Resonant's orchestration/specialists.py is already a subagent system; the adoptable deltas are (a) per-agent MODEL routing — run 'explore/scout'-style read-only recon on a small fast local model on the Mac Studio and reserve glm-5.2:cloud / DeepSeek v4 pro turns for build work, directly relieving cloud 403 pressure your governor exists to manage; (b) a first-class read-only 'plan' mode with tool-level enforcement (deny edit/write/bash) rather than prompt-level 'please don't edit' — weak instruction-followers WILL edit if the tool is available; (c) markdown-file agent definitions so users can add specialists without touching Python; (d) 'steps' caps per agent, which pairs naturally with your existing retry budgets.
- **Glob-pattern allow/ask/deny permission system (both tools)** *(medium)* — OpenCode gates every tool with three states — allow (run silently), ask (prompt user), deny (blocked) — configurable globally, per agent, and per pattern. Bash gets command-level granularity: {"git push": "ask", "grep *": "allow", "*": "deny"} auto-permits greps, confirms pushes, blocks everything else. The same pattern grammar gates skills ({"internal-*": "deny"}) and which subagents the task tool may spawn. The write tool is deliberately governed by the edit permission (one knob for 'can modify files'). Crush's version: default is prompt-for-everything, with permissions.allowed_tools (["view","ls","grep","mcp_context7_get-library-doc"]) as an allowlist, --yolo to bypass, options.disabled_tools to hide tools from the model entirely. *Relevance:* With flaky tool-calling models, hiding a tool (Crush's disabled_tools) is more reliable than instructing the model not to use it — the schema never enters context so it can't be miscalled, and it saves system-prompt tokens on every request (which also improves Ollama KV-cache stability, since a smaller stable prefix reuses cache better). The glob-based bash gating matters for autonomous missions: DeepSeek v4 pro running unattended in autonomous_loop.py should have 'git push', 'rm -rf', package publishes at deny/ask while read-only shell is allow — a policy file, not prompt engineering. Resonant's per-mission trust level could map directly onto an OpenCode-style permission dict.
- **Provider abstraction: AI SDK + models.dev catalog, explicit per-model limits, Ollama specifics (OpenCode)** *(small)* — OpenCode delegates wire protocols to Vercel's AI SDK: each provider entry names an npm package ("npm": "@ai-sdk/openai-compatible" for /v1/chat/completions endpoints, @ai-sdk/openai for /v1/responses, vendor packages otherwise) which is installed on demand via Bun. The models.dev open catalog supplies metadata (context windows, costs, capabilities) for 75+ providers so most models need zero manual config. Local models are just another provider: {"ollama": {"npm": "@ai-sdk/openai-compatible", "options": {"baseURL": "http://localhost:11434/v1"}, "models": {"llama2": {...}}}} — with each model declaring limit.context and limit.output, which OpenCode uses to track remaining context during a session. Docs explicitly warn that Ollama tool-calling quality depends on num_ctx being large enough. Model selection precedence: --model flag > config model > last-used > internal default; a 'variants' system predefines option bundles (thinking budgets, reasoning effort) per model, cycled with ctrl+t. OpenCode Zen is the same abstraction productized: a gateway of ~50 models where each model+hosting-provider combo was benchmarked as a coding agent, because 'only a few models work well as coding agents' and aggregators like OpenRouter don't guarantee serving quality. *Relevance:* Resonant is single-backend (Ollama) so the multi-provider machinery itself is not the lesson — three specifics are: (1) explicit per-model context/output limits as config-driven metadata that the session loop consults for compaction decisions (Ollama's API doesn't reliably surface effective context, and num_ctx defaults silently truncate — the exact failure mode OpenCode's docs call out for tool calling); (2) treating 'last-used model' and variant bundles (e.g. glm-5.2:cloud with/without thinking) as first-class selection state; (3) Zen's core insight — model+serving-config combos must be benchmarked as agents, not assumed — is precisely why Resonant's smoke-test harness should pin known-good num_ctx/temperature per model tag and treat those as tested artifacts.
- **Context compaction: auto-summarize + tool-output pruning + reserved buffer + small_model (OpenCode)** *(medium)* — opencode.json exposes a compaction object: auto (default true — when the session nears the model's context limit, the session is summarized into a continuation and the loop restarts on the summary), prune (default false — delete OLD TOOL OUTPUTS from history to reclaim tokens without full summarization), and reserved (a token buffer held back so compaction triggers before hard overflow). Manual /compact (alias /summarize) forces it. A separate small_model config routes lightweight work — session title generation and similar — to a cheaper model instead of the flagship. Plugins can intercept compaction via the experimental.session.compacting hook to inject context into the continuation summary or replace the compaction prompt entirely (explicitly pitched for multi-agent swarm sessions); session.compacted events fire afterward. Per-model limit.context metadata is what makes 'context is full' computable. *Relevance:* Long autonomous missions (autonomous_loop.py) are exactly where context overflows, and open models degrade sharply near their limit — GLM/DeepSeek start ignoring instructions well before hard truncation. Two Ollama-specific wrinkles make OpenCode's split design (prune vs summarize) valuable: (a) tool outputs (grep dumps, test logs) dominate agent context and pruning them is FREE — no model call — whereas summarization costs a full-context generation; (b) on local Ollama, any history rewrite invalidates the KV-cache prefix, forcing an expensive re-prefill on the Mac Studio — so you want compaction to be infrequent-but-decisive (one big summarize) rather than continuous trimming, and 'reserved' headroom controls that cadence. small_model maps perfectly to your split: route titles/summaries/acceptance-check phrasing to a small local model on 10.0.0.133, keep glm-5.2:cloud turns for real work — also relieving cloud rate limits. The compaction hook idea slots into your self-improvement loop: inject active skill/mission state into every continuation summary so it survives compaction.
- **AGENTS.md rules conventions + instructions glob array (OpenCode; Crush equivalent)** *(small)* — OpenCode reads project AGENTS.md (repo root, applies to that tree) and global ~/.config/opencode/AGENTS.md, with CLAUDE.md / ~/.claude/CLAUDE.md as migration fallbacks (AGENTS.md wins if both exist); contents are injected into the LLM context. /init scans the repo and generates or incrementally improves AGENTS.md (build commands, architecture, conventions), meant to be committed. Beyond that, opencode.json's instructions field takes an array of paths, glob patterns, and even remote URLs (5s fetch timeout): {"instructions": ["CONTRIBUTING.md", "docs/guidelines.md", ".cursor/rules/*.md"]} — letting teams reuse existing standards files without duplication. File references inside AGENTS.md (@rules/foo.md) are NOT auto-parsed; the documented pattern is teaching the model to Read them on demand. Crush mirrors this: auto-includes ~/.config/crush/CRUSH.md and ~/.config/AGENTS.md, customizable via global_context_paths, and its init writes AGENTS.md by default (initialize_as to rename). *Relevance:* AGENTS.md has become the cross-tool standard (OpenCode, Crush, Codex, Copilot all read it) — Resonant should read AGENTS.md with CLAUDE.md fallback so any repo already onboarded for other agents works day one, and so Resonant-generated projects are portable. For weaker models the /init pattern matters more than for frontier ones: GLM-5.2 benefits disproportionately from having build/test commands and conventions pre-stated rather than rediscovering them each session (fewer exploratory tool calls = fewer chances to flake, and a stable system-prefix helps Ollama KV-cache reuse across sessions). The instructions-glob mechanism is a natural feed for Resonant's skills system: field-observation skills that should ALWAYS apply could be surfaced as instruction files rather than on-demand skills.
- **Git-snapshot undo/redo of agent file changes (OpenCode snapshot system)** *(medium)* — OpenCode tracks every agent-made file change via Git-based snapshots (the project must be a git repo; a snapshot config option disables tracking with the documented warning that 'changes made by the agent cannot be rolled back'). /undo reverts both the conversation to a previous message state AND the associated file modifications; /redo re-applies only after an /undo. This makes each agent turn effectively transactional: bad turn → one command restores files+history to the pre-turn state, without touching the user's own uncommitted work (snapshots are kept separately from the user's index). *Relevance:* Weak-model harnesses need cheap rollback more than frontier ones — GLM-5.2 will sometimes confidently trash a file, and DeepSeek missions run unattended for hours. Resonant already has git_tools.py and retry budgets in autonomous missions; wiring a snapshot-per-turn (e.g. git stash create / temporary objects in the object DB, or a hidden worktree index) gives (a) /undo in interactive sessions and (b) automatic revert-to-last-good-snapshot when an acceptance check fails, instead of asking the model to repair its own damage — which weak models are notably bad at. This composes with your existing acceptance_check.py: check fails → snapshot rollback → retry with the failure appended, a much cleaner retry semantics than retrying atop broken state.
- **Plugin/hook system with tool interception (OpenCode)** *(medium)* — Plugins are JS/TS modules in .opencode/plugins/ or ~/.config/opencode/plugins/, or npm packages listed in config (auto-installed via Bun, cached). A plugin exports an async function receiving {project, client (the SDK pointed at the local server), $ (shell), directory, worktree} and returns a map of hooks. Hook surface: tool.execute.before/after (inspect/mutate/veto any tool call — e.g. throw to block reads of .env), chat/message and message.part events, permission.asked/replied, session.created/compacted/idle/deleted, file.edited, lsp.client.diagnostics, shell.env (inject env vars into every shell), TUI hooks (toast, prompt append), custom tool registration via a tool() helper with schema'd args, and the experimental compaction-prompt hook. Because plugins get the SDK client, they can drive the whole server (spawn sessions, send prompts) — enabling meta-automation. *Relevance:* Resonant's extensibility today is the skills system (prompt-space) — a hook system is the code-space complement, and tool.execute.before/after is the piece worth stealing first. Concrete uses in your codebase: enforce the .env/read guard and Ollama-host allowlists as hooks instead of hardcoding in tools.py; log every tool call+result as structured field observations feeding the self-improvement loop (your skills-ingest pipeline gets a clean tap point); auto-retry/normalize malformed tool args from flaky models in one interception layer rather than per-tool. Python entry-points or a simple 'load modules from .resonant/plugins/' with before/after callables gets 80% of the value without npm-style packaging.
- **Crush's cwd-keyed shared workspace model (multi-client sessions over one backend)** *(medium)* — When Crush runs against a shared backend (crush serve), clients are grouped into workspaces keyed by resolved working directory: two clients with the same --cwd join the same workspace and share the session list, message history, permission queue, LSP state, and MCP state. Joining is implicit — point a second client at the directory and it attaches. Lifecycle is tied to event streams: a workspace lives while at least one client holds an SSE stream open, and is torn down when the last disconnects. Sessions expose IsBusy (an agent turn in flight) and AttachedClients (how many clients are viewing) in the picker; process-wide flags like --yolo are first-wins (later clients can't escalate a running workspace). Session history persists per session with independent context, and the session picker switches/joins. *Relevance:* This is the concrete blueprint for Resonant's TUI+GUI coexistence problem: key shared state by project directory, let the web GUI attach to a mission the TUI started (or watch an autonomous mission from a phone browser), and share the PERMISSION QUEUE — so an unattended DeepSeek mission that hits an 'ask' permission can be approved from whichever client is open. The first-wins flag rule and IsBusy/AttachedClients signals are small, well-thought-out details that prevent two clients fighting over one session. The lifecycle rule (teardown on last disconnect) needs modification for Resonant since autonomous missions must outlive clients — mission-owned workspaces that persist regardless.
- **Crush multi-model: Catwalk registry, mid-session model switching, Ollama auto-discovery** *(small)* — Crush's model catalog comes from Catwalk (github.com/charmbracelet/catwalk), a community-maintained open registry of Crush-compatible providers/models with metadata (cost, context window); Crush auto-syncs from it at startup (disable via disable_provider_auto_update / CRUSH_DISABLE_PROVIDER_AUTO_UPDATE; manual `crush update-providers` can pull from Catwalk, a custom URL, or a local file, or reset to embedded data). Custom providers use type openai-compat with base_url/api_key/models declaring id, name, cost, context_window. Key local-model touch: a provider of type "ollama" (e.g. base_url http://localhost:11434/v1/) with an EMPTY models list auto-discovers whatever models the Ollama daemon has pulled. Headline UX: switch LLMs mid-session while preserving full conversation context — the session isn't bound to a model. Shell-style env expansion ($VAR, ${VAR:-default}) works throughout config. *Relevance:* Two directly-liftable mechanics: (1) auto-discovery from the Ollama daemon — Resonant should populate its model picker from GET /api/tags on 10.0.0.133 (plus the cloud tags) instead of hand-maintaining lists, overlaying a small local metadata file (context window, tool-call reliability rating, role hints) in the spirit of Catwalk; a versioned 'known-good models' registry file is also a clean distribution channel for your smoke-test-validated model configs. (2) mid-session model switching with preserved context is cheap to implement (history is provider-agnostic messages) and high-value in your dual-flagship setup: start on glm-5.2:cloud, hit sustained 403s (circuit breaker open), fail over the SAME session to a local model or DeepSeek without losing state — turning the governor's failure mode into a graceful degradation. Caveat: a model switch on local Ollama forfeits the KV cache and swaps which model is resident on the Mac Studio, so the UI should signal that cost.

### codex-gemini

Codex CLI is now a pure-Rust, zero-dependency binary whose defining design choice is separating two orthogonal axes: an OS-enforced sandbox (macOS Seatbelt, Linux/WSL2 bubblewrap over Landlock/seccomp, a native Windows sandbox) with three modes (read-only / workspace-write / danger-full-access), and an approval policy (untrusted / on-request / never, plus a granular per-category table) that governs when the agent may escalate outside the sandbox. Edits go through apply_patch, a context-anchored (no line numbers) file-oriented diff grammar parsed by a dedicated Rust crate with fuzzy context seeking; instructions for it are injected into the prompt for models that weren't trained on it. Layered AGENTS.md files (global -> repo root -> cwd, 32 KiB cap, override files, fallback filenames) supply persistent instructions, and `codex cloud` / `codex exec` split work between local headless runs and parallel cloud containers. Gemini CLI (TypeScript, cli+core packages) runs a reason-and-act loop hardened for imperfect models: automatic loop detection, a next-speaker check, and automatic history compression at a configurable fraction of the context window (model.compressionThreshold, default 0.5). It checkpoints project state into a shadow git repo before every file-mutating tool call (/restore rewinds files + conversation + re-proposes the tool call), layers GEMINI.md context files with @file imports and a configurable filename (AGENTS.md works), and ships an experimental auto-memory system that extracts memory patches and SKILL.md files from past sessions into a review inbox — a close cousin of Resonant's self-improvement loop. Its free-tier strategy leans on a 1M-token context (60 req/min, 1000 req/day via Google login), implicit token caching where the API supports it, and a ModelAvailabilityService that falls back across models on quota/server errors — optionally using a tiny local Gemma classifier (LiteRT-LM) to make routing decisions locally. The features most worth stealing for Resonant: Codex's sandbox/approval decoupling and apply_patch grammar (with prompt-injected instructions for open models), AGENTS.md layering; Gemini's shadow-git checkpointing, loop detection + compression thresholds tuned for local KV cache, model fallback chains (maps directly onto the Ollama cloud 403 governor), and the auto-memory review inbox to formalize Resonant's skills ingestion.

**Notable features:**

- **Codex: OS-level sandboxing (Seatbelt / Landlock->bubblewrap / Windows sandbox) with three sandbox modes** *(large)* — Codex wraps every spawned process — not just its own file ops — in a platform-native sandbox: macOS uses the built-in Seatbelt framework (sandbox-exec profiles), Linux and WSL2 use bubblewrap (which builds on Landlock/seccomp; the original Rust implementation bound Landlock/seccomp directly), and Windows has both a native PowerShell sandbox and the WSL2 path (the repo now has a whole app-server windows_sandbox setup flow). Three modes set the boundary via `sandbox_mode` in ~/.codex/config.toml or CLI flags: `read-only` (inspect only; any write/exec needs approval), `workspace-write` (default working mode: writes allowed inside the workspace plus `sandbox_workspace_write.writable_roots`; network access is OFF unless `sandbox_workspace_write.network_access = true`; `exclude_slash_tmp` / `exclude_tmpdir_env_var` trim default writable temp dirs), and `danger-full-access` (no boundaries). Because git/npm/pytest inherit the sandbox, a blocked write or network call surfaces as a sandbox denial that the agent can convert into an approval request rather than silently failing. *Relevance:* Resonant runs shell/git/browser tools driven by GLM-5.2 and DeepSeek v4 pro, which follow instructions less reliably than frontier closed models — prompt-level 'please don't touch files outside the repo' is much weaker insurance for them. An OS-enforced boundary makes autonomous missions (autonomous_loop.py) safe to leave unattended: a hallucinated `rm -rf ~` or a curl to a random host becomes a mechanical denial instead of damage. The 'sandbox applies to spawned commands' principle matters most: Resonant's tools.py shell tool is the escape hatch today. On the Mac Studio side Seatbelt is available natively; on Windows clients bubblewrap-in-WSL2 is the pragmatic route.
- **Codex: approval policy decoupled from the sandbox, with escalation and granular per-category approvals** *(medium)* — `approval_policy` is a separate axis from `sandbox_mode`: `untrusted` (pause before any non-trusted command; a built-in list of known-safe commands runs without prompting), `on-request` (agent works autonomously inside the sandbox and only asks when it wants to exceed it — e.g. network access or writing outside writable roots; blocked sandbox operations trigger an approval request to re-run the command unsandboxed), `never` (headless/CI: auto-approve nothing, the agent must work within the sandbox), and the deprecated `on-failure`. Mid-2026 config adds a granular form: `approval_policy = { granular = { sandbox_approval = bool, rules = bool, mcp_elicitations = bool, request_permissions = bool, skill_approval = bool } }`, plus `approvals_reviewer = "user" | "auto_review"` where an auto-reviewer model judges escalations. Command-prefix rules (allow/prompt/forbid) let you whitelist e.g. `npm test` without widening the sandbox; there's also a Starlark-based execpolicy crate for programmatic command classification. *Relevance:* Resonant currently conflates 'what the model may do' with 'what the user must confirm'. Separating them gives a clean matrix: interactive GLM-5.2 sessions run workspace-write + on-request (low friction, asks only at the boundary), autonomous DeepSeek missions run workspace-write + never (they can never block waiting for a human — today a mission that wants approval just stalls or YOLOs). The escalation pattern ('command failed due to sandbox; ask to retry unsandboxed') is also the right UX for flaky tool-calling: the failure is machine-readable, so the harness — not the model — decides to prompt. The `auto_review` reviewer idea maps directly onto Resonant's acceptance_check.py machinery: a cheap second model pass judging risky commands.
- **Codex: apply_patch edit format (context-anchored file-oriented diff, no line numbers)** *(medium)* — All edits go through one grammar: `*** Begin Patch` ... `*** End Patch` envelope containing file ops `*** Add File: path` (every body line prefixed `+`), `*** Delete File: path`, `*** Update File: path` (optionally `*** Move to: newpath` for renames), followed by hunks introduced by `@@` with optional header. Hunks carry 3 lines of context above/below each change (space=context, -=old, +=new); there are NO line numbers — location is found by matching context text, and ambiguity is resolved by stacking `@@ class Foo` / `@@ def method():` scope markers. Formal grammar: `Patch := Begin { FileOp } End; Hunk := "@@" [header] NEWLINE { HunkLine } ["*** End of File"]`. It executes as a shell command `["apply_patch", "<patch>"]` — the Codex binary self-invokes via a `--codex-run-as-apply-patch` argv flag — and the Rust crate (codex-rs/apply-patch) has a parser plus `seek_sequence` fuzzy context matching, so slightly-off context still lands. Failures return a parse/match error the model can retry against. Crucially, for models not trained on the format, Codex prepends the full instructions (codex-rs/prompts/templates/apply_patch_tool_instructions.md, and prompt_with_apply_patch_instructions.md as a full base prompt variant). The prompt also explicitly says 'do not re-read files after apply_patch — the call fails if it didn't work', saving tokens. *Relevance:* This is arguably the highest-leverage steal. Open models over Ollama are the exact case the instruction-injection path was built for: you get a single, deterministic, parseable edit channel instead of hoping GLM-5.2 emits valid JSON tool args for search/replace. Context-anchoring (no line numbers) tolerates the stale-line-number errors open models make constantly, and fuzzy seek_sequence absorbs whitespace drift. Because it's invoked as plain text inside a shell command rather than a structured tool-call argument, it also sidesteps flaky native tool-calling: DeepSeek can stream the patch as ordinary text and Resonant's harness can intercept it. The 'don't re-read after patch' rule is free token savings on a local KV cache. Port: a Python parser + seek matcher (~500 lines), inject the instructions template into tools.py prompts, benchmark GLM-5.2 vs its current edit format on the smoke-test harness.
- **Codex: layered AGENTS.md instruction files with overrides, fallbacks, and a hard byte budget** *(small)* — Codex builds an instruction chain: (1) global `~/.codex/AGENTS.override.md` then `~/.codex/AGENTS.md` (CODEX_HOME-relative); (2) from the repo root it walks down toward cwd, at each directory taking at most one file — `AGENTS.override.md`, else `AGENTS.md`, else names from `project_doc_fallback_filenames` (e.g. ["TEAM_GUIDE.md", ".agents.md"]); (3) files are concatenated root->cwd with blank-line separators, so closer files appear later in the prompt and win. `project_root_markers` config identifies the repo root. Total combined size is truncated at `project_doc_max_bytes` (default 32 KiB). The merged text is read once per session and prepended to the model prompt. AGENTS.md has become a cross-tool convention (agents.md) — Gemini CLI can read the same file via its configurable context filename. *Relevance:* Resonant has no per-project persistent-instruction mechanism visible in its architecture (skills are behavioral, not project conventions). For weaker-instruction-following open models, a short, always-present, deterministic instruction block beats hoping the model remembers norms from earlier in a long session — and because it's stable text at the top of the prompt, it's a perfect prefix for Ollama's local KV cache (stable prefixes = cache hits = faster time-to-first-token on the Mac Studio, the local analogue of vendor prompt-cache billing). The 32 KiB cap is an important discipline: open models degrade with bloated system prompts, so enforce a budget and truncate loudly. Adopting the exact AGENTS.md filename buys interop with users' existing files for free.
- **Codex: Rust rewrite — zero-dependency binary, native sandbox bindings, and a wire-protocol core (app-server)** *(large)* — In mid-2025 OpenAI replaced the TypeScript CLI with Rust (repo is now ~96% Rust) for four stated reasons (discussion #1174): zero-dependency install (no Node 22 requirement), native security bindings (Landlock/seccomp on Linux, sandbox-exec/Seatbelt on macOS, called directly from Rust), performance (no GC, lower memory), and an extensible wire protocol. The architecture that emerged: a protocol crate defines typed messages (SandboxPolicy, ApplyPatchApprovalParams, ExecPolicyAmendment... with generated JSON/TypeScript schemas), and an `app-server` daemon exposes the agent core over that protocol so the TUI, IDE extensions, and cloud all drive the same engine. Per-model behavior is externalized into instruction templates (gpt-5.2-codex_prompt.md, personality variants, collaboration-mode templates like plan/pair_programming/execute) selected per model, with `model_instructions_file` as a user override. *Relevance:* Not a call to rewrite Resonant in Rust — the transferable lessons are architectural. (1) The core-behind-a-typed-protocol pattern: Resonant already has harness/service.py plus TUI and web GUI; formalizing one schema'd protocol between engine and frontends (like app-server's generated schemas) prevents the GUI/TUI drift that plagued its recent UI passes. (2) Per-model instruction templates are directly relevant: Codex ships a different base prompt per model family — Resonant should ship distinct, tuned prompt templates for GLM-5.2 (interactive) vs DeepSeek v4 pro (missions) rather than one shared system prompt, because open-model families have very different tool-calling quirks. (3) The sandbox rationale confirms sandboxing must live in the harness, not the prompt.
- **Codex: cloud/local execution split (codex cloud, codex exec, GitHub @codex)** *(medium)* — Local headless mode: `codex exec` runs non-interactively (approval_policy=never, JSON event output) for CI/scripting. Cloud mode: tasks are delegated to OpenAI-hosted containers where Codex reads/edits/runs code in parallel isolated environments; you pre-configure each environment (repo, setup steps, dependency install, and an explicit internet-access policy), and results come back as reviewable diffs/PRs. The `codex cloud` CLI command delegates a task and can resume/apply a cloud task locally; `@codex` mentions on GitHub issues/PRs trigger runs whose output is a PR. The same agent core (via the wire protocol) powers local and cloud, so behavior is consistent. *Relevance:* Resonant already has the two halves — interactive sessions and autonomous missions (autonomous_loop.py, autonomous_factory.py) — but Codex's framing suggests the missing glue: a first-class 'delegate this from the interactive session' verb that snapshots context (branch, plan graph node, acceptance checks) into a mission environment and later offers 'apply mission result to my working tree'. For Resonant, 'cloud' is really 'the Mac Studio': DeepSeek missions can run against a dedicated worktree per mission (isolation-by-worktree instead of isolation-by-container), with an explicit network policy per mission. Parallel mission environments also spread load in a way the adaptive concurrency governor in backends.py can schedule around ollama.com 403 rate limits.
- **Gemini CLI: hardened ReAct loop — loop detection, next-speaker check, automatic history compression** *(medium)* — The core package (packages/core) owns the reason-and-act loop: build prompt (history + tool definitions + GEMINI.md context) -> model responds with text and/or tool requests -> destructive tools (write_file, replace, run_shell_command) require user confirmation -> results are fed back -> repeat. Three guardrails wrap it: (1) a loop-detection service watches for repeated identical tool calls / content loops and halts them (opt-out via `model.disableLoopDetection`, default false — i.e. ON); (2) a 'next speaker check' decides after each model turn whether the model should continue or yield to the user (`model.skipNextSpeakerCheck`); (3) when context usage crosses `model.compressionThreshold` (a fraction of the context window, default 0.5), the core automatically compresses/summarizes older history before the next request, designed to preserve information while cutting tokens. `model.maxSessionTurns` caps runaway sessions. An experimental `experimental.modelSteering` lets the user inject hints mid-execution without breaking the loop. *Relevance:* These guardrails exist precisely because Gemini's loop must survive imperfect model behavior — the same regime as GLM-5.2/DeepSeek on Ollama. Open models loop far more than frontier ones (re-reading the same file, retrying an identical failing command); a harness-level loop detector in session.py (hash the last N tool calls, break + inject a corrective message) is cheap and high-impact for autonomous missions burning retry budgets. The compression threshold deserves local-first tuning: on Ollama, truncating/summarizing history invalidates the KV-cache prefix, so Resonant should compress rarely but decisively (compact once at a high threshold into a stable summary block that then becomes a new cacheable prefix), rather than continuous trimming. The next-speaker check fixes a classic open-model failure — ending a turn with 'I will now run the tests' and no tool call.
- **Gemini CLI: checkpointing via a shadow git repository with /restore** *(medium)* — When enabled (`general.checkpointing.enabled: true` in settings.json), every time the user approves a file-modifying tool (write_file, replace), the CLI first commits the ENTIRE project state to a hidden shadow git repo at `~/.gemini/history/<project_hash>` — completely separate from the project's own git, so no branches/index pollution. Alongside the snapshot it saves the full conversation history and the exact pending tool call as JSON under `~/.gemini/tmp/<project_hash>/checkpoints`. `/restore` lists checkpoints; `/restore <file>` reverts working-tree files to the snapshot, restores the conversation to that point, and re-proposes the original tool call for re-approval or modification. Entirely local; a related /rewind feature (docs/cli/rewind.md) extends this into general session time-travel. *Relevance:* Resonant has git_tools.py but that operates on the user's real repo — dangerous as an undo mechanism (users hate agent-created commits/stashes, and mission retries can trash uncommitted work). A shadow repo gives autonomous missions free, invisible undo: snapshot before each retry-budget attempt, and on acceptance-check failure roll back files AND conversation to the pre-attempt state instead of letting DeepSeek 'fix forward' on top of its own mess — fixing-forward is where open models spiral. It also makes the web GUI's mission review safer: show diff-vs-checkpoint, one-click revert. Implementation is genuinely easy in Python: `git --git-dir=<shadow> --work-tree=<project> add -A && commit`, keyed by a project-path hash, exactly as Gemini does it.
- **Gemini CLI: GEMINI.md hierarchical context files with modular imports and configurable filename** *(small)* — Three layers are concatenated into an instruction block sent with every prompt: (1) global `~/.gemini/GEMINI.md`; (2) workspace: from cwd up through parent directories to the project root; (3) just-in-time: when tools touch files in a subdirectory, that directory and its ancestors (up to a trusted root) are scanned for context files and their content is pulled in. Files support modular imports via `@relative/or/absolute/path.md` syntax (processed by the 'memport' processor, docs/reference/memport.md), so a root file can compose team docs. `/memory show` prints the exact concatenated text the model sees; `/memory reload` (formerly refresh) rescans. The filename is configurable — `"context": {"fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"]}` — giving cross-tool compat. The footer shows the count of loaded context files. There's also a manual `save_memory`-style tool path that appends facts to the global file. *Relevance:* Same core argument as Codex's AGENTS.md (stable, deterministic instructions beat in-context hope for open models; stable prefix = Ollama KV-cache hits), but Gemini adds three refinements worth copying: the `@import` composition (lets Resonant users keep one small entry file and import ARCHITECTURE.md sections without blowing the token budget on everything), the just-in-time subdirectory loading (monorepo-friendly, loads payment-service rules only when the agent enters that directory — good for keeping GLM-5.2's context lean), and above all `/memory show` — with weak models, debugging 'why did it ignore my instructions' starts with seeing the exact injected text, and Resonant's GUI could render this in one afternoon. Support AGENTS.md as the default filename for ecosystem interop.
- **Gemini CLI: auto-memory — background extraction of memories and skills into a review inbox** *(medium)* — Experimental (`experimental.autoMemory: true`). A background process analyzes past sessions (heuristic: sessions with 10+ messages idle 3+ hours) and extracts three kinds of durable knowledge: facts/preferences, workflow constraints (e.g. 'always run X to verify'), and procedural fixes for project-specific landmines. Each candidate is written as a unified-diff `.patch` file against a memory file, or as a reusable `SKILL.md`, under `<projectMemoryDir>/.inbox/<kind>/` — NOTHING is applied automatically. The user reviews the inbox (via /memory inbox); approved skills land in `~/.gemini/skills/` (user scope) or `.gemini/skills/` (workspace scope), approved memory patches are applied to the underlying memory files (project or global GEMINI.md) and memory is hot-reloaded into the current session. Gemini also ships a full skills system (activate_skill tool loading SKILL.md procedural expertise from .gemini/skills) that these feed into. *Relevance:* This is convergent evolution with Resonant's self-improvement loop (field observations -> skills, docs/self-improvement-loop.md) — validation that the design is right, plus two concrete upgrades. First, the diff-patch-inbox-with-approval pattern: Resonant's loop ingests observations as skills, but with open models generating the observations, silent self-modification compounds errors (a hallucinated 'lesson' pollutes every future session). Staging every proposed skill/memory as a reviewable .patch file in the GUI, applied only on approval, adds exactly the safety valve a weaker extractor model needs — and DeepSeek can do extraction as a cheap idle-time mission on the Mac Studio. Second, the idle-session trigger heuristic (10+ messages, 3h idle) is a sensible scheduling policy Resonant's orchestration/skills.py can copy directly.
- **Gemini CLI: extensions system + MCP integration (bundled servers, commands, hooks, skills)** *(large)* — MCP servers are configured under `mcpServers` in ~/.gemini/settings.json (stdio or HTTP), exposing their tools into the loop alongside built-ins, with list_mcp_resources / read_mcp_resource tools for MCP resources. Extensions package a whole capability as one installable unit: a `gemini-extension.json` manifest can bundle MCP servers, context files (GEMINI.md fragments), custom slash commands, prompts, themes, hooks, sub-agents, and agent skills. Install straight from a repo: `gemini extensions install https://github.com/gemini-cli-extensions/workspace`; manage with `gemini extensions list` / `/extensions list`; an official gallery lives at geminicli.com/extensions/browse. The docs tree also shows the surrounding ecosystem it feeds: hooks (docs/hooks/), subagents (docs/core/subagents.md), custom commands, and a policy engine (docs/reference/policy-engine.md) governing what bundled tools may do. *Relevance:* Two distinct decisions here. (a) MCP client support: medium effort, big payoff — Resonant's hand-rolled tools (browser.py, computer_use.py, rag.py) stay, but MCP unlocks the existing ecosystem of servers without writing adapters; caveat: open models degrade as tool count grows, so copy Codex's `enabled_tools`/`disabled_tools` allowlisting per server and expose a curated subset to GLM-5.2. (b) The bundling insight: Resonant's skills system currently distributes skills individually; a manifest that bundles skills + context file + tool config + acceptance checks as one installable 'capability pack' (from a git URL, like Gemini) would let its self-improvement loop output shareable artifacts. Start with (a); (b) is a roadmap item.
- **Gemini CLI: free-tier economics — 1M context, token caching, and model fallback routing (incl. local Gemma classifier)** *(medium)* — The free tier (Google-account OAuth) gives 60 requests/min and 1,000 requests/day on Gemini 3 models with a 1M-token context window; the usage pattern this enables is 'stuff, don't retrieve' — read_many_files concatenates whole directory trees via `@` mentions, and compression only kicks in at 50% of the (huge) window. Cost control comes from three mechanisms: (1) implicit token caching reuses the stable system prompt + context prefix across requests to cut billed tokens — but only for API-key and Vertex AI auth (the OAuth Code Assist API doesn't support cached content), visible via /stats cached-token counts; (2) a ModelAvailabilityService handles quota/server errors by walking a fallback chain (precedence: --model flag > GEMINI_MODEL env > model.name setting > local Gemma > 'auto' default) — user-facing operations prompt before switching models by default, while internal utility calls (prompt completion, classification, next-speaker checks) fall back silently; (3) experimental `gemmaModelRouter` runs a tiny Gemma3-1b via a local LiteRT-LM server (`experimental.gemmaModelRouter: {enabled, classifier: {host, model}, autoStartServer}`) so routing/classification decisions are made locally at zero API cost. *Relevance:* This is the closest analogue to Resonant's economics: quota-bound cloud models (ollama.com 403s) + free local compute, exactly inverted from pay-per-token. Three direct ports: (1) formalize a fallback chain in backends.py — when the circuit breaker opens on glm-5.2:cloud, degrade to a local Mac Studio model for utility calls (summarization, intent classification, acceptance pre-checks) silently, and prompt the user before downgrading the main conversation, mirroring Gemini's prompt-vs-silent split; (2) the local-classifier-model pattern is tailor-made for Resonant's intent_service.py and grill_me.py — a small local model (qwen-class on the Mac Studio) can do routing/classification without spending cloud quota or governor slots; (3) the caching lesson transposes: Resonant's 'billing' is Ollama prompt re-processing time, so engineer prompts exactly like Gemini engineers for implicit caching — stable system prompt, append-only history, compression as rare prefix-rebuilds — and surface a /stats-style cache-hit indicator in the GUI.

### aider-cline

Aider's core insight is that weak-model reliability is an engineering problem solved OUTSIDE the model: give it a cheap graph-ranked repo map instead of full-file context, pick the edit format each model can actually emit (measured per-model on a benchmark that separately tracks 'correct edit format %'), apply its imperfect diffs with aggressively forgiving patchers (9X error reduction), verify every edit with lint/test loops that feed errors back, and make every change instantly revertible via git auto-commits. Its architect/editor split lets a strong reasoner (e.g. DeepSeek) describe changes in free text while a format-reliable model emits the actual edits — historically the single biggest benchmark jump for open-model pairings. Cline and Roo pioneered XML-in-plain-text tool calling precisely because open/local models had flaky native function calling; as of mid-2026 both are migrating to native tool calls for capable 'next-gen' models (Roo removed XML as default around v3.33-3.40, Nov 2025-Jan 2026; Cline gates by model family) but keep the scaffolding that made weak models work: automated 'you did not use a tool' retry nudges, per-parameter missing-value errors with format reminders, progressive escalation after consecutive failures, consecutive-mistake counters, fuzzy Levenshtein diff application with line hints, a compact system prompt for local Ollama/LM Studio models, and JSON tool-use fallbacks for Ollama. Cline's Plan/Act split (read-only planning, per-mode model choice), shadow-git checkpoints after every tool use, and Roo's custom modes (tool groups + file-regex hard guardrails, sticky per-mode models) plus Orchestrator subtask context isolation round out the playbook. Nearly all of these map directly onto Resonant's existing subsystems (session.py loop, git_tools.py, specialists.py, plan_graph.py, acceptance_check.py) as incremental upgrades rather than new architecture.

**Notable features:**

- **Aider repo map: tree-sitter tags + personalized PageRank + binary-search token fitting** *(medium)* — Aider parses every file with tree-sitter (py-tree-sitter language packs) and runs per-language tag queries extracting 'name.definition.*' and 'name.reference.*' tags (pygments Token.Name backfills references for languages without ref queries). It builds a NetworkX multigraph: nodes = files, edges = referencing-file -> defining-file per identifier, weighted by sqrt(num_refs) times multipliers: x50 if the referencing file is in the active chat, x10 for identifiers mentioned in the conversation, x10 for long snake_case/camelCase names (>=8 chars), x0.1 for _private identifiers, x0.1 for identifiers defined in >5 files. It runs nx.pagerank with a personalization vector boosting chat files, then binary-searches over the ranked tag list (initial midpoint max_map_tokens//25, 15% error tolerance) to emit the largest map of signatures that fits the --map-tokens budget (default 1k, dynamically expanded when no files are in chat). Tags are cached in SQLite via diskcache keyed on file mtime, so re-computation is cheap. *Relevance:* GLM-5.2 and DeepSeek v4 pro degrade sharply as context grows, and Resonant pays for context twice: Mac Studio prompt-processing time and local KV-cache invalidation. A ~1-4k-token symbolic map gives cross-file awareness (call signatures, who-uses-what) without dumping files, and it's fully deterministic — no embeddings, no extra model calls, unlike Resonant's RAG which retrieves prose chunks. The chat-file x50 and mentioned-identifier x10 personalization means the map auto-focuses on the task. One caveat for Ollama KV caching: a map that changes every turn breaks prefix reuse, so pin it per-task (Aider has --map-refresh settings) rather than per-message. Complements rag.py rather than replacing it: map for structure, RAG for semantics.
- **Aider edit formats + per-model format registry (whole / diff / diff-fenced / udiff / editor-*)** *(medium)* — Aider defines ~6 plain-text edit formats: 'whole' (model returns full updated file — trivial to emit, expensive), 'diff' (SEARCH/REPLACE blocks styled like git merge-conflict markers), 'diff-fenced' (path inside the fence — added because Gemini-family models kept violating the standard fencing), 'udiff' (simplified unified diff with line numbers deliberately removed because 'GPT is terrible at working with source code line numbers'; hunks are treated as search/replace patterns), and 'editor-diff'/'editor-whole' (stripped-down variants for architect mode's editor model). Every model gets an entry in aider/resources/model-settings.yml pinning edit_format, use_repo_map, examples_as_sys_msg (few-shot examples moved into the system message — used for deepseek-chat, kimi-k2, llama), weak_model_name for commit messages, and use_temperature: false for reasoners. Aider's benchmarking concluded plain-text formats beat function-calling APIs for edits across every model tested. *Relevance:* This is the highest-leverage idea for open models: format compliance is a per-model property you measure, not assume. GLM-5.2 and DeepSeek v4 pro will almost certainly differ in which format they emit reliably (Aider ships deepseek-chat as edit_format: diff with examples_as_sys_msg: true — a directly reusable starting point). Resonant's tools.py presumably does native-tool-call edits today; adding a per-model 'edit dialect' setting (SEARCH/REPLACE text blocks parsed from the reply for the model that needs it) and pinning it in a model registry mirrors backends.py's existing per-model knobs. examples_as_sys_msg is also a free win: open models follow concrete few-shot examples far better than abstract format specs.
- **Forgiving edit application: Aider's flexible udiff patcher + Roo's fuzzy apply_diff** *(small)* — Aider assumes the model's diff is imperfect and recovers: it normalizes malformed hunks by re-diffing them, detects lines the model forgot to prefix with '+', tolerates indentation drift, splits large hunks into overlapping smaller ones, and retries matching with varying context-window sizes. Disabling this flexible patching increased errors 9X in their benchmark; udiff itself took GPT-4 Turbo from 20% to 61% on a refactor benchmark and cut lazy 'rest of code here' placeholders 3X. Roo Code's apply_diff does the analogous thing for SEARCH/REPLACE: blocks carry a mandatory :start_line: hint, matching is Levenshtein distance on normalized strings with a configurable confidence threshold (0.8-1.0), searched middle-out within a ~40-line buffer around the hint; failures increment consecutiveMistakeCountForApplyDiff per file and report a typed failure back to the model. *Relevance:* Weak models produce almost-right edits constantly — whitespace drift, missing markers, stale context lines. Every edit Resonant's applier rejects becomes another expensive round-trip through the Mac Studio (or a burned retry from a mission's retry budget), and under cloud rate limits each retry also fights the concurrency governor. A fuzzy applier converts failed turns into successful ones with zero extra tokens. The concrete recipe: normalize whitespace before matching, accept >=0.9 similarity, use line hints to bound the search, and on failure return a structured error naming the exact block that failed (Roo) instead of a generic 'edit failed'. This alone can be worth several points of task success for GLM-class models.
- **Aider lint/test auto-fix loop (deterministic verification after every edit)** *(small)* — After every LLM edit, Aider automatically lints the changed files (built-in tree-sitter-based linters per language; overridable with --lint-cmd 'language: cmd', any command that prints errors and exits non-zero). With --test-cmd + --auto-test it also runs the test suite after each edit. Any non-zero exit sends the captured stdout/stderr back to the model as a new message asking it to fix, looping until clean or the user stops it. In the benchmark the same mechanism caps test output fed back at 50 lines. Compiled languages are handled by making the 'linter' a compile-this-file script and the 'test' a build-and-test script. Formatters that rewrite files are wrapped to run twice so the second pass reports only real errors. *Relevance:* Deterministic verification is the great equalizer for weak models: GLM-5.2 doesn't have to be right the first time if a linter catches the syntax error and the loop feeds it back within the same turn budget. Resonant already has acceptance_check.py at mission granularity — this is the same idea moved into the inner loop of session.py at per-edit granularity, which catches failures orders of magnitude earlier (an unparseable file caught immediately vs. after 20 more agent turns built on top of it). Truncating fed-back errors (50 lines) matters doubly on Ollama where every token costs prompt-processing time. Cheap to add: lint hook on the edit tool, configurable test command per project.
- **Aider git auto-commit workflow (auto-commit, dirty-commit isolation, /undo, weak-model commit messages)** *(small)* — Every AI edit is immediately committed with a descriptive message; before editing, any pre-existing uncommitted user changes are first committed separately ('dirty commits') so AI work never mixes with human work. Commit messages are generated by the configured weak_model from the diff plus chat history, following Conventional Commits by default (customizable via --commit-prompt). /undo does an instant git revert of the last AI commit. Attribution is explicit: '(aider)' appended to author/committer name, optional 'aider:' message prefix or Co-authored-by trailer, all toggleable. *Relevance:* Flaky models make destructive mistakes; per-edit commits turn every mistake into a one-command rollback and make autonomous-mission audit trails free (git log IS the mission log). The dirty-commit isolation matters for a daily-driver tool: the user's half-finished work is never entangled with what DeepSeek did overnight. Using a small local Ollama model for commit messages instead of the cloud flagship saves rate-limited cloud calls — exactly what the concurrency governor exists to protect. Resonant's git_tools.py already wraps git, so this is mostly policy: commit-after-edit in session.py/autonomous_loop.py, an undo tool, a weak-model message generator.
- **Aider architect/editor two-model split** *(medium)* — One request is split into two inference steps. The architect model gets the problem plus repo context and describes the solution 'however comes naturally to it' — free text, no format constraints. Its entire response is then handed to a second editor model whose only job is translating that description into strictly formatted edits (using the streamlined editor-diff or editor-whole formats set via --editor-edit-format / --editor-model). Rationale: a single model must 'split its attention between solving the coding problem and conforming to the edit format', and separating them lifted scores across the board — o1-preview + DeepSeek hit 85% (vs o1-preview alone lower), and even self-pairing helped (Sonnet 3.5 80.5% vs 77.4% solo). Notably DeepSeek proved 'remarkably capable' as the editor. *Relevance:* This is tailor-made for Resonant's two-flagship setup: DeepSeek v4 pro (mission flagship, strong reasoner) as architect, GLM-5.2 or even a small local model as editor. Open models suffer most from the attention-split problem — their format compliance collapses exactly when the reasoning gets hard — so the measured gains for open-model pairings are larger than for frontier models. It also plays well with the governor: the architect call can go to cloud while the mechanical editor call runs on the local Mac Studio, halving cloud traffic per edit. Resonant's specialists.py already routes roles to models, so this is a new two-step edit pipeline in the engine rather than new infrastructure.
- **Aider benchmark methodology: per-model edit-format tuning with a compliance metric** *(large)* — The polyglot benchmark runs 225 Exercism exercises across C++/Go/Java/JS/Python/Rust. Each exercise: model implements from instructions, tests run; on failure the model gets the test error output (capped ~50 lines) for exactly one retry; final score counts both attempts. Crucially the leaderboard reports 'percent using correct edit format' separately from 'percent correct', so you can tell whether a model is failing at coding or failing at emitting parseable edits. Aider uses this harness to decide each model's edit_format entry in model-settings.yml (e.g. GPT-3.5 got 'whole' because diff compliance was poor; GPT-4 got 'diff'; the original study found plain-text formats beat function-calling for all models tested). Open models on the board: DeepSeek reasoner variants ~74%, Qwen and Kimi K2 in the 50s. *Relevance:* Resonant already has a smoke-test harness; extending it into a small standing benchmark (even 30-50 exercises) with a format-compliance column would let you empirically answer questions you currently guess at: does GLM-5.2 do better with native tool-call edits or SEARCH/REPLACE text? Does DeepSeek v4 pro need examples_as_sys_msg? Does quantization on the Mac Studio change the answer vs the :cloud tag? The two-attempt-with-test-feedback protocol is also the right acceptance-check shape for missions: one automatic evidence-based retry before consuming the retry budget. Without this measurement loop, every other feature on this list gets tuned blind.
- **Cline Plan/Act modes with per-mode model selection** *(small)* — Plan mode is hard-restricted to read-only: Cline can explore files, search, and discuss strategy but cannot edit or run commands — enforced by the harness, not by asking the model nicely. Act mode unlocks execution and inherits the full Plan conversation ('Cline remembers everything you discussed in Plan mode'). A settings toggle 'Use different models for Plan and Act' assigns a stronger reasoning model to Plan and a cheaper/faster one to Act. Docs codify task-size guidance: trivial fixes straight in Act, medium tasks Plan->Act, large tasks via a /deep-planning slash command that produces a comprehensive plan first. *Relevance:* Harness-enforced read-only planning is a guardrail that doesn't depend on GLM-5.2's instruction-following: the mode simply doesn't expose write tools (Resonant can filter tools.py definitions per mode — weaker models also behave better with fewer tools in the prompt). Per-mode models formalize what Resonant half-does already: DeepSeek v4 pro plans, GLM-5.2 executes interactively — and grill_me.py's spec interrogation is effectively a Plan-mode activity that should hand off its artifact into Act. The context-carryover detail matters for KV caching: keeping one conversation across the mode switch preserves the local prefix cache instead of restarting it.
- **Cline checkpoints: shadow-git workspace snapshots after every tool use** *(medium)* — Cline maintains a shadow git repository completely separate from the project's real git. After EVERY tool operation (each file edit, each command) it commits the full workspace state — including files not tracked by the user's git — to the shadow repo. The UI offers three restores per checkpoint: 'Restore Files' (revert workspace, keep conversation), 'Restore Task Only' (rewind the conversation, keep files), 'Restore Files & Task' (both). The user's git log stays pristine; checkpoints persist across editor sessions; it's on by default with a toggle for huge repos where snapshotting gets slow. *Relevance:* Finer-grained and cleaner than Aider-style auto-commits: autonomous missions with retry budgets need 'rewind to just before the step that went sideways' — including untracked scratch files — without polluting the repo the user reviews in the morning. The 'restore conversation but keep files' variant is the interesting one for weak models: when GLM-5.2 talks itself into a corner but the code is fine, you rewind the transcript, not the workspace. Natural fit for autonomous_loop.py (checkpoint per plan-graph node) and the web GUI (timeline scrubber per mission). Implementation is a hidden GIT_DIR with the worktree pointed at the project — moderate but well-trodden.
- **Tool-calling strategy for unreliable models: XML-in-text prompting, native-call gating, and recovery scaffolding (Cline + Roo)** *(medium)* — Both tools historically avoided native function calling entirely: tools are described in the system prompt and the model emits XML-ish tags in plain text (<tool_name><param>value</param></tool_name>), one tool per message, parsed from the stream — because open/local models mangled provider-native tool calls. As of mid-2026 both are hybrid: Cline gates native tool calls by model family (isNextGenModelFamily in model-utils.ts: Claude 4+, GPT-5, Gemini 2.5/3, Grok-4, Kimi K2, DeepSeek 3.2+...; everything else stays XML), added a z.ai/GLM native-calling provider, an Ollama JSON tool-use fallback, and per-model tool-capability detection for Ollama. Roo shipped a 'native tool protocol' (v3.32-3.33, Nov 2025) with a per-model/per-profile protocol selector and 'dynamic tool protocol resolution with proper precedence hierarchy', then made native the default and removed XML for most paths by ~v3.40 (Jan 2026) — leaving a trail of issues ('Roo should allow recovery when model returns malformed tool call XML'). The recovery scaffolding is the durable lesson, from Cline's responses.ts: if a reply uses no tool, an automated '[ERROR] You did not use a tool in your previous response! Please retry with a tool use' message goes back, appending the full XML format reminder only for non-native models; missing parameters get typed errors naming the parameter plus the format reminder; write_to_file with empty content escalates progressively — after 3 consecutive failures it forbids retrying the same tool and prescribes alternatives ('create empty file then replace_in_file in 50-100 line sections'), and it's context-window-aware ('Context window is N% full... use a strategy that produces smaller outputs'). A consecutive-mistake counter eventually asks the user for guidance. *Relevance:* This is Resonant's most acute pain point addressed directly. Ollama-served GLM-5.2 and DeepSeek v4 pro have exactly the flaky-native-tool-calling profile these mechanisms were built for. Concrete adoptions for session.py: (1) a per-model tool-protocol setting in backends.py (native vs text-parsed), decided by measurement, with Roo's precedence hierarchy (model default -> profile override); (2) the automated no-tool-used retry nudge instead of treating a toolless reply as terminal; (3) typed per-parameter errors with a format example on every malformed call; (4) progressive escalation with prescribed alternative strategies after N consecutive failures of the same tool — this is what keeps autonomous missions from burning their whole retry budget on the same doomed write; (5) context-usage warnings injected into error messages so the model stops attempting 800-line file writes near the window limit. History note: Roo's 2026 migration shows native calling is winning for frontier models, but they kept per-model selection — exactly the posture an Ollama-only harness needs.
- **Roo custom modes + Cline rules: declarative personas with hard tool/file guardrails** *(small)* — A Roo mode is a YAML/JSON object (.roomodes in the workspace, custom_modes.yaml globally; project overrides global wholesale, no merging): roleDefinition (identity, top of system prompt), customInstructions (rules, near the end), groups (which tool categories the mode gets: read/edit/command/mcp), and per-edit fileRegex restrictions (e.g. a docs mode that can only touch \.(md|mdx)$ — enforced by the harness, edits outside the pattern are rejected). Each mode is 'sticky' to the last model used with it, so switching modes switches models automatically. Built-ins: Code, Architect, Ask, Debug, Orchestrator. Cline's parallel: .clinerules/ folders of markdown (plus AGENTS.md/.cursorrules compatibility), individually toggleable in the UI, with conditional rules scoped by YAML frontmatter path globs ('paths: [src/components/**]') that activate only when matching files are open/edited/mentioned — saving context tokens when irrelevant. *Relevance:* Two transferable mechanics for specialists.py and skills.py. First, hard enforcement: fileRegex and tool-group restrictions are guardrails that hold even when GLM-5.2 ignores instructions — a 'test-writer' specialist physically cannot edit src/. Second, sticky per-mode models formalize the GLM-interactive/DeepSeek-mission split declaratively instead of in code. Cline's path-conditional rule loading is directly relevant to Resonant's skills system: skills that inject only when the touched files match their scope keep the system prompt short — which on Ollama means faster prompt processing AND a more stable prefix for KV-cache reuse (toggling whole rule files thrashes the cache; scoped activation bounded per-task doesn't).
- **Roo Orchestrator (boomerang tasks): subtask delegation with strict context isolation** *(small)* — In Orchestrator mode the parent task decomposes work and calls new_task, specifying a target mode (Code/Debug/etc.) and detailed instructions; the parent then pauses. The subtask runs in a completely fresh conversation — 'it does not automatically inherit the parent's context'. Information flows down only via the initial instructions and back up only via the subtask's attempt_completion summary; the parent never sees the subtask's diffs, file reads, or tool chatter. This keeps the parent transcript to pure coordination and lets each subtask start with a near-empty context window. *Relevance:* Resonant already has plan graphs, a walker, and specialists — the adoptable piece is the contract: fresh context per node, summary-only returns, explicit downward instruction-passing. Open models degrade badly on long transcripts (instruction drift, format decay), so an autonomous mission that accumulates one giant conversation is playing against GLM/DeepSeek's weakest attribute; N short conversations with a thin coordinator plays to their strength. On Ollama it's also a throughput win: short contexts mean fast prompt processing and small KV footprints, letting the Mac Studio serve parallel subtasks, and it keeps individual cloud calls small enough to slide under the rate-limit governor. Audit walker.py/plan_graph.py for context leakage between nodes and tighten the return channel to structured summaries.

### goose-local

Goose (originally block/goose, now aaif-goose/goose under the Linux Foundation's Agentic AI Foundation, v1.39 as of June 2026) is the most mature open harness explicitly engineered around weak-model realities: it REMOVED its automatic lead/worker model-switching feature in favor of an explicit Planning Mode (plan with a strong model, clear history, execute with a cheap one), added a 'toolshim' that uses a small local interpreter model with Ollama structured outputs to repair non-native tool calls, added Code Mode (3 meta-tools replace all MCP tool schemas in the prompt), and ships aggressive default context management (auto-compact at 80% of context, tool-output summarization after 10 tool calls). On the Ollama side, the agent-relevant surface matured substantially: template-aware incremental streaming tool-call parsing with JSON fallback, grammar-constrained structured outputs, a per-request `truncate:false` option that turns silent context truncation into a hard error (default is still silent oldest-message-dropping in server/prompt.go, logged only at DEBUG), VRAM-tiered default context (4k under 24GB, 32k for 24-48GB, 256k above — docs explicitly recommend >=64k for coding agents), local KV prompt-prefix reuse via llama.cpp's cache_prompt (default on, but coupled to the `shift` option, and per-slot — OLLAMA_NUM_PARALLEL>1 thrashes it), an Anthropic-compatible /v1/messages endpoint plus `ollama launch claude|opencode|codex`, and cloud models (:cloud tags) that per user benchmarks and open issue #16714 have NO server-side prompt caching — every agent turn re-prefills the whole conversation, which compounds with rate limits. Community consensus (goosebench, aider docs, Goose context-windows blog) ranks the levers for local models: (1) explicit context sizing + context discipline, (2) native tool calling over shims (consistent large gap at every model size), (3) fewer tool schemas in the prompt, (4) reflection/retry with the error text on malformed calls, (5) avoid heavy quantization for edit-heavy work.

**Notable features:**

- **Ollama silent context truncation and the truncate:false escape hatch (num_ctx discipline)** *(small)* — Ollama's chat path (server/prompt.go, chatPrompt) drops messages from the FRONT of the conversation until the rendered prompt fits num_ctx, always preserving system messages and the latest message, and logs only at DEBUG level ('truncating input messages which exceed context length') — the API response carries no truncation indicator (open issue #7043 asks for a warning). Historically the default num_ctx was 2048 then 4096; the current Ollama app auto-tiers the default by VRAM: 4k under 24GB, 32k for 24-48GB, 256k above 48GB, and docs.ollama.com/context-length explicitly says agents/coding tools 'should be set to at least 64000 tokens'. Overrides: per-request options.num_ctx, server-wide OLLAMA_CONTEXT_LENGTH env, or the app slider. New in the API (api/types.go): a per-request `"truncate": false` boolean makes the server return an error instead of silently dropping history (default is true = silent drop), and a separate `"shift"` boolean controls context-shifting during generation. Aider's Ollama docs document the same pitfall and its fix: aider computes the needed window per request and sets num_ctx = prompt tokens + 8k reserved for the response. *Relevance:* This is the single most common way an Ollama-based agent silently loses its mind: on the Mac Studio, if num_ctx is smaller than a long mission transcript, GLM-5.2/DeepSeek keep the system prompt and last message but lose the middle of the session — tool results, plan state, earlier file contents — with zero API-level signal, and the model starts re-reading files or contradicting earlier decisions. Resonant's backends.py should (a) always send an explicit options.num_ctx sized from its own token count (Aider-style: prompt + response reserve), (b) send truncate:false so overflow becomes a catchable error that triggers Resonant's own compaction instead of Ollama's blind head-drop, and (c) assert via `ollama ps` / logs that the model isn't spilling to CPU when num_ctx is raised (100% GPU vs split changes throughput drastically).
- **Local KV-cache prompt-prefix reuse (cache_prompt) and prompt hygiene for cache hits** *(small)* — Underneath Ollama, llama.cpp's llama-server keeps a per-slot KV cache and, when `cache_prompt` is true (default true in llama-server), reuses the longest common token prefix between the new request and what's already in the slot — only the differing suffix is re-processed (prefill). llama.cpp adds: `--cache-reuse N` (min chunk size to reuse non-contiguous cache pieces via KV shifting), `--slot-prompt-similarity` (default 0.10; routes a request to the slot whose cached prompt best matches), slot persistence endpoints (POST /slots/{id}?action=save|restore|erase) and timing fields (cache_n = tokens served from cache, prompt_n = newly processed). In Ollama, cache_prompt is currently hardwired to the public `shift` option (issue #16635 / PR #16639: one boolean drives both per-request cache_prompt and the --context-shift runner flag; shift defaults to true, so caching is on by default). Gotchas: each parallel slot has its OWN cache, so OLLAMA_NUM_PARALLEL>1 with interleaved sessions thrashes prefix reuse; ANY byte change early in the prompt (timestamp in the system prompt, reordered tool definitions, re-serialized JSON with different key order) invalidates everything after it; Ollama's MLX runner recently gained cross-conversation prefix sharing (PR #14887). PRs #15768/#8008 aim to expose prompt-cache hit counts in Ollama's completion response but aren't merged. Related knobs: OLLAMA_FLASH_ATTENTION=1 plus OLLAMA_KV_CACHE_TYPE=q8_0 halves KV memory (q4_0 quarters it) letting you afford bigger num_ctx; OLLAMA_KEEP_ALIVE / keep_alive=-1 keeps the model (and its warm cache) resident. *Relevance:* Resonant has no vendor prompt-cache billing to optimize — its 'prompt caching' is entirely this local KV reuse, and it's the difference between ~1s and ~60s per turn on a long mission transcript on the Mac Studio. Concrete rules for session.py/tools.py: keep the system prompt and tool-schema JSON byte-stable across turns (no timestamps, stable key ordering, stable tool ordering); build turns strictly append-only (compaction = one deliberate cache-bust, so do it rarely and in big steps); avoid mid-prompt mutation like re-rendering RAG context at the top each turn — append new context at the end instead; and be careful with the concurrency governor: fanning specialist requests for the SAME local model across parallel slots destroys prefix reuse, so pin one session to one slot / serialize per-session requests. Also worth watching: keep_alive so autonomous missions don't pay a model reload after 5 idle minutes.
- **ollama.com cloud models have NO prompt caching — agent loops pay full prefill every turn** *(small)* — Ollama cloud models (:cloud tags, e.g. glm-5.2:cloud) run on Ollama's datacenter GPUs; the local daemon transparently proxies /api/chat, or you can hit https://ollama.com/api/chat directly with an OLLAMA_API_KEY bearer token. Cloud models default to their maximum context length (docs.ollama.com/context-length). But per open issue #16714 (filed by a paying subscriber who benchmarked agentic loops with OpenCode + glm-5.1): 'I am 100% sure that the positive effect that we expect to see from carefully set cache boundaries in agentic loops are not there when using ollama cloud' — ollama.com does not expose or apparently implement provider-side prompt/prefix caching, unlike Anthropic/OpenAI/Z.ai direct APIs or aggregators. Issue #15600 asked the same question and was closed without a real answer. The Anthropic-compat layer docs also state 'Prompt caching and batch processing remain unavailable'. Consequence: every agent turn re-processes the entire conversation from token zero (O(n^2) total prefill over a session), which shows up as growing per-turn latency AND faster consumption of Ollama cloud's hourly/weekly usage limits — the same limits that produce Resonant's 403s. *Relevance:* This directly hits both flagships (glm-5.2:cloud interactive, DeepSeek v4 pro missions). It means (1) the latency growth Resonant sees late in long cloud sessions is structural, not governor misbehavior; (2) context bloat on cloud is doubly expensive — it costs prefill time AND rate-limit quota, so compaction thresholds should be MORE aggressive for cloud sessions than local ones (Resonant can key compaction policy off the ':cloud' tag in backends.py); (3) the adaptive governor's backoff math could incorporate transcript length as a predictor of per-request cost; (4) for very long autonomous missions, a hybrid routing policy (local model for high-turn-count grind phases, cloud flagship for planning/review turns) is rational because the local side at least gets KV prefix reuse. Worth subscribing to issue #16714 — if Ollama ships cloud caching, the tradeoff flips.
- **Ollama template-aware streaming tool-call parser + grammar-constrained structured outputs** *(small)* — Streaming tool calls (ollama.com/blog/streaming-tool): Ollama's incremental parser reads each model's chat TEMPLATE to learn that model's tool-call prefix/tokens, so it can split tool calls out of a token stream in real time instead of buffering the whole response and regexing JSON afterwards. Fallbacks handle badly-behaved models: if a model emits an unprefixed tool call, the parser detects 'start of a JSON' and attempts tool-call parsing; if the JSON doesn't match the model's tool format it's passed through as text; improved prefix/state tracking stops models that MENTION a previous tool call from triggering duplicate re-invocations. The blog explicitly recommends 32k+ context for reliable tool calling. Structured outputs (ollama.com/blog/structured-outputs): pass a JSON Schema in the `format` field of /api/chat//api/generate and the server constrains decoding to that schema (Pydantic model_json_schema() / Zod zodToJsonSchema() feed it directly); recommended practice is schema + a 'return as JSON' instruction + temperature 0. Tool-calling docs (docs.ollama.com/capabilities/tool-calling) cover single-shot, parallel calls, and multi-turn tool-result messages ({role:'tool', tool_name, content}), with `think` interleaving for reasoning models. *Relevance:* Two direct wins. First, Resonant should trust and lean on the server-side parser rather than duplicating fragile client-side extraction: stream with tools enabled, render tool calls live in the GUI, and treat the (now rare) malformed call as an explicit retry case. Second — bigger — every non-conversational LLM call in Resonant that today parses free text is a structured-outputs candidate: acceptance_check.py verdicts, grill_me.py question/answer extraction, intent_service.py classification, plan_graph node generation, skills ingestion. With GLM-5.2/DeepSeek-class open models, schema-constrained decoding converts 'usually valid JSON' into 'always valid JSON' at zero extra latency, eliminating a whole class of retry loops. Caveat: format-constrained decoding can degrade reasoning quality if the schema is huge — keep schemas small and flat, and let the model think (think:true) before the constrained final answer where supported.
- **Goose toolshim: a small local interpreter model repairs/extracts tool calls via structured outputs** *(medium)* — Goose's experimental Ollama toolshim (goose-docs.ai/docs/experimental/ollama) targets models with no or unreliable native tool calling. Mechanics: the PRIMARY model is instructed to express intended tool usage as JSON in plain text; a SECOND small local model (default mistral-nemo, configurable via GOOSE_TOOLSHIM_OLLAMA_MODEL, e.g. llama3.2) is then invoked with Ollama structured outputs to translate the primary model's message into schema-valid JSON, which Goose converts into actual tool invocations. Enabled with GOOSE_TOOLSHIM=1; docs recommend OLLAMA_CONTEXT_LENGTH=32768 for the server. Crucial empirical caveat from Goose's own benchmark (goosebench, blog 2025-03-31, 4000+ eval runs): toolshim configurations consistently scored far below natively tool-calling models AT EVERY SIZE CLASS (e.g. qwen2.5-coder:32b native = 0.80 vs deepseek-r1-671B+toolshim = 0.48, gemma3:27b+toolshim = 0.43), i.e. the shim is a crutch, not a substitute — 'native tool calling capabilities significantly impact performance on agentic tasks'. *Relevance:* GLM-5.2 and DeepSeek v4 pro DO have native tool calling, so Resonant should not adopt a full toolshim — but the pattern is valuable as a cheap REPAIR tier: when a tool call comes back malformed (wrong arg types, hallucinated tool name, JSON embedded in prose), instead of burning an expensive cloud turn on 'please fix your call', run a tiny always-loaded local model on the Mac Studio with a structured-outputs schema of {tool_name: enum of real tools, arguments: object} to salvage the intent, then validate args against the tool's JSON schema before executing. That's a sub-second local fix for what is today either a failed turn or a full flagship retry, and it slots naturally into session.py's tool-dispatch error path. The goosebench numbers are also the citable justification for Resonant's model-gating: only offer models with native tool support as mission-capable.
- **Goose Code Mode: replace N tool schemas with 3 meta-tools + sandboxed code execution** *(large)* — Code Mode (goose-docs.ai/docs/guides/managing-tools/code-mode) changes what the model sees: instead of injecting every enabled extension's full MCP tool definitions into every prompt, the prompt contains only three meta-tools — list_functions (discover available tools), get_function_details (fetch one tool's spec on demand), and execute_typescript. The LLM writes TypeScript/JavaScript that Goose executes in 'pctx', a custom Deno-based sandbox runtime, where discovered tools are callable as functions; multiple tool calls can be batched in one execution and intermediate results chained/processed locally without round-tripping through the model. Prompt context therefore holds 3 meta-tool defs + only the tool specs actually fetched this session. Limitations: only text tool results (images/binary dropped); Goose recommends it for 5+ extensions or well-defined multi-step workflows, and classic tool calling for small setups. *Relevance:* The underlying finding — every tool schema in the prompt costs context and dilutes open-model attention — matters more than the specific implementation. Resonant's tools.py exposes a wide surface (fs/git/browser/computer-use/RAG/skills); the cheap version of this insight is TOOL TIERING: send GLM-5.2 only the 8-12 tools relevant to the current phase (walker/plan_graph already knows the phase) and add a `load_toolgroup` meta-tool to pull in browser or computer-use schemas on demand. The full Code Mode (model writes Python executed in a sandbox with tool bindings) is a bigger bet and riskier with open models, which write buggier glue code than Claude-class models — goosebench-style eval before committing. Also note Goose ships this as a replaceable 'platform extension', which is the same shape as a Resonant specialist.
- **Goose smart context management: auto-compaction at 80%, tool-output cutoff, pluggable overflow strategies** *(medium)* — Goose (goose-docs.ai/docs/guides/sessions/smart-context-management) runs a two-tier defense. Tier 1, auto-compaction: at GOOSE_AUTO_COMPACT_THRESHOLD (default 0.80 of the context limit; 0.0 disables) it summarizes OLDER conversation while keeping recent tool calls verbatim; independently, once a session exceeds GOOSE_TOOL_CALL_CUTOFF (default 10) tool calls, older tool OUTPUTS get summarized/elided first — tool results are treated as the most disposable token class. Tier 2, overflow strategies via GOOSE_CONTEXT_STRATEGY: summarize (recommended), truncate (drop oldest), clear, or prompt (ask the user; CLI default). Context limits are resolved by precedence: explicit model config > per-role env (GOOSE_PLANNER_CONTEXT_LIMIT) > GOOSE_CONTEXT_LIMIT > model-name pattern matching > 128k fallback; there's even GOOSE_INPUT_LIMIT specifically to cap input prompt size for Ollama requests. Loop safety: GOOSE_MAX_TURNS (default 1000) bounds consecutive turns without user input, GOOSE_SUBAGENT_MAX_TURNS (default 25) bounds subagents. *Relevance:* The transferable design decisions: (1) the harness owns token accounting — never trust the backend's window (Ollama truncates silently, see feature 1); Resonant needs a client-side tokenizer estimate + configured per-model limit exactly like GOOSE_CONTEXT_LIMIT, with a separate one for the local vs cloud variant of a model. (2) Compact tool OUTPUTS before conversation — in coding sessions 70%+ of tokens are file dumps and command output that age fast; an 'elide tool outputs older than K calls, keep a one-line digest + a re-fetch handle' rule is cheap and preserves the reasoning thread. (3) Trigger compaction proactively at ~80% rather than reactively on overflow — for Resonant this also aligns compaction (a KV-cache bust, feature 2) to happen once, deliberately. (4) Distinct turn budgets for main loop vs specialists map cleanly onto autonomous_loop.py retry budgets. All of this is more valuable for open models, which degrade earlier in the window than frontier models.
- **Goose recipes: declarative, parameterized agent runs with success checks, retries, and schema-typed results** *(medium)* — A recipe (goose-docs.ai/docs/guides/recipes/recipe-reference) is a YAML/JSON file that fully specifies an agent run: title/description; `instructions` (context) and/or `prompt` (kicks off headless execution); `extensions` (exact MCP servers/tools available, with per-extension timeout and env_keys); `settings` (goose_provider, goose_model, temperature, max_turns); `parameters` (typed inputs — string/number/boolean/date/file/select, required/optional/user_prompt, with {{ param }} Jinja-style templating, inheritance via {% extends %}, filters); `sub_recipes` (composition with pinned values); `response.json_schema` (the run's final answer must match a JSON Schema — enforced so automation can consume it); and `retry` (max_retries, timeout_seconds, `checks` = shell commands that must succeed, `on_failure` cleanup command). Execution: load → prompt for missing params → substitute → init extensions → apply settings → run → run success checks → on failure run on_failure then retry until success or budget exhausted → return schema-shaped response. Recipes are shared via files, a marketplace, and deeplinks; sessions can be exported to recipes. *Relevance:* Resonant already has the semantic pieces (missions, acceptance_check.py, retry budgets, skills) but not the artifact: a single portable file that binds prompt + allowed toolset + model settings + acceptance checks + retry policy + typed output. That artifact is what makes runs reproducible and shareable, and it composes perfectly with Resonant's existing subsystems: acceptance_check becomes recipe `checks`; the mission result becomes `response.json_schema` enforced via Ollama structured outputs (feature 4) — with open models the schema-enforced final report is dramatically more reliable than prose parsing; per-recipe `extensions`/tool allowlists implement tool tiering (feature 6) per task type; parameterized recipes give the GUI a one-click 'run this mission template on repo X' surface; and successful missions can be auto-exported as recipes, which is a natural extension of the skills self-improvement loop. Shell-command success checks are model-independent, which is exactly the right verification style when the model is the unreliable component.
- **Goose lead/worker (removed) → Planning Mode: the multi-model lesson** *(small)* — Original lead/worker (blog 2025-06-16 'multi-model-in-goose'): GOOSE_LEAD_MODEL = strong planner handles the first GOOSE_LEAD_TURNS turns (default ~3), then GOOSE_MODEL (cheap worker) executes; on GOOSE_LEAD_FAILURE_THRESHOLD consecutive REAL failures (tool execution errors, syntax errors, file-not-found, explicit user corrections — not transient issues) control escalates back to the lead for a few fallback turns. As of 2026 this automatic turn-based switching HAS BEEN REMOVED from Goose (deprecation notice on blog 2025-08-11) and replaced by Planning Mode: `/plan <description>` runs a dedicated planner model (GOOSE_PLANNER_PROVIDER/GOOSE_PLANNER_MODEL/GOOSE_PLANNER_CONTEXT_LIMIT, falling back to the defaults), which iteratively asks clarifying questions (budget, tech choices, auth, etc.; user can batch-answer or demand a 'generic plan'), produces a step-by-step plan, then asks 'Do you want to clear message history & act on this plan?' — acceptance CLEARS the context and hands the plan to the execution model as a fresh prompt. The implicit lesson: mid-session automatic model swapping (mixed-provider message histories, KV cache invalidation on every swap, ambiguous failure attribution) lost to an explicit plan → clear → execute pipeline with a hard context boundary. *Relevance:* Resonant is architecturally ahead here (grill_me.py IS the clarifying-question loop; plan_graph/walker is the plan artifact), and the Goose experience is evidence for doubling down on explicit phase boundaries rather than building automatic lead/worker switching: (1) plan with glm-5.2:cloud, then START THE EXECUTION SESSION FRESH with only the plan + repo context — the history-clear is not just token savings, it removes the planner's meandering from the executor's context (open-model executors imitate whatever mess they see); (2) the 'escalate only on REAL failures' classification (tool errors, syntax errors, user corrections — not transient 403s) is directly reusable in autonomous_loop.py for deciding when a DeepSeek mission turn should be retried locally vs escalated to the interactive flagship or the human; (3) per-role context limits (planner vs executor) matter when the planner is cloud (max context, no KV cache — feature 3) and the executor is local (KV reuse, bounded num_ctx).
- **Ollama as an agent platform: Anthropic-compatible /v1/messages + `ollama launch` for coding agents** *(small)* — Ollama now exposes an Anthropic Messages API-compatible endpoint at /v1/messages (docs.ollama.com/api/anthropic-compatibility): supports streaming, tool use with schemas and tool results, system prompts, multi-turn, vision (base64 only), and thinking/extended-thinking passthrough; NOT supported: tool_choice forcing, metadata, /v1/messages/count_tokens, prompt caching, batches. Any Anthropic-SDK app can be pointed at it with ANTHROPIC_BASE_URL=http://localhost:11434 and a dummy ANTHROPIC_AUTH_TOKEN — the documented use case is running Claude Code against local or cloud Ollama models (recommended: qwen3-coder, glm-4.7:cloud). The `ollama launch` CLI command automates this: interactive configure-and-launch of Claude Code, OpenCode, Codex, VS Code, and Droid against Ollama models (`ollama launch claude --model qwen3.5`), writing the env/config for you. There's also a parallel OpenAI-compat surface (/v1/chat/completions), and PR #14891 is extending the Anthropic endpoint with num_ctx support. *Relevance:* Strategic context more than a feature to copy: Ollama itself is commoditizing 'frontier harness on local models' — a user can now run Claude Code or OpenCode against the same Mac Studio glm/qwen models Resonant targets, one command. Resonant's differentiation must come from the layers those harnesses lack on Ollama: mission autonomy with acceptance checks, the skills loop, plan graphs, the 403 governor, KV-cache-aware prompt discipline (features 1-3). Tactically: (a) the /v1/messages endpoint means Anthropic-format prompt/tool ecosystems (system-prompt packs, MCP bridges, eval suites built on the Anthropic SDK) can be reused against Ollama backends, and it's a second wire format backends.py could speak; (b) the endpoint's gaps (no tool_choice, no count_tokens, no caching) confirm Resonant must keep client-side token accounting; (c) watching what `ollama launch` configures (context length, keep_alive) for Claude Code is free R&D on Ollama's own recommended agent settings.
- **Community consensus: the harness techniques that actually move the needle for local/open models** *(medium)* — Converging findings across the primary sources: (1) CONTEXT DISCIPLINE FIRST — Goose's context-windows blog ('the difference between flaky and focused is just a few tokens'): short focused sessions, subagents to isolate dirty work, hints files instead of re-explaining, manual/auto summarization; Ollama's own guidance: 32k+ ctx for tool calling, 64k+ for coding agents; Aider auto-sizes num_ctx per request. (2) NATIVE TOOL CALLING BEATS SHIMS — goosebench (4000+ runs): a native-tool-calling 32B (qwen2.5-coder:32b, 0.80) outperformed a 671B model driven through a tool shim (0.48); the gap held across all size classes. (3) FEWER TOOL SCHEMAS — Goose Code Mode exists because 'with multiple extensions... every prompt includes all tool definitions'; recommendation threshold is just 5+ extensions. (4) RETRY-WITH-ERROR-TEXT ON MALFORMED OUTPUT — Ollama moved robust tool-call extraction server-side (template-aware parser with JSON fallback and dedupe); Aider 'works hard to deal with LLM edits that are almost correctly formatted', feeds failures back, and recommends `--edit-format whole` and two-step architect mode (one model proposes, one formats/applies) for models that can't follow diff formats — the same models are 'more prone to disobeying the system prompt', and heavily quantized local models have measurably more edit-format failures. (5) MODEL-INDEPENDENT VERIFICATION — Goose recipes gate success on shell-command checks, not model self-report. *Relevance:* This is the priority ordering for Resonant's polish push, adapted to GLM-5.2/DeepSeek v4 pro: they're strong open models, so the biggest residual gaps vs frontier harness behavior are instruction adherence under long context and edit-format fidelity. Concrete ranked backlog: (1) explicit num_ctx + truncate:false + client-side token budget (feature 1) — hours of work, removes the worst silent failure; (2) byte-stable prompts for KV reuse locally + aggressive compaction on cloud (features 2-3); (3) phase-scoped tool tiering in tools.py (feature 6-lite); (4) a three-tier malformed-call ladder in session.py: server parser → local structured-outputs repair (feature 5) → one retry with the exact validation error quoted; (5) whole-file edit fallback when a model repeatedly fails search/replace-style edits, per Aider; (6) keep acceptance checks shell-based (already Resonant's design — validated by Goose recipes converging on the same thing).

### glm-deepseek

GLM-5.2 (753B MoE, 1M context, MIT, released 2026-06-13) and DeepSeek V4 (V4-Pro 1.6T/49B active; V4-Flash 284B/13B active; 1M context; API GA with deepseek-chat/reasoner deprecated 2026-07-24) are both explicitly trained and productized around Claude Code-style agent scaffolds — both vendors ship Anthropic-compatible endpoints and official Claude Code integration guides. The highest-leverage harness work for Resonant: (1) match the scaffold shape these models were tuned on (Claude Code conventions: CLAUDE.md/AGENT.md, opus->flagship + haiku->cheap-model mapping, max effort for agents); (2) wire thinking correctly — GLM-5.2 uses reasoning_effort max|high, DeepSeek V4 has high/max effort tiers, and DeepSeek REQUIRES replaying reasoning_content across tool-call turns (Resonant's session.py currently does not pass message.thinking back); (3) defend against each model's tool-call encoding on Ollama — GLM's XML <arg_key>/<arg_value> template stringifies nested JSON objects (confirmed ollama/ollama#15645 for glm-5.1:cloud), and DeepSeek V4's DSML tokens (<|DSML|tool_calls> etc.) leak into text content on Ollama Cloud (ollama/ollama#16375) because the :cloud passthrough bypasses local parsers and no DSML parser exists in the ollama repo; (4) respect Ollama Cloud caps and instability around tool calls (args truncated, num_predict capped at 65536 for v4-pro vs published 384K output, 500/503 storms); (5) adopt prefix-stability discipline since Ollama Cloud does not surface prompt caching (unverified benefit per #16714) and local KV cache is prefix-exact; (6) use vendor sampling (temp 1.0, top_p 0.95-1.0), not low-temp coding folklore. Verified benchmark reality: terminal-bench 2.1 shows Claude Code + GLM-5.1 at 58.7% (best verified open entry, rank 13) vs frontier ~83%; GLM-5.2 self-reports 81.0 TB2.1 and 62.1 SWE-bench Pro; DeepSeek V4-Pro-Max self-reports 80.6% SWE-bench Verified and 67.9% Terminal-Bench 2.0; Aider polyglot shows DeepSeek line has excellent diff-edit-format adherence (97.3%).

**Notable features:**

- **Match the Claude Code scaffold shape GLM-5.x and DeepSeek V4 are tuned for** *(medium)* — Both vendors now treat Claude Code as the reference harness. Z.ai's official dev-pack docs configure Claude Code against api.z.ai/api/anthropic with GLM-5.2 recommended for the Opus/Sonnet roles and GLM-4.7 as default, plus API_TIMEOUT_MS=3000000 and CLAUDE_CODE_AUTO_COMPACT_WINDOW knobs; the GLM-5 paper ('From Vibe Coding to Agentic Engineering', arXiv 2602.15763) describes async agent-RL on long-horizon interactions, and the only human-verified terminal-bench 2.1 entry for GLM runs it inside the Claude Code harness. Z.ai's GLM-5.2 docs explicitly recommend a 'CLAUDE.md or Agent.md' file for engineering standards and a /goal-style mode for refactors. DeepSeek's API docs likewise map deepseek-v4-pro to claude-opus and deepseek-v4-flash to claude-haiku/sonnet via api.deepseek.com/anthropic, set CLAUDE_CODE_SUBAGENT_MODEL=deepseek-v4-flash, and auto-escalate thinking effort to 'max' for 'complex agent requests like Claude Code'. *Relevance:* These models' agentic RL training distribution IS the Claude Code trace shape: a terse system prompt with tool-use rules, a small orthogonal tool set (read/edit/bash/grep-style), an AGENTS.md/CLAUDE.md project-memory file, TODO-list discipline, and subagent fan-out to a cheaper model. Resonant's engine/tools.py and orchestration/specialists.py get in-distribution behavior (fewer malformed calls, better long-horizon persistence) the closer they sit to that shape. Concretely: keep a CLAUDE.md/AGENTS.md convention in projects, mirror Claude Code's tool naming/granularity where reasonable, and copy the vendor pattern of flagship-for-main-thread + flash/cheap-model-for-subagents (GLM-5.2 interactive, deepseek-v4-flash could serve as Resonant's specialist/acceptance-check worker instead of running v4-pro everywhere).
- **Per-role thinking-effort control (GLM reasoning_effort, DeepSeek high/max, Ollama think levels)** *(small)* — GLM-5.x: reasoning_effort accepts 'max' (default) and 'high'; thinking can be disabled with enable_thinking=false; Z.ai API toggles via thinking:{type:'enabled'|'disabled'}. DeepSeek V4: thinking defaults enabled; OpenAI-format toggle thinking:{type:'enabled'/'disabled'}, Anthropic-format output_config.effort:'high'|'max'; 'high' is default, 'max' is auto-applied for agent harnesses; V4-Pro advertises three reasoning modes. On Ollama, the think parameter accepts true/false/'low'/'medium'/'high'/'max' — but top-level 'max' was only recently documented on main (docs/api.md); on older Ollama builds 'max' is rejected at top level and only works as options.think (ollama/ollama#15831), and the Ollama Anthropic-compat /v1/messages endpoint has no way to request max thinking at all (#15952). *Relevance:* Resonant already sends options.think with a per-model wire-value mapper in backends.py (_wire_think_value), so this is mostly tuning: run GLM-5.2 interactive sessions at 'high' (Z.ai says max is default; high cuts latency for the daily-driver use case, and glm-5.2:cloud slowness is already an open complaint, ollama/ollama#16779) and run DeepSeek v4 pro autonomous missions at 'max', which is what DeepSeek itself does for agent traffic (CLAUDE_CODE_EFFORT_LEVEL=max). Also verify the installed Ollama version accepts top-level think:'max' so the mapper can stop special-casing, and never route mission traffic through Ollama's /v1/messages shim where max is unreachable.
- **Replay DeepSeek reasoning_content across tool-call turns (interleaved thinking contract)** *(small)* — DeepSeek's thinking-mode guide draws a hard distinction: without tool calls, intermediate reasoning_content is ignored if passed back; but 'with tool calls, the intermediate assistant's reasoning_content must participate in the context concatenation and must be passed back to the API in all subsequent turns.' V4 reasons before each tool invocation (interleaved thinking), and the DSML encoding (a Python encode_messages() implementation, not a Jinja template — see the DeepSeek-V4 HF README's encoding folder and vLLM's V4 encode/decode implementation) re-embeds that reasoning into the prompt. On Ollama's /api/chat, thinking arrives in message.thinking and the assistant message object supports a thinking field on replay, so the harness must copy it back verbatim into the messages array for every assistant turn inside a tool loop. *Relevance:* This is the single most concrete correctness gap found: resonant_client/engine/session.py does not pass thinking back on assistant messages in the agent loop (grep shows no thinking-field handling in the transcript replay). For deepseek-v4-pro autonomous missions, dropping reasoning_content between tool calls silently degrades exactly the multi-step planning the mission flagship is chosen for — the model loses its own chain of intent each hop and re-derives plans from scratch, which shows up as flip-flopping and redundant tool calls. Fix is mechanical: store message.thinking on each assistant turn and include it on replay (harmless for GLM, whose template manages think-block retention itself via clear_thinking).
- **Design tool schemas for GLM's XML arg_key/arg_value encoding (nested objects become strings)** *(medium)* — GLM-5.2's chat template (huggingface.co/zai-org/GLM-5.2 chat_template.jinja) renders tools as JSON inside a <tools> block but has the model EMIT tool calls as XML: <tool_call>{name}<arg_key>k</arg_key><arg_value>v</arg_value>...</tool_call>, with each arg value JSON-serialized inside the XML tag. Ollama parses this with per-model parsers (model/parsers/glm46.go, glm47.go...), and for :cloud models the passthrough proxy (server/cloud_proxy.go) skips local parsers entirely. Confirmed consequence (ollama/ollama#15645, tested on glm-5.1:cloud): nested JSON objects in tool arguments arrive as JSON *strings* — {"message": {"type": "ping"}} becomes {"message": "{\"type\":\"ping\"}"} — breaking any tool whose schema expects an object-typed parameter. *Relevance:* Resonant's engine/tools.py is full of type:object/properties schemas. Two defenses: (1) keep tool parameters flat and string/number/enum-typed — avoid nested object params, oneOf/anyOf unions, and array-of-object args in every tool GLM will call; (2) add a coercion layer in the tool-dispatch path that, when a parameter typed object/array arrives as a string, attempts json.loads before validation (this also rescues the same failure from Qwen-family models per the same issue). This is cheap insurance that converts a hard tool failure into a transparent recovery, which matters double in autonomous missions where a failed dispatch burns retry budget.
- **DSML leak detector/salvage parser for DeepSeek V4 on Ollama Cloud** *(small)* — DeepSeek V4's native tool-call wire format is DSML: <|DSML|tool_calls><|DSML|invoke name="X"><|DSML|parameter name="p" string="true">value</|DSML|parameter></|DSML|invoke></|DSML|tool_calls>. On Ollama (reported against 0.24.0 for both deepseek-v4-flash:cloud and deepseek-v4-pro:cloud, ollama/ollama#16375, still open), these tokens sometimes pass through as plain assistant text instead of being parsed into tool_calls — a code search shows no 'dsml' parser anywhere in the ollama repo, and #15645's analysis confirms :cloud responses bypass local parsers, so only ollama.com's server-side parser can fix it. When the leak happens the harness sees a text-only turn, assumes the model chose not to call a tool, and the loop derails; if the transcript is replayed through an Anthropic-compat validator it can hard-fail turns later. *Relevance:* Resonant's mission flagship is exactly the affected model. A harness-side guard is straightforward: scan assistant content for '<|DSML|' (and generically for other vendors' leak signatures like Kimi's <|tool_call_begin|>); on detection either (a) regex-reconstruct the invoke/parameter structure into a proper tool call — the format is regular and the parameter 'string="true"' attribute even tells you types — or (b) strip and re-request the turn. Wire this into session.py's response handling and count leaks in telemetry so the smoke-test harness can flag when an Ollama upgrade fixes/regresses it. Without the guard, a multi-hour autonomous mission can silently stall on one leaked turn.
- **Ollama Cloud payload caps: small tool args, clamped num_predict, file indirection** *(small)* — Documented Ollama Cloud limits and bugs that bite agent loops: (1) tool_call.arguments observed truncated to exactly 214 chars on the Cloud API (ollama/ollama#15647, April 2026); (2) /api/chat on cloud rejects num_predict > 65536 for deepseek-v4-pro despite the published 384K output / 1M context spec (#16890) — which also caps Think-Max reasoning budgets since DeepSeek recommends 'at least 384K tokens' of window for Think Max; (3) waves of 500s on deepseek-v4-pro:cloud (#15832, ~70% failure rate reported in May) and recurring 503 'server overloaded' storms across cloud models (#15419, #15453). *Relevance:* Resonant already has the adaptive concurrency governor + circuit breaker for 403s in backends.py; extend its trip conditions to 500/503 bursts on the v4 endpoints. More structurally: never design tools that expect large payloads inside tool-call arguments (e.g. write_file with full content as an arg is a truncation hazard on cloud) — prefer indirection where the model writes large content via multiple smaller edits or the harness fetches content from the model's plain-text output; validate argument JSON completeness (balanced braces) before dispatch and treat truncation as a retryable model error, not a tool error. Clamp num_predict to <=65536 for deepseek-v4-pro:cloud until #16890 is fixed rather than letting requests 400.
- **Prefix-stability discipline for KV/prompt cache (local and cloud)** *(medium)* — DeepSeek's own API caches by 'cache prefix units' created at request boundaries — a later request only hits cache if it fully matches a persisted prefix unit, and hits/misses are surfaced as prompt_cache_hit_tokens/prompt_cache_miss_tokens (api-docs.deepseek.com/guides/kv_cache). Ollama Cloud, by contrast, does not surface any cache metrics; a maintainer says caching exists server-side but users benchmarking OpenCode+glm-5.1 report no measurable prefix-cache benefit (ollama/ollama#16714) — so assume every cloud turn reprocesses the full prompt. Local Ollama's KV cache is prefix-exact per loaded model: any byte change early in the prompt (system prompt, tool list order, injected timestamps) forces full re-prefill, and changing num_ctx reloads the model. *Relevance:* With 1M-context models and no vendor-billed caching, prompt-prefill time is Resonant's real latency currency, especially on the Mac Studio for local models. Rules to enforce in session.py/harness: append-only transcripts (never rewrite earlier turns mid-session); keep system prompt and tool-definition JSON byte-stable and identically ordered across turns (no timestamps/dynamic counters in the system prompt — put volatile context in the latest user message); pin num_ctx per model. One GLM-specific wrinkle: the GLM-5.2 template's clear_thinking behavior strips old <think> blocks from history — deciding once whether Resonant retains or strips thinking, and doing it consistently, avoids prefix churn between turns. On glm-5.2:cloud, where responses are already slow (#16779), avoiding prompt rewrites is the cheapest speedup available.
- **Use vendor sampling defaults: temp 1.0 / top_p 0.95-1.0, and don't fight thinking mode** *(small)* — GLM-5.2's model card benchmarks run at temperature=1.0 with top_p=0.95 for reasoning tasks (max generation 163,840 tokens) and temp=1.0/top_p=1.0 elsewhere; Z.ai API examples use temperature 1.0 (0.6 shown for one streaming example). DeepSeek V4's HF README recommends temperature=1.0, top_p=1.0, and DeepSeek's API explicitly does NOT support temperature/top_p/presence_penalty/frequency_penalty in thinking mode — they're ignored or rejected. Both model lines were RL-trained at these settings; the old 'temperature 0.0-0.2 for coding' folklore predates reasoning-mode models and measurably hurts them. *Relevance:* Ollama's server-side defaults (temperature 0.8, top_p 0.9 historically, plus whatever a model's Modelfile bakes in) match neither vendor recommendation, and cloud tags may or may not carry correct params. Resonant should pin per-model sampling in backends.py's options dict: glm-5.2 -> temp 1.0/top_p 0.95, deepseek-v4-pro -> temp 1.0/top_p 1.0 (or omit sampling params entirely when thinking is on, matching DeepSeek's API contract). Weaker open models are more sensitive to off-distribution sampling than frontier closed models — wrong temperature shows up directly as malformed tool-call XML/DSML and edit-format failures, which Resonant pays for in retries.
- **Explicit context-length plumbing (num_ctx) per model on Ollama** *(small)* — GLM-5.2 ships a 'truly usable' 1M window (976K as exposed by ollama.com's glm-5.2:cloud tag; 128K max output), and DeepSeek V4 supports 1M with >=384K recommended for Think Max. But on Ollama, context is opt-in: local models default to a small num_ctx (a default of 4096 is the confirmed root cause of the glm-ocr crash in ollama/ollama#16696), and 'ollama create' does not inherit model_info from the parent model, so Modelfile-derived variants silently lose their context_length metadata (#16891). Cloud models enforce their own caps server-side regardless of what the client requests (see the num_predict cap in #16890). *Relevance:* Resonant already passes num_ctx in options (backends.py line ~1250), but the guidance is: (1) query /api/show per model at backend init and log the effective context_length rather than trusting tag documentation — especially for any custom Modelfile variants Resonant creates, which per #16891 lose the metadata; (2) size the harness's compaction threshold (autonomous_loop.py) off the queried value, not a constant; (3) for local models on the Mac Studio, remember KV cache for huge num_ctx eats unified memory — 200K+ contexts on a local GLM quant can evict the model or thrash, so the interactive default should be the largest num_ctx that keeps the model resident, with mission runs opting into bigger windows deliberately.
- **Benchmark-calibrated expectations: edit formats, retry budgets, and harness choice** *(small)* — Verified vs self-reported numbers diverge sharply for these models. Terminal-bench 2.1 (human-verified, tbench.ai): Codex CLI+GPT-5.5 83.4%, Claude Code+Claude 5 Fable 83.1%; the best verified open entry is Claude Code+GLM-5.1 at 58.7% (rank 13); no verified DeepSeek V4 entry exists yet. Zhipu self-reports GLM-5.2 at 81.0 TB2.1 and 62.1 SWE-bench Pro; DeepSeek self-reports V4-Pro-Max at 80.6% SWE-bench Verified and 67.9% Terminal-Bench 2.0. Aider's polyglot leaderboard (no GLM-5.x or V4 entries yet) shows the DeepSeek line achieving 97.3% correct-diff-edit-format adherence (V3.2-Exp reasoner, 74.2% solve) — strong evidence the family handles search/replace-diff editing natively. DeepSeek also offers strict function-calling (beta, base_url api.deepseek.com/beta, strict:true, closed JSON-schema subset: all properties required, additionalProperties:false, no minLength/maxItems) — not available through Ollama, but it defines the schema subset the model was aligned to. *Relevance:* Three practical consequences. (1) Expect a real 15-25 point gap between vendor marketing and what GLM-5.2/V4 deliver inside a harness — Resonant's acceptance checks, retry budgets, and grill_me spec-refinement are not optional polish, they're the mechanism that closes that gap, so keep investing there rather than assuming the model 'just works'. (2) Diff-style edits are in-distribution for DeepSeek (97.3% adherence) — if Resonant's edit tooling offers exact-string-replace or unified-diff edits, prefer those over whole-file rewrites for v4 missions (also cheaper against the cloud num_predict cap). (3) Keep tool JSON schemas inside DeepSeek's strict-mode subset (flat, all-required, no additionalProperties, no length/item constraints) so the same tools.py definitions are maximally in-distribution for both the Ollama path and any future direct-API path.

### cross-cutting

By mid-2026 a consensus harness architecture has emerged across Claude Code, Amp, Cline, OpenCode, Cursor, Devin and Manus, and it is model-agnostic: (1) context is managed in layers — hard truncation of tool results at ingest, eviction of stale tool outputs when nearing the limit, then LLM summarization as a last resort — because performance degrades as context fills and summarization is lossy; (2) code retrieval has shifted from vector RAG to agentic search (ripgrep/glob + follow-the-imports, optionally a tree-sitter repo map), with embeddings surviving only as a supplement in very large repos (Cursor's data: +12.5% answer accuracy, but they still run grep heavily); (3) every edit is followed by a machine check — LSP/linter diagnostics injected into the next turn, auto-run tests, or accessibility-tree browser snapshots — so the loop closes on pass/fail signals instead of 'looks done'; (4) parallelism happens at the git-worktree/session level, not inside one task (Cognition's rule: parallel subagents making decisions without shared context produce conflicting work); (5) execution is moving into lightweight OS sandboxes (Seatbelt on macOS, bubblewrap+seccomp on Linux) with default-deny network via proxy allowlists; (6) for self-hosted serving, KV-cache prefix stability is the top economic lever — Manus calls KV hit rate 'the most important metric of a production agent' — which for Ollama means a byte-stable system-prompt prefix, append-only history, deterministic tool-result serialization, keep_alive=-1, and awareness that compaction rewrites invalidate the cache; (7) subagents return schema-constrained structured results (Ollama's format parameter grammar-constrains decoding), which doubles as the mitigation for flaky tool-calling on open models; and (8) a visible todo/plan that the agent re-recites into recent context is used deliberately as an attention-steering device against goal drift on ~50+ tool-call tasks. Resonant already has several partial versions of these (compression.py compaction, head/tail truncation, lint/test feedback caches, acceptance checks, plan graphs, CDP browser), so most adoptions are refinements rather than new subsystems; the highest-leverage, lowest-cost items are the KV-cache prefix discipline, structured subagent outputs, offset-windowed file reads, and plan recitation.

**Notable features:**

- **Layered context compaction: evict tool results first, summarize last** *(medium)* — The now-standard pipeline has three escalating layers. Layer 1: at ingest, every tool result is truncated (Resonant already does head-truncate for file reads, tail-truncate for shell output). Layer 2: when approaching the context limit, the harness clears/evicts the *content* of old tool results deep in history (replacing them with a stub like '[output cleared]') while keeping the assistant/user turns intact — Anthropic's context-editing beta does exactly this and reports an 84% token reduction on a 100-turn eval and +29% task performance from eviction alone, because agents rarely re-read raw outputs they already acted on. Layer 3: only if still over budget, an LLM pass summarizes the oldest span of conversation into a compressed note preserving 'architectural decisions, unresolved bugs, and implementation details', and the session reinitializes with that summary. Claude Code documents this exact ordering: 'It clears older tool outputs first, then summarizes the conversation if needed', plus user-tunable compact instructions ('always preserve the full list of modified files and test commands'). A complementary rule from Manus: keep failed actions and error messages in context rather than cleaning them up — error recovery evidence measurably improves subsequent behavior. *Relevance:* Resonant's compression.py already does summary-based compaction, but summarization by GLM-5.2/DeepSeek is the lossiest and most expensive option — open models write worse summaries than frontier models, so every avoided summarization pass directly preserves mission reliability. Inserting the eviction layer (clear old tool-result bodies, keep the last N turns' results verbatim) before compress() fires would cut most compactions entirely. One Ollama-specific tradeoff to encode: eviction/summarization rewrites history and therefore invalidates the local KV-cache prefix (see the KV feature), so it should trigger in large batched steps at high-water marks, not incrementally every turn.
- **File-read offset/limit windows and pagination-aware tool results** *(small)* — Instead of returning a whole file (or its head-truncation), the read tool takes offset+limit parameters (Claude Code: default 2000 lines, cat -n numbered so the model can cite and edit by line) and the truncation footer explicitly tells the model how to get the rest ('showing lines 1-400 of 3200; re-call with offset=400'). Same pattern for grep (head_limit/offset) and shell output. The key design point is that truncation messages are *actionable*: they name the exact tool call that retrieves the next window, so the model pages through large artifacts instead of losing data silently. This pairs with Anthropic's 'just-in-time context' principle: keep lightweight identifiers (paths, line ranges) in context and re-fetch on demand rather than holding full contents. *Relevance:* Resonant's tools.py has truncate_head/truncate_tail with footers but no offset parameter on file reads — so when GLM-5.2 needs the middle of a large file it simply can't get there, and it either re-reads the head repeatedly or gives up. Open models are worse than frontier models at inventing workarounds (e.g. spontaneously running sed -n '400,600p'), so the harness must make paging a first-class, schema-documented parameter. This is a contained change to read_file/grep in tools.py plus footer text that spells out the follow-up call.
- **Agentic search as primary code retrieval; vector RAG demoted to supplement** *(medium)* — The industry moved from embed-the-repo RAG to letting the agent search like a developer: ripgrep for content, glob for files, then read-and-follow-imports, iterating queries based on what it finds. Cline's writeup gives the canonical argument: chunking 'literally tears apart' code logic, indexes go stale against a moving repo, and embeddings create a second copy of proprietary code to secure. Claude Code ships no index at all — pure Grep/Glob/Read agentic search. Amp likewise uses agentic search tools, not embeddings. Aider adds the middle ground worth copying: a tree-sitter 'repo map' — parse files into symbols, build a dependency graph (file nodes, import/reference edges), PageRank it, and emit the top signatures within a fixed token budget (default 1k tokens) as orientation context. Cursor is the honest counterpoint: their A/B tests show semantic search still adds ~12.5% answer accuracy (6.5–23.5% by model), mainly on 1,000+-file repos — but even they run 'heavy use of grep' alongside it. Consensus: grep-first, embeddings optional. *Relevance:* Resonant carries rag.py; the question is whether it earns its complexity. For the repo sizes a solo daily-driver tool targets, a fast ripgrep tool + a tree-sitter repo map injected at session start will beat a stale vector index, and it removes an embedding pipeline that costs Mac Studio memory alongside the LLM. Open models benefit disproportionately from the repo map specifically: GLM-5.2 is weaker at blind exploration strategy than Claude, and a 1k-token oriented symbol map reduces the number of exploratory tool calls it must plan itself. Keep rag.py as an optional supplement for natural-language 'where do we handle X' queries on big repos, mirroring Cursor's hybrid.
- **Post-edit diagnostics injection (LSP/linter feedback loop)** *(medium)* — After every file edit, the harness collects machine feedback and injects it into the next model turn as part of the tool result: OpenCode auto-downloads and starts LSP servers keyed on file extension and feeds language-server diagnostics to the agent so it 'can find and fix issues'; Claude Code exposes the same via code-intelligence plugins ('see type errors and warnings after edits') and recommends hooks that run eslint/typecheckers after each edit deterministically. The mechanics: keep a per-file fingerprint of last-reported diagnostics, run the checker (LSP pull-diagnostics or a fast CLI linter like ruff/pyright/tsc --noEmit) after Edit/Write, diff against the fingerprint, and append only *new* diagnostics to the tool result so the model fixes its own type errors immediately instead of discovering them at test time — and so repeated identical warnings don't spam context. *Relevance:* Resonant's session.py already has _lint_feedback_cache and _test_feedback_cache with fingerprinting — the architecture is in place. The upgrade path is breadth (pyright/tsc, not just a linter) and latency (run checks synchronously inside the edit tool result rather than later). This is one of the highest-ROI loops for open models: GLM-5.2 and DeepSeek make more small syntax/type errors than frontier models, and immediate deterministic feedback converts those from mission-failing drift into single-turn self-corrections without burning acceptance-check retries. Full LSP client integration is the 'large' version; extending the existing CLI-checker loop is medium.
- **Verification as a stop-gate: checks that block 'done', plus fresh-context adversarial review** *(small)* — Claude Code's best-practices doc formalizes an escalation ladder for verification: (1) in-prompt ('run the tests and iterate'), (2) a goal condition an evaluator re-checks after every turn, (3) a deterministic Stop hook — a script that runs the check and *blocks the turn from ending* until it passes (with an escape valve after 8 consecutive blocks to prevent infinite loops), and (4) an adversarial reviewer subagent that sees only the diff and the criteria in a fresh context — 'the agent doing the work isn't the one grading it', and a fresh context 'won't be biased toward code it just wrote'. Two hygiene rules attach: require the agent to show evidence (test output, command + result, screenshot) rather than asserting success; and instruct reviewers to report only correctness gaps, because a reviewer asked for findings will always produce some, driving over-engineering. *Relevance:* Resonant already has acceptance_check.py and retry budgets for missions — the missing pieces are (a) the deterministic stop-gate form (a script/exit-code gate the model cannot talk its way past, crucial because open models are more prone to declaring success prematurely and to ignoring soft instructions), (b) the loop-breaker counter so a flaky check doesn't eat the whole retry budget, and (c) a fresh-context reviewer pass wired into the orchestrator: spin a clean session that gets only git diff output + the mission spec and returns structured gaps. Since specialists.py and the harness orchestrator exist, this is mostly wiring, and it converts autonomous missions from 'trust DeepSeek's self-report' to 'trust an exit code'.
- **Browser verification via accessibility-tree snapshots, screenshots as secondary** *(medium)* — Playwright MCP established the pattern now copied broadly: instead of screenshots + vision, the browser tool returns an accessibility-tree snapshot — a structured text representation of the page with roles, names, and stable element references (uids) that subsequent click/fill calls target directly. Microsoft's stated rationale: 'LLM-friendly, no vision models needed, operates purely on structured data' and 'deterministic tool application, avoids ambiguity common with screenshot-based approaches'. Screenshots remain in the toolkit but for visual verification only (compare against a design mock, confirm layout), not for element targeting. Claude Code's UI-verification recipe layers on top: paste/serve the target design, implement, screenshot the result, ask the model to list differences, and iterate until they converge. *Relevance:* Resonant's browser.py drives real Chrome over CDP — CDP exposes the accessibility tree directly (Accessibility.getFullAXTree / DOMSnapshot), so adding a snapshot tool that returns role/name/uid nodes and letting click/type take uids is a natural extension. This matters doubly for open models: GLM-5.2's vision-free operation on structured text is far more reliable than coordinate-guessing from screenshots, and snapshot text is dramatically cheaper in tokens than base64 images on a local context budget. Keep the existing screenshot path for the post-build GUI verification pass (per your own post-build E2E memory), but make snapshots the default interaction substrate.
- **Parallel agent sessions via git worktrees (parallelize tasks, not decisions)** *(medium)* — The standard mechanism for running multiple agents on one repo: git worktree add creates additional working directories sharing one .git store, each on its own branch, so N agent sessions edit files without colliding; the harness creates/cleans worktrees per task and merges results via normal git. Claude Code documents this as the primary parallelism pattern (separate CLI sessions in isolated checkouts; the desktop app auto-manages one worktree per session), plus quality patterns it enables: Writer/Reviewer split across two sessions, and one session writing tests while another implements. Cognition's 'Don't Build Multi-Agents' supplies the guardrail that shapes everyone's designs: actions carry implicit decisions, and parallel subagents that can't see each other's full traces make conflicting decisions — so parallelize *independent tasks* (different files/features, investigations that return summaries), never split one coherent design task across concurrent agents. *Relevance:* Resonant's autonomous missions (autonomous_loop.py, plan_graph.py) currently execute plan nodes serially in one checkout. Worktree-per-mission-node gives three wins: parallel node execution on independent subtrees of the plan graph, crash isolation (a bad mission can be discarded by deleting the worktree instead of resetting the user's checkout), and clean diff-scoped review for the acceptance checker. git_tools.py already exists to build on. The Cognition guardrail maps directly onto the plan graph: only fan out nodes with no shared decision surface, and have the walker serialize anything touching shared files. Note the local constraint: parallel sessions multiply concurrent Ollama load, so the concurrency governor in backends.py should cap fan-out.
- **Lightweight OS-level sandboxing with default-deny network (no containers)** *(large)* — The 2025-26 trend is away from Docker toward native OS primitives that sandbox individual agent commands with near-zero overhead. Anthropic's open-source sandbox-runtime (srt) is the reference implementation: on macOS it wraps processes in sandbox-exec with dynamically generated Seatbelt profiles (allowed read/write paths, allowed localhost proxy ports); on Linux it uses bubblewrap plus seccomp BPF filters and removes the network namespace entirely. Filesystem policy is asymmetric: reads default-allow with deny-lists, writes default-deny with explicit allowWrite paths, and sensitive files (.bashrc, .gitconfig, .vscode/) are always write-blocked. All network egress is forced through host-side HTTP/SOCKS5 proxies that enforce a domain allowlist — default-deny, explicitly allow domains. Claude Code exposes this as /sandbox, positioned as the thing that lets you *reduce* permission prompts safely: the agent works freely inside hard boundaries instead of asking per-command. *Relevance:* Resonant runs long unattended missions where DeepSeek executes arbitrary shell commands — currently with the user's full account privileges on the host. Open models are more susceptible to prompt-injection-driven and plain-confused destructive commands, and missions run while the user is away, so hard OS boundaries matter more for Resonant than for a watched interactive session. Practical path: wrap the shell tool's subprocess in a policy (write-allow = mission worktree + scratchpad; network-allow = 10.0.0.133:11434, ollama.com, and per-mission domains). The catch: Resonant's daily-driver host here is Windows, where no Seatbelt/bwrap equivalent exists (srt supports macOS/Linux only) — so this lands as a per-platform feature (full enforcement on the Mac Studio side, restricted-token/AppContainer or WSL-based best-effort on Windows), which is why it rates large.
- **KV-cache-first prompt discipline for self-hosted serving (static prefix, append-only, deterministic serialization)** *(small)* — Manus's context-engineering post names KV-cache hit rate 'the single most important metric for a production-stage AI agent' — in an agent loop the context grows ~100:1 input:output, so prefill dominates cost/latency, and cached prefix tokens are ~10x cheaper hosted (or near-free locally). The rules: (1) keep the prompt prefix byte-stable — 'even a single-token difference can invalidate the cache', so no timestamps, no per-request IDs, no reordered tool lists in the system prompt; (2) make history append-only — never edit or reorder past messages mid-session; (3) serialize tool results deterministically (stable JSON key order, stable formatting templates), since nondeterministic serialization silently breaks the prefix; (4) never add/remove tool definitions mid-session — mask unavailable tools at decode time instead, because tool schemas sit at the very front of the context. Server-side, vLLM's automatic prefix caching and SGLang's RadixAttention (radix-tree KV reuse, up to 5x throughput, biggest wins on time-to-first-token) reward exactly this discipline. Ollama's runner does longest-common-prefix KV reuse across requests within a loaded model (kvcache CanResume/prefix matching; llama.cpp slot cache underneath): each new request reuses cached KV up to the first divergent token and reprocesses from there. *Relevance:* This is the single biggest perf lever available to Resonant and it costs almost nothing. There is no vendor cache billing on Ollama — the KV cache *is* the local Mac Studio GPU doing or skipping a full re-prefill of a 50k-token conversation every agent step. Concretely: audit that the system prompt (including skills text injected by the skills system) is byte-identical across steps of a session; sort JSON keys in tool-result serialization; never mutate history except at explicit compaction points (each compaction is a deliberate full-cache-invalidation event — batch it); set keep_alive=-1 so the model (and its KV state) isn't unloaded between steps; and be aware OLLAMA_NUM_PARALLEL slot assignment can miss the cached slot, so interactive-session traffic should avoid interleaving unrelated requests on the same model. For glm-5.2:cloud requests the same discipline maximizes ollama.com-side prefix caching and reduces the long-prompt latency that currently trips the concurrency governor. Also note OLLAMA_KV_CACHE_TYPE=q8_0 roughly halves KV memory, buying longer usable num_ctx for missions.
- **Schema-constrained structured outputs for subagent results, intent parsing, and acceptance verdicts** *(small)* — Two converging practices. (a) Orchestration side: Anthropic's multi-agent research system has subagents do tens of thousands of tokens of work but return only 'a condensed, distilled summary (often 1,000-2,000 tokens)' to the lead, and found delegation only works when the task spec includes 'an objective, an output format, guidance on tools/sources, and clear task boundaries'; Claude Code's SDK equivalent is a structured-output tool the subagent must call with a JSON-schema-validated result (retry on validation error). (b) Decoding side: Ollama's structured outputs take a JSON schema in the format parameter and constrain generation grammar-style so output *cannot* violate the schema — 'more reliability and consistency than JSON mode' — recommended with temperature 0 and Pydantic-defined schemas. Combined, the parent agent never parses freeform prose from a child: the schema is enforced at token level and validated at ingestion. *Relevance:* This directly attacks Resonant's stated pain point — flaky tool-calling and weaker instruction-following on open models. Anywhere Resonant currently asks GLM-5.2/DeepSeek to 'respond with JSON' (specialist results in specialists.py, intent_service.py classification, acceptance_check.py verdicts, grill_me.py spec extraction, skill_extraction.py), switching to the Ollama format parameter makes malformed output structurally impossible rather than merely discouraged. It also standardizes the subagent contract: every specialist returns {status, summary, files_touched, evidence, gaps} so the orchestrator and plan-graph walker consume machine-checkable results. Caveat worth encoding: constrained decoding can slightly degrade reasoning quality, so the pattern is 'reason freely in the transcript, then emit the final answer via one schema-constrained call' — which the specialist runner can enforce as a final step.
- **Todo/plan recitation as an attention-steering mechanism** *(small)* — Manus discovered that on tasks averaging ~50 tool calls, agents drift off-goal because the original objective is buried at the far end of a long context; their fix is deliberate 'recitation' — the agent maintains a todo.md and rewrites it as steps complete, which pushes 'the global plan into the model's recent attention span' at the *end* of context every few turns, exploiting recency bias to fight lost-in-the-middle degradation. Claude Code's TodoWrite tool is the same mechanism productized: a structured todo list the model updates as it works (statuses pending/in_progress/completed), rendered back into context and doubling as user-visible progress UI. Anthropic's context-engineering guidance generalizes it as 'structured note-taking': persist plans/notes outside the context window and re-inject them, so they also survive compaction — the note file is re-read after a summarization event to restore goal state losslessly. *Relevance:* Resonant has plan graphs for missions but (per the code) no in-session todo recitation for the interactive agent. Open models drift more and earlier than frontier models — this is the cheapest known countermeasure, pure prompting mechanics with no model requirements. Concrete adoption: give the interactive session a todo tool whose current state is re-rendered near the end of the prompt each turn; for autonomous missions, have the walker inject 'current node, acceptance criteria, remaining nodes' as the last context block on every step; and make compression.py always carry the todo/plan state verbatim (never summarized) across compaction. One interaction to respect: appending an updated todo block each turn is KV-cache-friendly, but rewriting it in place mid-history is not — recite at the tail, don't edit the middle.
