## TL;DR — surprising upset: flash beats pro for autonomous

**Flash converged on the first iteration and produced clean working code.
Pro consistently failed to write any code across two independent runs**,
both ending with `stop_reason=stuck` and `wordcount.py` never created.

This is the **opposite of what `RESONANT.md` currently claims** ("use pro
for multi-specialist work where the planner / evaluator role benefits
from more deliberation"). For the autonomous-mission workload
specifically, **flash is the right default tier**.

Update RESONANT.md before GA. See §6 below for proposed wording.

## 2. Flash performance — solid

Flash dispatched the implementer specialist, which spent 4.5 minutes
producing a clean 25-line `wordcount.py`:

```python
#!/usr/bin/env python3
"""Count lines, words, and characters in a file (like wc -l -w -c)."""

import argparse


def main() -> None:
    parser = argparse.ArgumentParser(
        description="Count lines, words, and characters in a file."
    )
    parser.add_argument("file", help="Path to the input file")
    args = parser.parse_args()

    with open(args.file, encoding="utf-8", errors="replace") as f:
        content = f.read()

    lines = content.count("\n")
    words = len(content.split())
    chars = len(content.encode("utf-8"))

    print(f"{lines:>6}{words:>6}{chars:>6} {args.file}")


if __name__ == "__main__":
    main()
```

**Quality observations:**
- Followed the stdlib-only constraint
- Used argparse correctly
- Handled UTF-8 encoding explicitly
- Used `errors="replace"` defensively
- Output format mirrors `wc` (right-justified columns)
- Has a docstring + main() guard

This would pass a code review. Flash followed the planner → implementer
→ verifier flow as designed; the autonomous loop converged on iter 1's
first reflect pass.

REFLECT correctly identified the `wc` failure as environmental
(passed-bash 3, failed-bash 1) and **didn't add a fix-it item** — there's
no code change that would make `wc` available on Windows cmd.exe, so
"stuck" is the right outcome (manual intervention needed: change shell,
fix spec, etc.).

## 3. Pro performance — deterministic failure

**Both runs ended identically: no file created, 1/4 acceptance.** The
only difference was wall-clock (40s vs 435s) and the specific path the
planner took before giving up.

### What pro actually did (audit log, run 2)

```jsonl
intent started
dispatched specialist (plan)
tool_call (×2)        ← planner explored with read-only tools
plan_change: "The goal is cut off — I can't tell what the utility should do beyond its name..."
plan_change (no payload)
dispatched specialist (probably explore)
tool_call (×7)        ← more exploration
plan_change: "Exploration Results / Relevant Files / ..."
dispatched specialist
plan_change: <tool_call name="glob">...</tool_call>   ← emitted as TEXT, not invoked
dispatched specialist
plan_change: <tool_call> <tool_call name="glob">...   ← nested tool_call as text
plan complete (1 node, all_done=true)
```

### Diagnosis

Pro's planner specialist consistently misinterprets its role. It's
supposed to emit a JSON envelope of the form:

```json
{"subgoals": [
    {"goal": "...", "specialization": "implement"},
    {"goal": "...", "specialization": "verify", "depends_on": [0]}
]}
```

Instead, pro emits **textual `<tool_call>` blocks** as if it were the
implementer trying to call tools directly. The walker can't parse a
plan from this output, so it accepts it with confidence=0.5 and marks
the plan-graph "complete" with just 1 node — no implementer ever runs.

This is a **classic instruction-following failure** specific to pro's
deliberation style. Pro reads the prompt's tool list (READ_ONLY_TOOLS +
await_user) and tries to USE the tools rather than PLAN with them as
context. Flash, being snappier, just emits the JSON envelope as
instructed.

### Why both runs failed the same way

If this were random model variance, we'd expect at least one of the two
runs to stumble into success. Both failing identically (with very
different durations, no less) suggests this is a **systematic
prompt-comprehension issue** — not transient.

The PLAN specialist's prompt (in `orchestration/specialists.py`) is
quite explicit:

> You are a PLANNER. Your ONLY output is a JSON plan. You do NOT
> implement, write files, run shell commands, or edit anything — those
> tools are not available to you.

But the tool allowlist DOES include `READ_ONLY_TOOLS | _AWAIT_USER`,
which is for "reading code first if needed before planning." Pro reads
that and decides to do extensive reading INSTEAD of planning.

## 4. Other findings worth flagging

### 4.1 Title truncation in `_seed_item_from_intent`

Pro's first plan_change said "The goal is cut off — I can't tell what
the utility should do beyond its name." That's a real bug:

```python
first_sentence = intent.split(".", 1)[0].strip()
```

For `intent = "Build a Python CLI utility `wordcount.py` at the
project root."`, `split(".", 1)[0]` cuts at the **first period — inside
the filename**, giving title = `"Build a Python CLI utility `wordcount"`.

The full intent IS in the description, and `dispatch_item` includes
both. But pro's planner clearly fixated on the title. Worth fixing —
should split on a sentence boundary that respects code-block / filename
context. Filed as v0.5.1 candidate.

### 4.2 Bash criterion env portability

`wc`, `find`, `grep -E` are not portable to `cmd.exe`. The smoke harness
should either:
- Force `bash` shell on Windows (e.g. detect Git Bash and use it)
- Document criterion-authoring rules ("use Python or stdlib commands")
- Or retry `wc`-style criteria via Git Bash on shell=True failure

Pre-existing issue; the smoke surfaced it loudly. v0.5.1 candidate.

### 4.3 Walker's permissive plan parsing

The walker accepted pro's malformed `<tool_call>`-as-text output with
confidence=0.5 and marked the graph complete. Better behavior: if the
planner doesn't emit a parseable subgoals JSON, retry once with a
"please emit JSON" reminder, then escalate to await_user or fail loudly.
The current "accept and silently no-op" failure mode is invisible to
the user — they just see "stuck" with no obvious cause.

This is a real product risk for v0.5.0 GA. A user who picks pro for
their first autonomous mission will see a 7-minute "running…" spinner
followed by "stuck" with no diagnostic surface. Filed as **GA blocker
for tier guidance: tell users to use flash, OR fix the planner-output
loud-failure path before GA.**

### 4.4 Ollama 503s never fired in this round

Both flash + pro completed without retry-layer activation. Either
Ollama Cloud is less loaded right now (after-hours?), or the v0.5.0a9
retry layer is silently absorbing them and we're not seeing the
warning logs in this output. Either way: no negative signal on the
retry layer.

## 7. Open questions / v0.5.1 backlog

1. **Why does pro misbehave on the planner role?** Tightening the
   planner's prompt (`Your ONLY output is a JSON plan. Tools are
   available for context-gathering ONLY; do NOT use them to do work.`)
   may fix it. Worth a focused prompt-tuning pass.
2. **Should the walker retry on unparseable planner output?** Currently
   it accepts confidence=0.5 and moves on. A "I need a JSON envelope,
   please retry" reminder would be cheap and might rescue pro.
3. **Title truncation in `_seed_item_from_intent`** — split on first
   period breaks for filenames. Use sentence-boundary detection or just
   take the first 80 chars of the description.
4. **Cross-platform criterion validation** — `wc`/`find`/`grep` aren't
   on `cmd.exe`. Either force bash on Windows or document the
   constraint in the rigorous-grill prompt.
5. **More smoke runs per model** — N=1 for flash and N=2 for pro is
   small. A v0.5.1 smoke pass with N=5 each would tighten the
   confidence interval on these findings.
6. **What does pro's grill phase look like?** This smoke skipped the
   grill. Pro's deliberation might be GREAT for the grill (more
   thorough questions) and only bad for the planner. Worth a separate
   grill-only run before deciding pro is "not recommended" overall.
