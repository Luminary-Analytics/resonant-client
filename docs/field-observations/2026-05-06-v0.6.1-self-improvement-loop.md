## Findings (ranked by severity)

### F1 — Trivial-mission bypass: extractor/curator never fire (HIGH)

The v0.6.0+v0.6.1 hooks (`extract_skill_hook` + `queue_curation_hook`)
fire from `_run_full_reflect` and `_emit_stop` in
`gui/autonomous_loop.py`. Both run **only when the mission enters the
formal autonomous-iter loop**.

When the grill agent recognizes a prompt as "concrete executable
instruction, not a feature to grill on" (rigorous-grill skill behavior),
it self-executes during drafting via direct tool calls and **never
transitions to the iter loop**. The mission state stays "drafting" —
permanently, in mission 1's case.

**Consequence:** The simplest, most successful missions — the ones
where the agent immediately knows what to do — produce **zero** skill
captures. The self-improvement loop only ever sees missions that
required grilling, which is the wrong selection bias.

**Fix candidates:**
- (A) Have the grill agent emit a synthetic single-iter result when it
  self-executes during drafting. Run `_run_full_reflect` on that single
  iter so hooks fire normally.
- (B) Add a separate "trivial-mission completed" code path in
  `autonomous_loop.py` that calls the hooks directly with a synthesized
  IterContext.
- (C) Add an explicit `extract_skill_from_drafting_completion` hook in
  the grill agent's "I'll just do it" branch.

A is closest to existing semantics. B is simplest. C duplicates work.
Recommend A.

### F2 — Cloud rate-limit stalls have no clear UX recovery (HIGH)

When `deepseek-v4-flash:cloud` 503s exhaust retry budget (4 attempts),
the iter halts. The status banner shows "Backend rate-limited (HTTP
503) — retrying" but **disappears** after retries succeed-or-give-up.
After that, the chat is silent. The user cannot tell if the agent is
thinking, retrying, or stalled.

Daemon stdout has the truth (`ERROR: Ollama 503 on /api/chat (model=…)
…`) but the GUI only shows the transient banner.

**Fix candidates:**
- Persistent error chip on the iter card when retry budget exhausts
- Auto-promote a stall to a visible chat message ("backend is slow,
  considering switch to {alt-model}?")
- Surface daemon stderr in a collapsed panel under the chat

### F3 — Skill names from prior runs are unreadable (MEDIUM)

Currently in `~/.resonant/skills/global/`:
- `actually-create-wordcountpy-with-word-counting-logic-the-fil`
- `add-a-contributingmd-to-this-project-with-three-sections-set`
- `bootstrap-a-typescript-roguelite-skeleton-with-strict-tsc-a`
- `build-a-python-cli-utility-wordcount-build-a-python-cli-util`
- `build-a-python-cli-utility-wordcountpy-at-the-project-root-b`
- `create-a-file-called-hello-create-a-file-called-hellotxt-at`

Naive `slugify(intent)[:60]` produces mid-word truncations + redundant
prefixes ("create-a-…", "build-a-…", "bootstrap-a-…"). They sort
alphabetically into clumps because the head is duplicated. Hard to
match by eye. Hard to scan in `resonant-skill list`.

**Fix:** Word-boundary truncation at ~30 chars + drop common verb-noun
prefixes. Optionally have the extractor model emit a short name
directly. Owned by **v0.6.2a2**.

### F4 — No GUI surface for skills (MEDIUM)

8 skills exist on disk, 2 are bundled+pinned, but nothing in the GUI
shows them. The user has no way to inspect skill captures, pin a hot
one, or archive a stale one without dropping to CLI.

Owned by **v0.6.2a3**.

### F5 — Drafting phase progress is opaque (LOW)

Mission 2 sat in "drafting" for 90+s with the daemon hammering 503s.
The GUI showed only:
- "Drafting" badge (static)
- Brief banner appearance + disappearance
- Empty chat panel

No "model thinking" indicator, no token-stream pulse, no retry counter
in the chat itself.

**Fix candidate:** thinking-spinner or token-counter in the chat
header during long drafting waits. Probably v0.6.3+.
