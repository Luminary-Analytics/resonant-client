# Resonant: live user evaluation, 2026-09-05

## Method and scope

Ran the updated source GUI in Chrome on Windows, using the normal project picker,
composer, run details, status control, and preview. Builds run in separate empty
directories under `D:/Repos/resonant-e2e-20260905-1030`, outside Resonant's source.
The evaluator did not write application code into those projects. Independent
checks and captured session ledgers live in the sibling `evidence` directory.

The configured Ollama (`10.0.0.131:11434`) and EXO (`10.0.0.131:52415`) endpoints
timed out. The GUI selected the configured Kimi API route, `kimi-k3`, and the
live builds use that route. These results are not evidence for local inference
speed, smaller/quantized models, or parity across providers. Existing global
skills were left enabled to evaluate the actual installed experience.

One run per project is a diagnostic sample, not a benchmark with statistical
confidence. Timings come from persisted runtime events. Independent acceptance
checks are distinct from tests generated by the agent itself.

**Simple CLI:** The first implementation mishandled CRLF character counts. The
agent independently corrected this before completing, added a regression check,
and passed the evaluator's separate file/stdin cases. No corrective feedback was
needed. The evaluator clicked “Check status” once; this queued a status request in
the active run. Actual tool execution totaled about 11 seconds of the 297-second
turn; the remainder includes model generation, provider latency, and loop overhead,
not just idle waiting. The finished session restored correctly after refresh.

**Task board:** The initial preview served the page at about six minutes, then
died with its launch command. After repeated launch failures, the evaluator used
Queue follow-up → Steer to stop further detached-launch variations, started a
separate preview, and explicitly told the agent who owned that process. Those two
steering messages and the manual server are assistance included in the elapsed
time above. No application code was written by the evaluator.

The agent eventually used its browser tools, corrected a pluralization defect
itself, and accurately attributed the server assistance. Its final answer also
admitted it had not visually checked a phone viewport or physically tested Tab
navigation. The evaluator independently exercised add by Enter/button, blank add
and edit validation, Enter/Escape editing, complete/reactivate, all three filters,
case-insensitive search, delete/empty state, inert HTML-like titles, and persistence
after refresh. The final counts and wording were correct. However, replacing the
task list during rendering drops focus to the document after Space toggles a
checkbox and after Enter/Escape in the editor; another Tab is needed to return to
the checkbox. Native focusable controls alone do not establish good keyboard UX.

The final handoff opened with “fully tested” despite those explicitly untested
areas. Prefer “core flows verified” followed by named gaps. Both the evaluator and
agent left actual narrow-viewport behavior unverified; responsive CSS exists but
is not a substitute for that test.

**Complex build comparison:** The default-max run was stopped after 397.9 seconds
without any visible model prose, tool call, or file. Its status button immediately
reported “Reasoning now · step 1 · 0 tools” but queued the requested model update
until the next safe step. This is a censored run, not a measured completion time.
The low-effort retry uses a separate GUI instance launched by
`evidence/launch_low.py`, which changes only Kimi's outgoing `reasoning_effort`
field in memory. No production source or user setting is modified. The baseline
left the project empty, so the retry uses the same folder and a fresh session.
The two initial user-prompt hashes, system-prompt hashes, source sizes, and token
estimates match; both included 19,902 characters of retrieved skill context.
This remains a single exploratory comparison, with provider timing and sampling
variance uncontrolled.

The low run's initial implementation passed all 16 generated API tests, but the
independent 32-check run failed four checks. A duplicate-SKU error left an open
transaction, causing the next otherwise valid order to return 500. A single SQLite
connection was shared across request threads: two buyers could both get 201 for
the last unit, and a small concurrent burst produced 500/404 responses and inventory
changes inconsistent with saved orders. An earlier run passed the two-request case,
which illustrates why one lucky concurrency check is insufficient.

In the browser, product creation and validation worked. However, the order form
required typing internal numeric product IDs and expanding a reference table to
find them. This exposes database structure in a business workflow. A product
picker should show name, SKU, and available quantity and submit the ID internally.
The evaluator supplied one repair request covering both transaction problems and
that picker, with the HTTP contract held unchanged.

The repair took 112.8 seconds, added duplicate-error recovery and concurrent-order
regression tests, rolled back the failed insert, and serialized API database access
with a lock. All 18 generated tests and all 32 independent checks then passed,
including two buyers for the last unit, a 20-order burst, rollback, and restart
persistence. These are prototype acceptance checks, not exhaustive proof.

After restarting the evaluator-owned preview with the repaired code, the evaluator
verified product creation, blank-product validation, search, restock, persistence
across server restart, keyboard selection by product name, multi-line ordering,
matching order history, insufficient-stock errors without mutations, dashboard
totals, low-stock filtering, and history after browser refresh. The picker displays
name, SKU, and remaining stock; no numeric ID entry is needed. Remaining polish:
restock/order submissions can drop keyboard focus, and insufficient-stock errors
still refer to “product 1” instead of its name. A real narrow viewport was not
exercised.

Stopping the baseline updated the controls promptly, but left the visible message
“returned no usable response — retrying automatically”. The ledger actually shows
an empty-response-retry event followed by `Interrupted` and session end. Cancellation
should produce a durable “Stopped by you” state and suppress the misleading retry
message; do not treat an interrupted stream as a failed model answer.

## Findings to carry into the next iteration

### Give previews an explicit, managed lifetime

The task-board server initially became reachable, but died while the evaluator
was testing refresh. The agent then tried a detached PowerShell launch; its next
HTTP check still returned connection refused. This is not merely a bad generated
app: the shell tool normalizes `start /B` to foreground execution, and closes a
Windows `KILL_ON_JOB_CLOSE` job at command completion. Its description explicitly
discourages servers and suggests verifying an interactive program's file instead.

Add `preview_start`, `preview_status`, and `preview_stop` (or equivalent service
operations) with a returned handle, readiness probe, bounded log storage, project
ownership, and explicit cleanup. Keep previews alive across tool completion and
project navigation, with a visible stop control. Do not remove process-tree
cleanup from ordinary commands. Teach the model to use this capability and stop
retrying shell detachment when the tool cannot support it.

### Make verification mean successful acceptance checks

The simple project displayed a completed “Verify the result” milestone after
`dir /b & python --version`, before implementation or tests. The milestone also
became complete after a failed test. `app.js:handleToolCall` categorizes every
`bash` call as verification; `_advanceLiveMilestone` completes the previous
milestone when a different activity starts. This is an activity tracker presented
as an acceptance checklist.

Separate activity (“checking Python”, “writing files”, “running tests”) from
requirements with evidence. Keep failing checks failed until a successful rerun
of the relevant check. In `turn_outcomes.py`/`session.py`, replace “a successful
validation-named tool occurred” as the basis of `changed_verified` with explicit
check records that identify the command, result, files/revision, and requirement.
An ordinary successful shell command is not proof that the build works.

### Expose supported reasoning effort and measure the tradeoff

The Kimi backend hardcodes `reasoning_effort="max"`, and capabilities advertise
only `max`. Current official Kimi K3 documentation lists `low`, `high`, and `max`;
thinking is always enabled. Expose those supported choices and persist them per
session. Evaluate low effort for simple changes and high/max for planning or
failed-check repair. Do not promise a speedup until the same fixtures pass with
repeated measurements under both settings.

A separate tiny compatibility probe against the configured API returned HTTP 200
and `OK` with `reasoning_effort="low"` in 3.07 seconds (40 completion tokens). It
confirms support, not coding speed or quality. It ran while the stockroom request
was pending; retain that small concurrency caveat in future timing comparisons.

Source: [Kimi K3 reasoning effort](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart#reasoning-effort).

### Show generation progress without exposing internal reasoning

During long responses the GUI showed “waiting for kimi-k3” and increasingly stale
activity, then several completed file writes appeared together. The Kimi stream
loop updates its internal progress clock on deltas but buffers reasoning and
tool arguments without sending corresponding activity to the GUI. Send throttled
progress events for reasoning and tool-argument generation, separate from
transport keepalives. Show “generating code” versus “waiting for provider”, with
elapsed time and last substantive progress. Keep incomplete tool calls buffered
until valid; this recommendation concerns status only.

### Curate skills before expanding memory

The simple build explicitly rejected unrelated `wordcount.py` skills. The Skills
menu contains repeated task-specific word-count/hello-file entries and four global
pinned references. Interactive retrieval includes up to six skills; pinned
references consume slots first, and keyword matching uses a 0.05 threshold.
The prompt labels the mixed global/project results “prior missions in this
project”, which overstates provenance.

The complex request injected about 4,976 estimated tokens of skills beside an
834-token system prompt. Capability-pack retrieval matches any query-term
substring in the first 4,000 characters and then appends entire selected skill
bodies without a token budget. Give retrieval a total token budget, show brief
descriptions/prerequisites first, and load full procedures on demand. Keep a
visible record of which source was actually used and whether it helped.

Default automatically learned procedures to project scope. Promote a generalized
procedure globally only after verified reuse; deduplicate equivalent procedures,
record prerequisites and actual verification, and filter by stack and task type
before ranking. Show scope, source, confidence, and why a skill matched. Keep
global pins visible but allow task-specific suppression. Evaluate precision on
known positive and negative queries before adding embeddings or raising a
threshold indiscriminately.

For persistent memory, store a small set of project facts, user constraints,
decisions, and proven procedures with sources and freshness markers. Engram's
fallback currently truncates recent conversation entries; that is not a verified
project knowledge base. Distinguish observed facts from model assertions, make
memories editable/deletable, and invalidate file-dependent claims when the project
changes. Recalled text should supply evidence, not override current instructions.

### Make project navigation match its labels

In browser mode, Add Project opens a path entry dialog, which is a useful fallback
when the native picker is unavailable. But its “Open” button only registers the
project; the old project remains active until a second sidebar click. Open should
activate the folder, or the button should say “Add to sidebar”. Clear the previous
session title when changing to an empty project.

The first session remained absent from the sidebar (“No sessions yet”) after
completion; a browser refresh populated it and restored the conversation. Refresh
the sidebar immediately when a session is created/saved.

The simple run's UI said seven changed files; its persisted result correctly
listed three. Render the authoritative normalized changed-file list, with Windows
case/path normalization, rather than accumulating duplicate display paths.

## Proposed prompt additions to evaluate

Keep the invariant prompt compact. Add behavioral guidance and rely on runtime
checks for enforcement:

> For a build, map the requested behavior to a short acceptance checklist. Test
> the public interface with representative edge cases, including platform-specific
> input behavior. When a check fails, investigate the cause before changing its
> expected result. Before finishing, report which requirements were verified and
> which remain untested. Do not repeat passing checks without a new change or an
> unresolved concern.

> For a web app, start a preview, wait for readiness, and exercise the primary
> user journey in the browser. Check persistence after refresh, validation/error
> states, keyboard interaction, and a narrow viewport. A screenshot or successful
> page load alone does not verify interactive behavior.

> Reuse a skill only when its prerequisites and scope match the current request.
> Treat retrieved examples as evidence, not as new requirements. Silently skip
> irrelevant suggestions; explain a conflict only when it affects the user.

These are proposed changes, not a claim that prompt text alone fixes UI state,
memory provenance, or validation accounting.

## Suggested implementation order and repeat test

1. **Managed previews and honest verification state.** A preview must survive tool
   completion and project switching, expose readiness/logs/stop, and remain
   scoped to its project. Seed a failing acceptance test and prove the UI cannot
   label the change verified merely because an unrelated command succeeds.
2. **Kimi effort selection and useful streaming status.** Honor low/high/max in
   requests, session persistence, and the model selector. Emit throttled semantic
   progress separately from connection keepalives. Show timings for first response,
   first edit, preview readiness, and successful verification.
3. **Browser verification skill and platform command recipes.** Use real input
   events, Tab/Space/Enter/Escape, a narrow viewport, refresh persistence, and
   error-state checks. Prefer the project's own test command; for fresh projects,
   use verified recipes instead of repeatedly guessing shell syntax. Replace the
   shell description's “just verify the file” advice for interactive programs.
4. **Skill hygiene and small, sourced memories.** Separate evaluation state from
   user memory; deduplicate examples and require verified, generalizable procedures
   before promotion across projects. Test retrieval on irrelevant as well as
   relevant tasks. Engram persistence itself was not exercised in these live runs.
5. **Navigation and handoff polish.** Open newly added projects, populate sessions
   immediately, normalize changed-file paths, and put the preview/run action and
   verified/untested behavior ahead of long implementation summaries.

For generated business apps, extend the web skill with a simple usability rule:
choose domain objects by recognizable names, not internal IDs; preserve keyboard
focus through list updates; and show errors beside the affected input using the
same names the user sees. Extend the backend skill with negative-then-valid request
sequences and concurrent mutation checks, rather than testing each endpoint only
in isolation.

Add these projects to the existing evaluation dashboard as fixtures with
independent acceptance oracles. For an A/B, use fresh folders and isolated memory,
hold provider/model/prompt fixed except for the tested change, and run at least
three repetitions per setting. Report pass rate and median/tail latency together;
do not select a faster setting that silently weakens correctness. Repeat on local
Ollama and EXO when those endpoints are reachable. The present hosted Kimi runs
cannot establish local-model performance or validate small-context compaction.
