## TL;DR

Run the bootstrap-roguelite spec (8 typed acceptance criteria, all
three validation types) end-to-end through a live `AutonomousMissionDaemon`
twice — once against `deepseek-v4-flash:cloud`, once against
`deepseek-v4-pro:cloud` — and characterize where the pro tier's
extra deliberation actually pays off. Two artifacts:

1. **GA decision** — if both runs reach `verdict=satisfied` and ship
   working code, v0.5.0 is GA-ready.
2. **Tier guidance** — concrete "use pro for X, flash for Y" advice
   we can put in `RESONANT.md` and the autonomous-mission UI.

---

## 1. Why we're doing this

We've shipped the deterministic spine (a1–a4) + the daemon (a5) +
production wiring (a6). Every layer has unit + integration tests, but
no live mission has run yet.

The "convergence is real, not a model mood" contract is mechanically
enforced — but we still don't know:

- **Does the rigorous grill produce usable specs in practice?** The
  prompt's invariants are tested; whether deepseek actually FOLLOWS
  them across a 10–25-question interview is not.
- **Can the daemon converge a [chrome] criterion via REFLECT?** REFLECT
  needs to drive `browser_navigate` + assert via `browser_js`. The
  prompt says how; we've never watched it happen.
- **How long does a typical iteration take?** Token cost? Wall-clock?
  These shape the time-budget UX.
- **Does pro produce meaningfully better outcomes than flash?** Or
  is pro just slower and more expensive? RESONANT.md says pro is
  "for multi-specialist work where the planner / evaluator role
  benefits from more deliberation" — but we haven't validated that
  claim against autonomous missions specifically.

The smoke is what answers these questions before we GA.

## 2. The mission spec we'll run

The canonical bootstrap-roguelite spec from
[`docs/long-running-agents-phase-2.md`](./long-running-agents-phase-2.md) §11.2:

> Bootstrap a TypeScript roguelite skeleton with strict tsc, a
> centered Canvas rendering the player as a single green circle on a
> dark navy background, dev-server-driven via Vite. Six source files
> total, no `any` types.

Eight typed acceptance criteria spanning all three validation types:

```
- [ ] `[bash]` `npm install` exits 0
- [ ] `[bash]` `npm run build` exits 0
- [ ] `[bash]` `npx tsc --noEmit` exits 0
- [ ] `[bash]` `find src -type f | wc -l` output == 6
- [ ] `[bash]` `! grep -rn ': any' src/` exits 0
- [ ] `[chrome]` Navigate to http://localhost:3000; canvas exists
      with width 800 height 600
- [ ] `[chrome]` Center pixel of canvas reports rgb(0±5, 255±5, 153±5)
      via `browser_js`
- [ ] `[vision]` Screenshot shows a single green circle on a dark
      navy background, no other shapes visible
```

Time budget: **4h** (per the spec's recommendation).

This is a deliberately tight scope: ~6 source files, ~150 lines of
code, no third-party assets. A capable model should ship it in
~30–60 minutes; the 4h budget is for one round of revisions if
REFLECT flags anything.

## 3. Run protocol

### 3.1 Setup

For each run (flash, then pro):

1. Fresh project dir: `D:\smoke\roguelite-flash` (or `-pro`)
2. Initialize empty git repo (`git init && git commit --allow-empty -m initial`)
3. Launch `resonant-gui`
4. Set chat model to the appropriate tier in the header dropdown
5. Click 🎯 Mission, toggle ∞ Run autonomously
6. Project picker: point at the smoke dir
7. Feature description: paste the roguelite description verbatim from §2
8. Hit Start

### 3.2 Watch the grill

The rigorous-grill prompt should produce 10–25 questions covering
scope → users → data → integrations → constraints → acceptance →
risks → time budget. Score:

- **Q-count in range:** count questions; flag if <10 or >25
- **Question quality:** subjective 1–5 score per question (does it
  surface a real decision the user must make, vs. busywork?)
- **Recommendations present:** every question must have "My
  recommendation: ..." — count missing
- **Spec emission format:** verify the final spec has the typed
  criteria + Time budget subsection + ≥4 binary criteria

Answer all questions with the canonical answers (record them so the
flash + pro runs see identical input — the grill is supposed to be
deterministic given the same answers, modulo token sampling).

### 3.3 Click "∞ Build autonomously"

Confirm the budget (4h preset). The daemon spawns. Walk away or watch
mid-run.

### 3.4 What we record

For each run, log:

**Per-iteration (from the daemon's events):**
- Iter number
- Picked item ID + title
- Sub-mission duration (seconds)
- Sub-mission outcome (success / fail)
- Commit SHA produced (or `<empty>`)

**Per-reflect-pass:**
- Iter at which it ran
- Verdict (continue / satisfied / blocked)
- Tally: bash_passed/failed/errored, vision_passed/failed/errored,
  chrome_pending count
- Summary text length (proxy for depth)
- Cross-check fired? (model claimed satisfied but daemon overrode?)

**Run totals:**
- Total iterations
- Total wall-clock time
- Total tokens (read from cost-tracking infra)
- Total $$$ (same)
- Final verdict + stop_reason
- Final acceptance summary (X/8 criteria met)
- Did the dev server actually start? (manual eyeball)
- Did the rendered canvas actually look like a green circle? (manual eyeball)

### 3.5 Both runs from the same spec

To make flash vs pro comparable, both runs use the same finalized
spec (the one flash produces if its grill is competent; otherwise
hand-edit until both runs see identical input). Save the spec
markdown alongside the run logs.

## 4. Scoring rubric — flash vs pro

### 4.1 Quantitative

| Metric | Flash | Pro | Tilt |
|---|---|---|---|
| Grill question count | _ | _ | want 10–25 for both |
| Iterations to converge | _ | _ | lower = better |
| Wall-clock to converge | _ | _ | lower = better |
| Tokens spent | _ | _ | lower = better |
| Cost (USD) | _ | _ | lower = better |
| Acceptance criteria met | _/8 | _/8 | higher = better |
| Cross-check overrides fired | _ | _ | lower = better (model claimed false convergence) |
| Failed sub-missions | _ | _ | lower = better |
| Stuck verdicts | _ | _ | lower = better |

### 4.2 Qualitative (1–5 scores)

| Aspect | Flash | Pro | Notes |
|---|---|---|---|
| Grill question quality | _ | _ | does it surface real decisions? |
| Spec rigor | _ | _ | binary criteria? type tags? complete? |
| Implementer code quality | _ | _ | spot-check the diffs |
| REFLECT verdict accuracy | _ | _ | satisfied claims that hold up? |
| REFLECT chrome validation | _ | _ | does it actually drive the browser? |
| Recovery from failures | _ | _ | does it adapt or grind? |

### 4.3 Tier guidance — what we'll write into RESONANT.md

Based on the scores, expect to land somewhere in:

- **"Use flash for…"** — short specs (≤3 criteria), pure-bash specs,
  fast iteration (multiple missions per day)
- **"Use pro for…"** — complex specs with multiple [chrome] /
  [vision] criteria, multi-tier roadmaps, missions you'll run once
  and walk away from for hours
- **"Hybrid pattern"** — possibly: flash for the grill (it's sharper
  in conversation), pro for autonomous (better deliberation under no
  human pressure). v0.5.x could expose a per-phase model selector.

We won't know the exact recommendations until we run the smoke. The
template above is what the conclusion section of this doc will look
like once we have data.

## 5. Failure-mode coverage we want during the smoke

Some failure modes only show up in live runs. Watch for:

- **Grill exhaustion** — model generates the same question twice or
  drifts off-topic. Expect more from flash than pro, but pin the
  rate.
- **Rigorous-grill non-compliance** — model emits a spec WITHOUT
  type tags or with <4 criteria. Our parser will reject; we'd see
  the daemon refuse to start with `misconfigured`.
- **`!` parser miss** — does the model produce `! grep ...` syntax
  correctly? The parser is unit-tested; the grill's prompt example
  uses it, but live behavior is the test.
- **REFLECT JSON drift** — bad JSON, missing keys, fenced vs
  unfenced. `parse_reflect_verdict` is lenient by design; verify
  the leniency actually helps in practice.
- **`browser_navigate` to localhost:3000 before dev server starts**
  — common race. Does REFLECT handle this gracefully (await_user?
  retry?) or just fail the criterion?
- **Vision model unavailable** — if `qwen2.5vl:7b` isn't pulled,
  graceful-degrades to errored. Verify the chat surfaces this
  clearly.
- **Cycle guards trip mid-iteration** — IMPLEMENT specialist gets
  stuck on a build error. Does the daemon's check_failed_streak
  fire correctly?
- **Empty-roadmap-stuck** — if REFLECT verdict=continue but no items
  added, daemon should stop with "stuck" (ADR 10). Watch for it.

## 6. What we'll do if the smoke surfaces real bugs

Standard procedure: fix in flight, capture each as a v0.5.0 patch
release (a8 / a9 / etc.) so the GA tag has every fix folded in.
The implementation guide's §5 (decisions log) gets a new ADR for
each significant judgment call.

The "stuck" rule in ADR 10 is exactly the kind of thing — caught at
unit-test time, would have been caught at smoke too. We expect 1–3
similar bugs from the live runs.

## 7. Beyond v0.5.0

Things deliberately not part of the smoke (saved for follow-ups):

- Resume-from-restart (kill the daemon mid-run, restart, verify
  recovery)
- Cross-mission roadmap continuity (v0.6.0 territory)
- Multiple parallel autonomous missions (architecture supports it,
  UI doesn't)
- Custom model overrides per criterion (e.g., `[vision:llava-next:13b]`)
- Non-DeepSeek models (Qwen3.5, GLM-5.1, etc.) — autonomous
  missions in principle work with any backend that exposes the
  required tool calls; characterizing that is a v0.6.0+ job

## 8. When to run this

After a7 (frontend) ships AND we've confirmed:

- ✅ Rigorous-grill prompt produces typed criteria (a3 unit tests)
- ✅ Daemon iterates correctly with stub hooks (a5 unit tests)
- ✅ Production hooks (factory + session) construct cleanly (a6 unit tests)
- ⏳ Frontend can launch + display autonomous missions (a7)

Then this smoke is the GA gate. Two runs (flash + pro), both
expected to take 1–6 hours each (within the 4h budget plus
post-run review). Total wall-clock investment: 1 day.

## 9. Open questions (to be resolved by the smoke itself)

1. **Does flash's 24K context window hold a full mission run?** The
   roadmap doc grows over time (iteration log entries); REFLECT's
   prompt is 4601 chars + the goal text; the chat session
   accumulates tool calls. Worst-case context blow-up is the
   biggest unknown.

2. **Does pro consistently respect the rigorous-grill question
   count?** Pro likes to over-explain; if it batches 3–4 questions
   per turn, the rigorous mode breaks down.

3. **Is the cross-check ever actually triggered?** A well-behaved
   model never claims false convergence; if neither run trips the
   cross-check, that's good news for the design but bad news for
   our coverage of the cross-check code.

4. **Does the REFLECT JSON parser's leniency get exercised?** Same
   question — if both models produce textbook fenced-JSON output,
   our drift-tolerance is dead code.

5. **What's the actual cost differential?** RESONANT.md doesn't
   commit to a $/h figure. Even an order-of-magnitude estimate
   would make tier guidance more concrete.

The plan is to record the answers in this doc post-smoke, then fold
the tier guidance into RESONANT.md and the implementation guide.
