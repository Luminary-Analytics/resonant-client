## a1: F1 — grill never self-executes

**The finding.** v0.6.2's field run dispatched a marker-append mission. The grill agent correctly recognized it as "a concrete instruction, not a feature" — then **just did the work inline** with `file_edit` + `bash`. Consequences:
- the mission stuck in `drafting` phase forever (never dispatched)
- the autonomous loop never ran → the v0.6.1 `extract_skill_hook` and `queue_curation_hook` never fired
- the self-improvement loop silently missed the simplest, most common class of mission

**Root cause.** The grill prompt had no rule for "what if the request is a concrete one-shot task, not an open-ended feature." The agent improvised — into a dead end.

**The fix (prompt-only, `grill_me.py`).** A new precedence rule at the top of the shared base prompt:

> **Rule 0 — you are an INTERVIEWER, never an IMPLEMENTER.**
> Read-only codebase tools (`glob`/`file_read`/`grep`) for research only.
> Never use `file_edit`/`file_write`/`bash` to do the work yourself.
> A concrete one-shot task → emit a *minimal* Final spec (1–3 criteria),
> don't refuse and don't self-execute.

The rule names the failure mode explicitly (stuck-in-drafting) so the model understands *why*, not just *what*. Rigorous-mode R3 (the 4-criterion floor) gains a one-shot exception that points back at Rule 0 so the two don't contradict.

No parser change needed: `build_roadmap_from_spec` already accepts any non-empty criteria list (the "≥4" was guidance text, never an enforced minimum).

8 tests in [tests/test_grill_me_rigorous.py](../tests/test_grill_me_rigorous.py)::`TestRule0InterviewerNotImplementer`.

**Hardening candidate (deferred):** strip mutating tools from the grill session entirely so self-execution is *impossible*, not just discouraged. The prompt fix is the primary fix; with pro as the v0.6.2 default model, Rule 0's precedence framing holds reliably.

## a2: skill loader wired into the runtime

v0.6.0a4 built `match_skills_for_query` + `format_skills_for_prompt` but the v0.6.2 field run found they were **never called** from the autonomous mission daemon — the read side of the loop was dead code. Skills got extracted (write side) but never surfaced back into a later mission.

**`skill_loader.py`** — `SkillContext` dataclass + `build_skill_context()`: one-shot match+format helper. Best-effort by contract — a matcher exception logs and returns an empty context, never propagates.

**`skills.py`** — `mark_skill_surfaced()`: touches `last_used_at` *without* bumping success/fail counts. Distinct from `record_skill_use`: surfacing a skill into planner context means "still relevant" (resets the curator's 90-day staleness clock) but is not a quality signal. Without this, every agent-created skill would auto-deprecate 90 days after extraction even while being surfaced daily — the loop would quietly collapse.

**`autonomous_factory.py`** — `dispatch_item` (gated by new `enable_skill_loader` flag, default `True`):
- matches skills against each roadmap item's goal text
- appends the formatted skills block to the planner goal
- calls `mark_skill_surfaced` on every surfaced skill
- emits a `skill_context_loaded` event (intent_id, item_id, skill_ids, skill_count)
- whole block is best-effort — a loader failure dispatches without skills, never breaks the mission

16 tests in [tests/test_skill_loader_wiring.py](../tests/test_skill_loader_wiring.py).

## a3: iter-card skill chip

v0.6.2a3 deferred the iter-card chip because the loader wasn't wired. a2 wired it; a3 renders it.

`handleSkillContextLoaded` (app.js) attaches a **"🛠 N skills"** chip to the iter card on each `skill_context_loaded` event. Each skill id is a clickable pill → opens the v0.6.2a3 skill detail modal. The full read side is now visible: a skill feeds an iter → user sees the chip → clicks → reads the skill body.

Live-verified in MCP Chrome: chip renders with the right label + pills; pill click opens the detail modal; no console errors. JS-and-CSS only.

## What this delivers

After v0.6.2, the self-improvement loop existed but barely fired:
1. **Trivial missions bypassed the extractor** — most successful runs captured nothing
2. **The matcher was never called** — extracted skills never fed a later mission

After v0.6.3, the loop is closed on both sides:
1. The grill never self-executes → every mission enters the iter loop → the extractor fires
2. Every dispatched iter pulls relevant prior-mission skills into its planner context, and surfacing them keeps them alive against the curator
3. The read side is visible — the iter card shows which skills fed each iter

And the repo is now MIT-licensed — the foundation for the open-source-flagship goal.
